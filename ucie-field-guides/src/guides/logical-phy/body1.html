1 · What the Logical PHY does

The spec lists its jobs: link initialization and power states (the LTSM), byte-to-lane mapping, redundancy remapping, sideband messaging, scrambling and patterns, and width degrade. This page covers the data-path ones.

Width

One byte per lane

Every lane carries one whole byte per 8 UI, bit 0 first. Wide RDI beats become parallel lanes, not serial bits on one lane.

Spec§4.1.1, p.98

Framing

Valid marks the bytes

A Valid lane, 4 UI high then 4 UI low per 8-UI block, says which 8 UI carry data. No headers or symbols on the wire.

Spec§4.1.2, p.100

Yield

Route around bad bumps

Advanced Package repairs up to two data lanes per 32 using redundant lanes, plus one clock/track lane and the Valid lane. Standard Package halves width instead.

Spec§4.3, p.107–118

2 · Bytes to lanes

Byte 0 goes on lane 0, byte 1 on lane 1, and so on; within a byte, bit 0 is sent first. When the width changes, the rule is the same: one byte per lane per 8 UI. Pick a width to see where a 256B flit's bytes go.

RDI byte k = lane k. RDI byte order (flit byte 0 on RDI byte 0) and lane order line up, so the PHY needs no knowledge of flit formats: a 64B RDI beat on a x64 module is exactly one 8-UI Valid frame. Multi-module and degraded links keep "ascending bytes on ascending active lanes and module IDs".

Spec§4.1.1, p.98 · §10.3.1, p.559–561 · §4.7.1, p.175

3 · Valid framing and clock gating

8-UI blocks, aligned forever

  • For each 8-bit transfer, Valid is high for the first 4 UI and low for 4 UI.
  • In Active, every transfer starts an integer multiple of 8 UI after the rising edge of the first transfer's Valid. The receiver tracks this alignment.
  • An invalid Valid encoding is a framing error: the PHY raises pl_error and retrains.

Spec§4.1.2, p.100 · Table 10-1 (pl_error), p.524

Retimers return credits on Valid

Valid bits (bit 0 first, right to left)Meaning
0000 0000no data, no credit
0000 1111data, no credit
1111 0000no data, 1 credit
1111 1111data, 1 credit

Each credit = 256B. The encodings guarantee detection of 3 bit flips. At ≤ 48 GT/s a receiver may retrain on any bit error or correct single-bit errors; above 48 GT/s it must correct single-bit errors.

Spec§4.1.2.1 and Table 4-1, p.101

Clock gating with a postamble

When Valid goes low, the forwarded clock keeps toggling for a fixed postamble, then stops: 16 UI (8 cycles) at half-rate clocking, 32 UI (8 cycles) at quarter-rate. Not gated if free-running clock was negotiated or the partner requested Runtime Recalibration.

Spec§4.1.3, p.101 · §5.11

Free-running clock mode

The forwarded clock keeps toggling even with Valid low. Must be supported (to turn off dynamic clock gating for normal operation or debug) and negotiated before mainband training. Always used above 32 GT/s.

Spec§4.1.4, p.101 · §4.5.3.3.1, p.137

4 · Sideband serial format

  • One serial data + clock pair per direction per module, 800 MT/s single data rate.
  • Messages are a 64-bit header, optionally with 32 or 64 bits of data. Every serial packet is 64 UI; 32-bit data is padded with zeros in the MSBs.
  • Packets are separated by at least 32 UI of low. A message with data = header, 32 UI low, data, 32 UI low.
  • PMO (Performant Mode, negotiated in MBINIT.PARAM SBFE): no 32-UI gap; packets back to back. Receivers must still accept gaps.
  • PSPT (Priority Sideband Packet Transfer, needs PMO): a pending priority packet may interrupt a normal packet at an 8-UI boundary after 8 UI of idle. Opcode 11111b ends a priority chain and resumes the normal packet; 11110b says another priority packet follows.

Spec§4.1.5–4.1.5.2.1, p.102–104 · §5.13, p.254

Who shares the sideband

Link management packets (training, RDI and Adapter state messages) and Management Port Messages (MPMs) share each sideband. Arbitration is implementation-specific but must not delay link management packets into timeouts; an MPM with data must finish within 512 UI (with PMO) or 768 UI (without).

Spec§4.8, p.182 · §8.2.5.1.2

5 · Lane reversal and Lane ID

Every device must support data lane reversal within a module: local physical data lane 0 connects to remote lane N−1, lane 1 to N−2, and so on (N = 8, 16, 32 or 64). On Advanced Package the redundant lanes reverse too. Track, Valid, Clock and sideband are never reversed.

Every logical data and redundant lane has a unique Lane ID (x64 Advanced: 0–63 data, 64–67 redundant; x32: 0–31 and 64–65). MBINIT.REVERSALMB sends each lane's ID in an unscrambled 16-bit pattern so the receiver can see which transmitter lane it is connected to.

Spec§4.2–4.2.1, p.104–107 · Table 4-7, p.151

Why reversal exists

Two identical dies placed face to face on a package, or one die rotated 180°, see each other's lanes in mirror order. Supporting reversal in silicon means the package designer does not need crossing routes, which on Advanced Package interposers with 25–55 µm bump pitch would cost routing layers.

6 · Lane repair (Advanced) and width degrade (Standard)

Advanced Package: each group of 32 data lanes has two redundant lanes (TRD0/TRD1 for lanes 0–31, TRD2/TRD3 for 32–63). One failure shifts toward TRD0; two failures shift the lower one toward TRD0 and the upper one toward TRD1. Click up to two lanes below to see the mapping for lanes 0–31.

Limits

Up to two data lanes per group of 32 (four per x64 module). If TRD0 (or TRD2) is itself faulty, no lane in that group can be repaired; if TRD1 (or TRD3) is faulty, one can. Unused redundant lanes are tri-stated and their receivers disabled.

Spec§4.3, p.107–108

Clock, Track, Valid

One broken lane among clock (P/N) and track can be remapped onto the redundant clock/track lane (RDCK). Valid has its own redundant lane (RDVLD). Both are detected and repaired in MBINIT.

Spec§4.3.4–4.3.6, p.115–118

Standard: halve the width

x16 → x8 using logical lanes 0–7 or 8–15, whichever half has no faults; x8 → x4 using 0–3 or 4–7. If faults are in both halves, width degrade cannot help. Disabled lanes are tri-stated.

Spec§4.3.7, p.118 · Table 4-9, p.155

7 · Multi-module links

  • Permitted configurations: one, two or four modules. Each has a Module ID, advertised in MBINIT.PARAM.
  • Each module trains on its own sideband through LINKSPEED step 2; the Multi-module PHY Logic (MMPL) then resolves one outcome for all.
  • All modules run at the same speed and width. If a module fails, MMPL degrades to the next permitted configuration (fewer modules, or lower speed), using the flowcharts in Figures 4-47 and 4-48.
  • The MMPL swizzles bytes so the remote receivers see bytes laid out from LSB to MSB in ascending Module ID and Lane ID across all active lanes, even if the partner's Module IDs differ.

Spec§4.7–4.7.1, p.175–178

Which sideband carries what

Training messages (Tables 7-9 and 7-11) go on each module's own sideband. Register accesses, RDI/Adapter link management and other non-vendor messages (Tables 7-8, 7-10) use one sideband: the lowest Module ID whose LTSM is past SBINIT. Retimer credits ride on the Valid of the lowest Module ID in Active. In both cases the receiver may see them arrive on a different module ID.

Spec§4.7.1.1, p.178

Choosing between fewer modules and lower speed. For a speed difference, MMPL compares bandwidth: with CMLS = common maximum speed and HMLS = highest maximum speed of the next lower module count, if HMLS/2 > CMLS it drops modules; otherwise all modules slow to CMLS. The "HMLS/2 > CMLS" case also rescues a link where some modules fail even 4 GT/s (CMLS = 0): those are disabled instead of the whole link going to TRAINERROR.
