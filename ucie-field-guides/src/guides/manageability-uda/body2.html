8 · Why each rule exists

Architecture§8.1.2 p.305

Sideband management first, mainband optional

Every manageable chiplet should have at least one sideband Management Port, enough to build a single management domain over sideband alone. Mainband ports are recommended only for high-bandwidth uses.

Why

The sideband is up before the mainband trains, and can run on an auxiliary clock, so management can discover and configure chiplets whose mainband is still down (or broken). Requiring only sideband keeps the barrier for simple chiplets low.

Real-time example

A package controller discovers four chiplets over sideband, sets their link parameters, then software starts mainband training. Later, a trace dump uses the mainband port for bandwidth.

If you break it

A chiplet manageable only over mainband is invisible whenever its mainband fails to train, exactly when you most need to debug it.

Check it in the spec
  • SpecPort recommendations §8.1.2, p.305
  • SpecMgmt_clk for sideband §10.1.2, p.529
Architecture§8.1.2 p.306

One active Management Director

Several elements may be capable of being Management Director, but only one is active at a time. It configures the network and is the manageability Root of Trust.

Why

Routes, IDs and security settings need a single authority, or two directors could configure conflicting routes. Being the root of trust, it is also the anchor for security decisions.

Real-time example

An I/O chiplet with a microcontroller is the director; a compute chiplet that could also act as director stays passive.

If you break it

Two active directors programming routes for the same traffic class produce loops or black holes.

Check it in the spec
  • SpecDirector role §8.1.2, p.306
  • SpecSelection out of scope §8.1.2
Transport§8.1.3.1 p.307–309

Packets cross the network unmodified

MTPs are produced and consumed by Management Entities and flow unmodified through the network; reserved fields are forwarded as-is and ignored by receivers.

Why

End-to-end integrity (the optional packet CRC) and future extensions both depend on intermediate hops not touching the packet. It also keeps bridges and ports simple.

Real-time example

A packet from chiplet A to chiplet C passes through B's fabric and two UCIe links; its CRC is checked only at C.

If you break it

A port that clears "reserved" bits in transit breaks the packet CRC and silently drops future-version fields.

Check it in the spec
  • SpecUnmodified flow; reserved field rules §8.1.3.1, p.307
Transport§8.1.3.1.1 p.308

Traffic classes are separate ordering domains

Eight traffic classes; no ordering between classes, nor between requests and responses. Every class must make forward progress.

Why

Independence prevents a slow class (for example a long firmware download) from blocking an urgent one (for example a power control message), and lets the director route classes over different links.

Real-time example

A bulk debug dump on TC2 goes over the mainband port; a thermal query on TC0 goes over sideband and returns first.

If you break it

Software that assumes a TC0 response arrives after an earlier TC2 write may read stale data.

Check it in the spec
  • SpecTC rules and routing example §8.1.3.1.1, p.308–309
Link§8.2.3.1 p.372–374

Credits per VC, per RxQ, before any traffic

After capabilities, each MPG returns credits for every enabled VC (requests and responses) on every enabled RxQ-ID, then sends Init Done for that RxQ-ID. Only after Init Done is sent and received on all RxQ-IDs may MTPs flow.

Why

Receive buffers must be known before sending, or packets would overflow. Separate request and response credits avoid request/response deadlock; per-VC credits keep one VC from starving another.

Real-time example

Two RxQs, one VC: four credit-return messages (VC0 request and response on RxQ0 and RxQ1), then Init Done on each RxQ.

If you break it

Credit returns for an RxQ-ID that was not negotiated are a fatal error: mp_mgmt_up stays low with mp_mgmt_init_done high, and the path does not come up.

Check it in the spec
  • SpecInitialization phase steps §8.2.3.1, p.372–374
Link§8.2.5.1.3 p.384

Heartbeat: something every 4 ms, timeout at 8 ms

Each MPG sends an MPM at least every 4 ms per RxQ-ID path (a credit return if nothing else). The receiver's 8 ms Heartbeat timer restarts on any MPM; on timeout the path is torn down.

Why

The management path is long-lived and independent of mainband state, so it needs its own liveness check. Sending at half the timeout guarantees a live partner is never declared dead.

Real-time example

A partner chiplet's management domain is reset; its MPMs stop. Within 8 ms the local receiver times out, drops mp_mgmt_up 16 ms later, and SB_MGMT_UP clears so the path can be renegotiated.

If you break it

An idle MPG that sends nothing for 10 ms is declared dead by its partner even though it is fine.

Check it in the spec
  • SpecHeartbeat timer, 4 ms rule, teardown §8.2.5.1.3, p.384 · §8.2.3.1
UDA§8.3.1 p.391–392

One hub, many spokes

A chiplet's test/debug features (spokes) sit behind a DFx Management Hub that handles discovery, routing to spokes and global security control. A chiplet may have more than one hub.

Why

Software finds a group of debug features through one Management Network ID and one security gate, instead of each vendor's scan, BIST and trace blocks having their own access method.

Real-time example

A DMH at Management Network ID 1040h has four spokes with DMS-IDs 1–4 (for example a scan controller and a memory BIST). A test program enumerates them through the hub's registers using UMAP.

If you break it

Spokes reachable without the hub bypass its security control.

Check it in the spec
  • SpecHub-spoke model, Figure 8-58 example §8.3.1, p.391–392
UDA§8.3.5 · Table 7-1 p.269

UCIe's own debug registers are DMS spokes

The Adapter (Spoke Type 0), PHY (Type 1) or both (Type 2) expose DMS registers, accessed over the FDI config bus with the DMS Register Read/Write opcodes, which always target local registers.

Why

Link debug data (training logs, eye margins, error counters) then appears to UDA software like any other spoke. Restricting DMS opcodes to local registers keeps remote access going through the management network and its security.

Real-time example

A SiP-level test reads PHY lane margins from chiplet B's Type 1 spoke via chiplet B's DMH, over the sideband management path.

If you break it

A DMS Read issued toward the remote die is not allowed; remote spokes are reached through their own DMH.

Check it in the spec
  • SpecSpoke types and access §8.3.5
  • SpecDMS opcodes local only Table 7-6, p.273

10 · Test yourself

Interview-style questions.

Name the three kinds of Management Entity. Basic

Management Element (implements a service), Management Port (connects to a point-to-point management link), Management Bridge (connects to another interconnect).

Spec§8.1.2, p.305

How are MTPs carried on the sideband? Basic

Encapsulated in Management Port Messages (opcodes 10111b without data, 11000b with data) between Management Port Gateways, using per-RxQ credited buffers.

Spec§8.2.1 · Table 7-1, p.269

What are the two phases of sideband management path setup? Intermediate

Negotiation (in MBINIT.PARAM: support and number of RxQs) and Initialization (capabilities with NumVC and Port ID, credit returns per VC per RxQ, Init Done).

Spec§8.2.3, p.371

Why does an idle MPG still send credit returns? Intermediate

To keep the partner's 8 ms Heartbeat timer alive: an MPM must be sent at least every 4 ms per RxQ-ID path.

Spec§8.2.5.1.3, p.384

Where do a UCIe Adapter's DMS registers live, and how are they accessed? Advanced

Spoke Type 0 in the Adapter, Type 1 in the PHY, Type 2 split. Accessed over the FDI config bus using the DMS Register Read/Write sideband opcodes, which only target local registers.
