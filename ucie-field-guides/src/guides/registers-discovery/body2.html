9 · Why each rule exists

Discovery§9.3 p.457 · §9.8 p.520

Host links live in a UiRB found through ACPI

Host UCIe Link DVSECs sit in a per-link UiRB at a static host address, enumerated by the UEDT ACPI table. Only UCIe link registers may live there.

Why

One link may be shared by two Root Ports, so the link's registers cannot belong to either port's config space. A separate region, described once in ACPI with both Root Ports listed, gives software a single place to manage the shared link.

Real-time example

A CPU has two UCIe links, each carrying two Root Ports. UEDT has two UCLS records, each with stack size 2h and two Device/Function numbers.

If you break it

Putting non-UCIe registers in the UiRB is not allowed; a UCIe-aware driver walking it could misread them.

Check it in the spec
  • SpecUiRB rules §9.3, p.457
  • SpecUCLS fields Table 9-84, p.520
Discovery§9.7 p.519

MSI ends the UiRB capability list

The Link DVSEC in the UiRB points to the MSI capability; MSI in the UiRB must have Next Capability = 0h, and software stops the walk when it sees ID 0005h.

Why

The UiRB is not a PCIe function, so there is no standard config-space list to end it. A fixed, short chain (DVSEC then MSI) is easy for firmware to build and for software to walk.

Real-time example

A driver reads the DVSEC header, follows Next Capability to offset 100h, sees ID 0005h, programs MSI and stops.

If you break it

A non-zero next pointer from MSI sends software into undefined UiRB space.

Check it in the spec
  • SpecMSI in UiRB §9.7, p.519
  • SpecNext Capability for UiRB Table 9-5, p.464
ControlTable 9-9 p.468–469

Start training and Retrain are different buttons

Start UCIe Link training does full training (through Link Down if the link was up). Retrain UCIe Link retrains an up link without Link Down, and does nothing if the link is down.

Why

Going through Link Down resets everything beneath the link (protocol state included). Recovery from errors on a working link should not cost that, so a gentler retrain exists, but it cannot bring a dead link up.

Real-time example

Correctable CRC errors climb on an up link: software sets Retrain; traffic pauses but the PCIe hierarchy below survives. After a fatal error took the link down, software uses Start training.

If you break it

Setting Retrain on a down link: nothing happens, and the bit clears. Setting Start on an up link: the link drops and everything below resets.

Check it in the spec
  • SpecBits 10 and 11 Table 9-9, p.468–469
  • SpecLink Status bit 15 Table 9-10, p.471
ControlTable 9-9 p.468

Switch downstream ports train without software

After a conventional reset, a switch DSP's hardware or firmware starts training on its own, without waiting for the Start bit. DSPs may default Raw Format Enable through straps or firmware.

Why

Backward compatibility: an OS that knows nothing about UCIe expects devices below a switch to appear after reset, as they do with PCIe. If the DSP waited for UCIe-aware software, they never would.

Real-time example

A UCIe switch on a server with an older OS: its downstream links train after reset and the endpoints enumerate normally.

If you break it

A DSP that waits for software leaves its endpoints missing on UCIe-unaware systems.

Check it in the spec
  • SpecBit 10 note; Raw Format Enable default Table 9-9, p.468
StatusTable 9-10 p.471

Link Status means RDI and FDI both up

Link Status bit 15 is 1 only if the RDI and the FDI are both up (with two stacks: RDI and any FDI). It stays 1 while the link is retraining.

Why

Software cares whether traffic can flow, which needs the Adapter and the PHY. Keeping it 1 during retrain stops software treating a short retrain as a link loss; bit 16 tells you a retrain is in progress.

Real-time example

During a retrain triggered for eye margining, bit 15 reads 1 and bit 16 reads 1; when bit 16 falls, the retrain is done.

If you break it

Software that waits for bit 15 to drop to detect a retrain waits forever.

Check it in the spec
  • SpecBits 15–16 Table 9-10, p.471
Mailbox§9.5.1.11 p.477

The mailbox is not atomic

Accesses to the mailbox are non-atomic; higher-level software must coordinate so one agent does not overwrite another's request.

Why

A request is several separate register writes (index, data, then trigger). Two agents interleaving them would send a mix of both requests. Hardware arbitration was left out to keep the mailbox simple.

Real-time example

A BMC firmware reads remote eye data while an OS driver reads remote Link Status. Without a lock, the BMC's address and the driver's trigger produce a read of the wrong register.

If you break it

Wrong data returned with Success status: nothing in hardware flags it.

Check it in the spec
  • SpecNon-atomic note §9.5.1.11, p.477
MailboxTables 9-17 to 9-20 p.478–479

Wait for the trigger to clear before reading anything

Read data and the Status field are valid only after the Write/Read trigger bit has cleared from 1. Data is undefined until then.

Why

The access crosses the sideband to another die and back; the trigger is the only completion signal software has. Polling it keeps the hardware free of interrupts for this path.

Real-time example

Software writes the trigger, polls Control bit 0 until it reads 0, checks Status = 11b, then reads Data Low.

If you break it

Reading Data Low straight after the trigger returns stale or undefined data.

Check it in the spec
  • SpecData and Status validity Tables 9-17, 9-20, p.478–479
ErrorsTables 9-28, 9-31 p.483–485

Every UCIe error is masked at reset

All uncorrectable and correctable mask bits default to 1. A masked error still sets its status bit but is not forwarded to the protocol layer for escalation.

Why

A UCIe-unaware OS does not know these errors exist. Forwarding them by default could surface unexplained PCIe/CXL "internal errors". UCIe-aware software opts in by unmasking.

Real-time example

A driver loads, clears stale status, then clears the UE mask bits it handles so fatal Adapter errors escalate through AER.

If you break it

Forgetting to unmask: errors are logged in status but nothing tells the OS.

Check it in the spec
  • SpecMask defaults Tables 9-28, 9-31
  • DerivedOS-compatibility reason
ErrorsTable 9-33 p.487

Clear the status bit to re-arm "first fatal error"

First Fatal Error Indicator keeps its value until software clears the matching UE status bit. Because of a race, it may not always point at the true first error.

Why

The first error is usually the root cause; later errors are often side effects. Locking the field until it is acknowledged keeps the root cause from being overwritten.

Real-time example

An Adapter Timeout (bit 0) then an Internal Error (bit 2) are logged; the indicator reads 00h. Software clears bit 0; if bit 0 recurs later it can become "first" even though bit 2 is older.

If you break it

Software that skips status bits it does not recognize never re-arms the indicator; the spec says it must still clear them.

Check it in the spec
  • Spec[22:18] and race note Table 9-33, p.487
ErrorsTable 9-29 p.484

Only one uncorrectable error defaults to non-fatal

Severity defaults to fatal for every UE except "Sideband Non-Fatal Error Message received".

Why

The other five describe a link that cannot carry on: three are defined as bringing the link down, one is the partner reporting a fatal error, and one means no protocol or format could be agreed. A non-fatal message reports a problem the partner judged survivable, so it keeps that severity.

Real-time example

An endpoint sends a Non-Fatal {ErrMsg}; at the Root Port, UE bit 4 sets and is reported as non-fatal (if unmasked).

If you break it

Treating bit 4 as fatal by default resets a link that the partner said was still usable.

Check it in the spec
  • SpecSeverity defaults Table 9-29, p.484
  • Spec"brings Link Down" notes Table 9-27, p.482
  • Derivedreasoning for the defaults
HealthTable 9-66 p.506

Clear Eye Margin Valid before you retrain

Hardware logs new eye margin measurements only while EMV is cleared. Software clears EMV, retrains, then reads margins once EMV is set.

Why

EMV acts as a latch: once set, the values stay stable for software to read, even if hardware retrains autonomously later. Clearing it is how software asks for a fresh measurement.

Real-time example

A fleet health tool reads margins weekly: clear EMV, retrain, wait, read. If EMV stays 0 after the retrain, the measurement had an error.

If you break it

Retraining with EMV still set returns the old margins, not today's.

Check it in the spec
  • SpecEMV and flow §9.5.3.40, p.505 · Table 9-66, p.506

Interview-style questions.

Where is the UCIe Link DVSEC for a host Root Port, and how does software find it? Basic

In the UiRB, a host-defined static memory region per UCIe link. The ACPI UEDT table lists each link's UiRB base and length and the Root Ports that share it.

SpecTable 9-2, p.457 · §9.8, p.520

Link Status bit 15 reads 1. Can the link be retraining right now? Basic

Yes. Bit 15 stays 1 during retraining; bit 16 shows training or retraining in progress.

SpecTable 9-10, p.471

Code 2h in the width field: what width is it? Intermediate

It depends on the register: x64 in Link Capability Max Link Width, x16 in Link Control Target Link Width, and x16 in Link Status Link Width enabled.

SpecTables 9-8 to 9-10, p.466–470

Give the mailbox steps for reading a 32-bit register on the partner die. Intermediate

Write Index Low (opcode, BE, Addr[18:0]) and Index High (Addr[23:19]); write 1 to the Control trigger; poll until it clears; check Status = 11b; read Data Low. On CA/UR, Header Log 1 holds the request header.

An Adapter Timeout is logged. Which register tells you which handshake timed out? Intermediate

Header Log 2 in the D2D/PHY block (offset 2Ch): bits [3:0] give the reason; for an unanswered LSM request, [9:7] give the request and bit 10 the LSM.

Why might UCIe errors not reach the OS on a fresh system, even though status bits are set? Advanced

All UE and CE mask bits default to 1, and all Error Notification Control enables default to 0. Software must unmask and enable reporting.
