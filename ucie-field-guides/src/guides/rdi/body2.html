7 · Why each rule exists, with real-time examples

Each card gives an RDI rule, the reason behind it, a worked example with real numbers, and what breaks when a design ignores it. Unless a card says otherwise, the numbers assume one x64 Advanced Package module at 16 GT/s and a 64-byte RDI at 2 GHz.

Clocking & width§10.1.1–10.1.2 p.529

One clock, one reset source, zeros out of reset

Both sides of RDI run on lclk, share a reset derived from one source, and drive every output to 0 coming out of reset. RDI has no reset wire of its own.

Why

Every RDI rule is counted in lclk cycles: one cycle of NOP before Active, at least one cycle from request to acknowledge, an error pulse pipelined with its data. Those counts only mean something if both sides see the same edges. Zeros out of reset make a block that wakes early see exactly what an idle partner looks like: lp_state_req 0000 is NOP, pl_state_sts 0000 is Reset.

Real-time example

SoC reset routing releases the PHY 4 cycles before the Adapter. For those 4 cycles the PHY samples NOP with lp_irdy low and does nothing; the Adapter wakes, reads Reset with pl_inband_pres low, and waits. No extra synchroniser between the two is needed.

If you break it

An Adapter that powers up driving Active never makes a NOP→Active edge, and the PHY never leaves Reset.

Check it in the spec
  • SpecSame reset domain from the same source; outputs driven to 0 §10.1.1, p.529
  • SpecSame clock domain; clock-crossing FIFOs only inside a block §10.1.2, p.529
  • SpecNOP for at least one clock before Active §10.3.3.1, p.565
  • IllustrativeThe 4-cycle reset skew
Clocking & width§10.1.2 p.529 · §10.3.1 p.561

NBYTES × lclk must match the link

Pick RDI width and lclk so the interface carries at least what the PHY delivers. The spec's example: 64 bytes at 2 GHz for one x64 module at 16 GT/s.

Why

The receive path has no backpressure (next card). If the interface is slower than the link, the PHY has nowhere to put bytes and something overflows. If it is faster, it simply idles. So the sizing rule is a floor, not a target.

Real-time example

x64 at 16 GT/s: 64 lanes × 16 Gb/s ÷ 8 = 128 GB/s. A 64B RDI at 2 GHz also moves 128 GB/s. Two x64 modules at 32 GT/s move 512 GB/s, so the RDI needs 256B at 2 GHz. A single x16 Standard Package module at 32 GT/s moves 64 GB/s: 64B at 1 GHz is enough.

If you break it

A 32B RDI at 2 GHz on the x64 16 GT/s link can carry only half the traffic; on receive, the PHY's elastic buffer overflows within microseconds.

Check it in the spec
  • Spec64B at 2 GHz matches a 64-lane module at 16 GT/s §10.1.2, p.529
  • Spec128B at 2 GHz for one Advanced module at 32 GT/s §10.3.1, p.561
  • DerivedThe 2-module and Standard Package rows
Clocking & width§10.3.1 p.559–561

Fixed byte order, and 68B flits travel whole on RDI

Flit byte k goes on RDI byte k mod NBYTES in transfer ⌊k/NBYTES⌋, bit 0 to bit 0, in both directions. For 68B formats the Adapter has already inserted the Flit Header and CRC, so RDI carries all 68 bytes, and the next flit starts right after.

Why

The PHY must not need to know flit formats. A fixed mapping lets it stripe bytes to lanes blindly. It also explains a difference from FDI: on FDI a 68B flit shows only its 64B payload, because header and CRC are added below FDI. On RDI the bytes are final.

Real-time example

128B RDI, 68B format: transfer 0 carries Flit 0 bytes 0–67 on RDI bytes 0–67, then Flit 1 bytes 0–59 on RDI bytes 68–127. Transfer 1 starts with Flit 1 byte 60. With 256B flits on a 64B RDI it is simpler: four transfers, bytes 0–63, 64–127, 128–191, 192–255.

If you break it

An Adapter that pads each 68B flit to a 64B boundary on RDI shifts every following byte; the remote Adapter sees CRC errors on every flit.

Check it in the spec
  • SpecLSB of the chunk to byte 0, bit 0 to bit 0, same in Tx and Rx §10.3.1, p.559
  • SpecRDI 128B mapping for 68B formats Figure 10-29, p.561
  • SpecFDI 128B mapping carries payload only Figure 10-28, p.560
  • SpecByte mapping unchanged for multi-module; MMPL handles ordering §10.3.1, p.561
Clocking & width§10.3.1 Implementation Note p.562

Wider than 256B: fill on Tx, accumulate on Rx

On transmit, the Adapter sends valid data across the full width, inserting NOP flits (and for 68B, PDS bytes) as needed. On receive, the PHY accumulates in multiples of 256B; if it has less than the RDI width, it waits for a gap of at least 16 UI (differential clock) or 32 UI (quadrature clock) on the link, then sends what it has on the low bytes and zeros above.

Why

Flit mode moves data over the link in 256B units. A 512B RDI cycle may have only one flit to carry. Zero-filled bytes need a defined meaning, and they have one: a 256B flit header of 0000h with CRC 0000h is silently dropped by the Adapter and is not counted for Runtime Link Testing.

Real-time example

Four x64 modules at 16 GT/s, 512B RDI. One 256B flit arrives followed by idle. The PHY holds it until the link shows 16 UI of no valid data (1 ns at 16 GT/s), then delivers it on bytes 0–255 with bytes 256–511 all zero.

If you break it

A PHY that never flushes partial data waits forever on the last flit before idle; the remote Retry timer fires and replays a flit that was actually received.

Check it in the spec
  • SpecTx full-width rule, Rx accumulation, 16 UI and 32 UI gaps, zero-fill, silent discard of 0000h header with 0000h CRC §10.3.1 Implementation Note, p.562
  • SpecNBYTES ≥ 512 recommended only for a 4-module Advanced link at ≥ 16 GT/s, as a multiple of 256 p.562
  • Derived16 UI at 16 GT/s = 1 ns
Tx path§10.1.4 p.532

Three-way transfer, no bubbles inside a flit

A beat moves when lp_irdy, lp_valid and pl_trdy are all high at a rising edge. Once a flit starts, the Adapter keeps lp_valid and lp_irdy high until its last beat; only pl_trdy may pause it.

Why

The PHY turns each beat into Valid-framed bytes on the wire. If the Adapter left holes inside a flit, the PHY would have to put gaps inside a flit on the link, and the receiver would need to stitch it back together. The matching PHY rule: if the Adapter streams continuously, the PHY must not put bubbles in the valid frames on the link.

Real-time example

A 256B flit on a 64B RDI is 4 beats. pl_trdy drops for 2 cycles after beat 1 (the PHY is inserting parity bytes for Runtime Link Testing). The Adapter holds beat 2 on the bus; the flit takes 6 cycles instead of 4.

If you break it

An Adapter that drops lp_valid mid-flit while waiting on its retry-buffer read port causes a Valid framing gap that the remote PHY can flag as an error, followed by a retrain.

Check it in the spec
  • SpecTransfer condition, no bubbles from Adapter, no assumption on pl_trdy timing §10.1.4, p.532
  • SpecPHY must not insert bubbles in valid frames for a continuous stream §10.1.4 Implementation Note, p.532
  • IllustrativeThe parity-insert cause of the 2-cycle stall
Tx path§10.1.5 Impl. Note p.533 · Table 10-1 p.522

lp_irdy is an early wake-up hint

lp_irdy may rise before lp_valid to say "data is coming"; the PHY ungates its clocks and raises pl_trdy when ready. lp_irdy must not be presented while status is Reset, except briefly on a LinkError → Reset transition, and the PHY ignores it in Reset.

Why

A PHY in Active may gate parts of its transmit path between bursts. Waking it on lp_valid would cost the ungate time on every first flit. A separate "I'm about to send" signal hides that cost. This is why RDI, like FDI, has two sender-side signals where AXI has one.

Real-time example

The Adapter knows two cycles ahead that a flit is leaving its retry buffer. It raises lp_irdy at cycle 0, lp_valid at cycle 2. The PHY takes 2 cycles to ungate, so pl_trdy is already high when the first beat appears, and nothing is lost.

If you break it

A PHY that treats lp_irdy without lp_valid as a transfer captures garbage. A checker that requires lp_irdy and lp_valid to rise together flags a legal design.

Check it in the spec
  • SpecEarly indication; Figures 10-4 and 10-5 §10.1.5 Implementation Note, p.533
  • SpecNot in Reset except LinkError→Reset; PHY ignores in Reset Table 10-1 (lp_irdy), p.522
  • Illustrative2-cycle ungate time
Tx pathTable 10-1 p.522

pl_trdy only in Active, or to drain in LinkError

The PHY asserts pl_trdy only when status is Active, or while running a stallreq/stallack handshake in LinkError so the Adapter can drain.

Why

Outside Active the link is not carrying data: it is training, retraining, in PM or down. Accepting bytes would mean dropping them silently. The LinkError exception lets the Adapter empty its pipeline cleanly when software intends to recover the link rather than reset the SoC.

Real-time example

The PHY moves status to Retrain after the stall handshake. pl_trdy is already low, so even if the Adapter's lp_valid logic glitches high for a cycle, no beat is transferred.

If you break it

A PHY that holds pl_trdy high in Retrain accepts a flit it can never send; the Adapter's retry buffer believes it went out and waits for an Ack that never comes.

Check it in the spec
  • Specpl_trdy restriction Table 10-1 (pl_trdy), p.522
  • SpecLinkError drain rules §10.3.3.7, p.568
Tx path§10.1.4 Impl. Note p.532

Parity inserts should match the RDI width

For Runtime Link Testing with parity, the receiving Adapter may answer {ParityFeature.Nak} if software asks for a number of 64-byte parity inserts that is not 256B or a multiple of the RDI width.

Why

Parity bytes are inserted into the byte stream. If they do not fill whole RDI beats, every following flit is shifted inside the beat, and the Adapter needs a barrel shifter across the full width just for a test feature. The spec lets it refuse instead.

Real-time example

64B RDI: 64B, 128B or 256B of parity are all fine. 256B RDI: only 256B lines up. Software asking for 3 × 64B on a 256B RDI gets a Nak.

If you break it

A test that sweeps every insert count against a 256B RDI DUT and expects Ack every time reports a false failure.

Check it in the spec
  • SpecNak permitted; width examples §10.1.4 Implementation Note, p.532
  • SpecRuntime Link Testing using Parity §3.9, p.95
Tx path§10.3.4 p.572 · Table 10-5

Vendor bits ride on the Valid lane (Raw Format)

In Raw Format, lp_/pl_vendor_defined can carry one extra bit per 8 UI per module by reusing the Retimer-credit encodings on TXVLD/RXVLD: 0000_0000b = not valid; 0000_1111b = valid, bit 0; 1111_1111b = valid, bit 1. They are pipeline-matched to data and meaningful only when valid is high.

Why

Some streamed protocols (the spec names JESD204E as an example) need a sideband bit per frame for sync markers or ECC. The Valid lane already carries an 8-UI pattern per frame, and without a Retimer its credit encodings are unused, so it costs no extra bumps.

Real-time example

Four x16 modules, 64B RDI: VS = 4, one bit per module. On a 128B RDI, VS = 8: bits 0–3 cover the first of every two valid frames per module, bits 4–7 the second.

If you break it

Asserting lp_retimer_crd in this mode corrupts the vendor bit; the spec says Retimer credits never assert here.

Check it in the spec
  • SpecEncodings Table 10-5, p.572
  • SpecVS examples Table 10-6, p.573
  • SpecSingle-bit error correction permitted on RXVLD; Retimer credits never assert §10.3.4, p.572
Rx path & errors§10.1.4 p.532 · §10.1.2 p.529

No backpressure on receive

Data moves whenever pl_valid is high. There is no ready signal from the Adapter. The PHY may put bubbles inside a flit; the Adapter must cope.

Why

Bits arrive from the far die at a fixed rate. The PHY cannot ask the remote transmitter to wait without a round trip across the link, so a ready signal would just move the overflow problem into the PHY. Bubbles are allowed because lane deskew, multi-module merging and clock crossings do not produce data on every cycle.

Real-time example

A four-module PHY merges bytes from modules whose deskew FIFOs fill at slightly different times. Beat 2 of a flit arrives one cycle late; pl_valid drops for that cycle and the Adapter's CRC engine simply pauses.

If you break it

An Adapter that puts a clock-crossing FIFO on its receive path sized for average traffic overflows on the first long burst. The spec warns about exactly this.

Check it in the spec
  • SpecNo backpressure, bubbles permitted §10.1.4, p.532
  • SpecInternal clock-crossing must account for no backpressure §10.1.2, p.529
  • IllustrativeThe deskew cause of the bubble
Rx path & errorsTable 10-1 (pl_error) p.524

pl_error arrives with or before the bad data

pl_error is a pulse, only in Active, pipeline-matched so it reaches the Adapter no later than the corrupted bytes. If pl_error and pl_valid are high together, the Adapter discards that flit, even a partial one. After it, the PHY sends no valid data (without pl_error) until a retrain completes.

Why

A Valid framing error means the PHY lost track of where frames start, so the bytes around it cannot be trusted. Signalling with or before the data lets the Adapter drop them before they reach CRC checking or the Protocol Layer. The retrain that follows re-establishes framing.

Real-time example

256B Latency-Optimized flit, store-and-forward off. The Adapter has forwarded the first 128B half to FDI. pl_error hits during the second half after only 64 of its 128 bytes. The Adapter sends 64 dummy bytes to finish the half and cancels it with pl_flit_cancel. After the retrain, Retry replays the flit.

If you break it

A PHY that raises pl_error one cycle after the bad beat lets that beat reach CRC. With 68B flits that is usually caught; with Retry disabled it can reach the Protocol Layer.

Check it in the spec
  • SpecPipeline matching, discard rule, no valid data until retrain, both examples Table 10-1 (pl_error), p.524
  • SpecRetry disabled: map to Uncorrectable Internal Error. Raw Format: forward to Protocol Layer pipeline-matched p.524
  • SpecPHY asserts pl_error with the flit, then stall handshake, then Req.Retrain §4.5.3.7.2, p.170
Rx path & errorsTable 10-1 p.524 · §10.0 p.521

Error pulses are events, and severity depends on Retry

Error signals are pulses of one or more cycles; the receiver treats each rising edge as one event and ignores pulse length. With Retry enabled, the Adapter ORs pl_error and pl_cerror into Correctable Internal Error logging. With Retry disabled or in Raw Format, only pl_cerror is correctable.

Why

Pulse length varies with clock ratios and pipeline depth, so counting cycles would make the error count depend on implementation. Severity follows recoverability: if Retry will replay what pl_error destroyed, nothing was lost, so it is correctable. Without Retry, data may be gone, so it escalates.

Real-time example

A PHY drives pl_cerror for 3 cycles after an eye-margin alarm. The Adapter's error counter increments once. If the PHY was clock-gated in L1 at the time, it first completes pl_clk_req/lp_clk_ack, then pulses.

If you break it

An Adapter that counts cycles logs 3 errors instead of 1 and trips a retrain threshold too early.

Check it in the spec
  • SpecPulse definition; rising edge is a new event §10.0, p.521
  • SpecOR rule and Retry dependence; clock-gating exit before pulsing Table 10-1 (pl_cerror, pl_nferror), p.524
  • Specpl_nferror has no architected PHY source; treat like a remote Non-Fatal ErrMsg p.524
State control§10.3.3.1 p.565 · §10.3.3.8 p.569–570

Leaving Reset needs an edge, not a level

Reset → Active (or LinkReset, Disabled) happens only after lp_state_req is NOP for at least one clock in Reset and then changes. After LinkError, LinkReset or Disabled → Reset, the PHY must not even start training until it sees NOP→Active or a Chapter 4 training trigger.

Why

The edge is the Adapter saying "now". A level could be stale: left over from before a link-down, or driven by logic that has not finished resetting. It also gives software a way to hold the link down: the Protocol Layer delays its NOP→Active on FDI, and the Adapter forwards that edge to RDI. The Adapter must forward it even if pl_inband_pres is 0, and may go back to NOP and clock-gate while it waits.

Real-time example

After a Downstream Port Containment event the link sits in LinkError. Software clears DPC status. Status goes to Reset, but nothing trains until the Protocol Layer, under software control, toggles NOP→Active. The Adapter mirrors it on RDI and the LTSM starts.

If you break it

A PHY that retrains on its own after LinkError → Reset brings the link up under software that is still cleaning up error state.

Check it in the spec
  • SpecReset exit rules §10.3.3.1 and Table 10-4 note a, p.565
  • SpecNo training before NOP→Active or a Chapter 4 trigger; forward even with pl_inband_pres = 0 §10.3.3.8, p.569–570
  • SpecDPC hold example Figure 10-32, p.576
State control§10.1.6 p.534

Active means both PHYs agreed

The PHY sends {LinkMgmt.RDI.Req.Active} only after sampling lp_state_req = Active, answers with Rsp.Active only after sampling Active locally, and shows Active only after it has both sent and received Rsp.Active. This happens on every Active entry.

Why

Each PHY reports "my Adapter is ready to receive" by responding. Only when both responses have crossed does either side know the other's Adapter is listening. That is why the Adapter must raise Active only when it is ready to receive and send parameter exchanges.

Real-time example

Die 1's Adapter is still loading firmware-provided capabilities. Die 0 sends Req.Active; Die 1's PHY holds its Rsp.Active until its own Adapter drives Active, about 50 µs later. Die 0 stays in Reset all that time and does not start Stage 3 too early.

If you break it

A PHY that answers Rsp.Active before sampling local Active lets the remote Adapter send {AdvCap.Adapter} to an Adapter that is not listening; parameter exchange times out.

Check it in the spec
  • SpecSteps 1–6 and "every entry to Active" §10.1.6, p.534
  • SpecMessage codes: Req 01h/01h, Rsp 02h/01h Table 7-8, p.275–276
  • IllustrativeThe 50 µs firmware delay
State control§10.3.3.4 p.566–567

Who can start a Retrain, and how it ends

The Adapter requests Retrain for: the software Retrain bit, CRC or parity errors over a threshold, a Raw Format Protocol Layer request, or another implementation reason. The PHY enters Retrain on a Valid framing error, a remote request, or an Adapter request. Exit from a Retrain entered from Active needs a fresh NOP→Active; from L1 an Active level is enough.

Why

The PHY sees signal problems (framing); the Adapter sees data problems (CRC). Both need a way to ask for a retrain. The NOP→Active requirement on exit gives the Adapter a pause point: it can finish side handshakes, such as the Parity Feature exchange, before the link goes Active again.

Real-time example

The Adapter counts 8 CRC errors in 1 ms (its own threshold) and requests Retrain. The PHY stalls the Adapter, exchanges Req/Rsp.Retrain, retrains, and reaches LINKINIT. The Adapter drives NOP for one cycle, then Active, after its parity-feature handshake finishes.

If you break it

An Adapter that holds Active through Retrain (no NOP cycle) leaves the link stuck in Retrain forever.

Check it in the spec
  • SpecTriggers for both sides; exit rules; the reason for the NOP→Active rule §10.3.3.4, p.566–567
  • SpecThreshold algorithm is implementation-specific p.566
  • Illustrative8 errors in 1 ms
State control§10.3.3.4 p.566 · §3.5 p.89

Retrain is pushed up and resets PM and Retimer credits

A Retrain on RDI is propagated to every Adapter LSM that is Active (not to CXL vLSMs). On entry, any PM handshake is cancelled, and the Retimer credit counter resets to the value advertised at bring-up. A Retimer drains its buffers and retrains its far link too.

Why

During Retrain no bytes cross the link, so anything in flight is lost and anything negotiated mid-flight is suspect. Resetting to known values on both dies is simpler than reconciling partial state. CXL vLSMs are exempt because CXL defines its own Retrain behaviour above the Adapter.

Real-time example

The Adapter had sent Req.L1 when the PHY detected a framing error. Retrain entry wipes the PM attempt. After the link is Active again, the Adapter starts PM entry from scratch if the idle conditions still hold.

If you break it

An Adapter that keeps counting Retimer credits across a retrain under-counts after the Retimer flushed its buffers, and throttles the link permanently.

Check it in the spec
  • SpecPropagation, Retimer credit reset, Retimer drain, PM reset §10.3.3.4, p.566–567
  • SpecRDI Retrain before Adapter LSMs; no Retrain exit request before all relevant LSMs are in Retrain §3.5, p.89–90
State control§10.3.3.8 p.569 · §10.3.5.1 p.575

LinkReset and Disabled reach RDI only when every stack agrees

Each Adapter LSM may go to LinkReset or Disabled on its own. RDI follows only if all Adapter LSMs are in a link-down state, and then takes the highest priority among them: LinkError › Disabled › LinkReset. The PHY then runs the matching sideband handshake; with no answer in 8 ms, RDI goes to LinkError.

Why

Two protocol stacks share one physical link. A PCIe hot reset on stack 0 must not drop the CXL traffic on stack 1. Priority picks the stronger action when stacks disagree, and the timeout guarantees a dead partner cannot leave the link half-down.

Real-time example

Stack 0 (PCIe) enters LinkReset because software set SBR. Stack 1 stays Active, RDI stays Active. Later stack 1 enters Disabled. Now both are down, so the Adapter requests Disabled on RDI (Disabled outranks LinkReset), and the PHY sends {LinkMgmt.RDI.Req.Disable}.

If you break it

An Adapter that forwards stack 0's LinkReset straight to RDI takes stack 1 down in the middle of its traffic.

Check it in the spec
  • SpecCommon-state propagation, priority, 8 ms timeout §10.3.3.8, p.569
  • SpecRDI to LinkReset only if all Adapter LSMs are there §10.3.5.1, p.575 · §10.3.3.5, p.567
  • SpecIf already link-down and not training, no remote notification needed Implementation Note, p.571
Power management§10.1.7 p.535

Ask for PM only when the mainband is silent

The Adapter requests L1 or L2 on RDI only after every Adapter LSM is already in that PM state: retry buffer empty, no flits and no Ack/Nak waiting. The PHY sends the PM Request only after sampling the request and finishing the stallreq/stallack handshake.

Why

Once in PM the mainband PLL may be off. Any flit still in flight, or an Ack the far side is waiting for, would be lost and trigger a replay into a link that is asleep. Making the upper state machines go first means the whole stack is idle before the wires go quiet.

Real-time example

A PCIe stack's L1 vote arrives while the Adapter still has 3 unacknowledged flits. It waits until the remote Acks drain the retry buffer (a few hundred ns), moves the Adapter LSM to L1 with the remote Adapter, and only then drives lp_state_req = L1.

If you break it

Requesting L1 with a non-empty retry buffer: the remote Nak arrives after the PHY has powered down, and the replay has to wait for a full L1 exit.

Check it in the spec
  • SpecAdapter LSMs first; empty retry buffer; no traffic; stall before PM Request §10.1.7, p.535
  • SpecAll Adapter LSMs in PM before RDI SM §3.5, p.90
  • Illustrative3 flits, a few hundred ns
Power management§10.1.7 p.535

A PM request is held until it resolves

Once the Adapter drives L1 or L2, it cannot change lp_state_req until status shows PM, Active.PMNAK, Retrain or LinkError. Requests that arrive meanwhile (Active from the Protocol Layer, a remote PM-exit for an Adapter LSM) are accepted but processed only after the status resolves, and the Adapter brings RDI back to Active first.

Why

The PHY is in the middle of a two-die negotiation. Pulling the request back would leave the remote PHY with a half-finished handshake. Holding the request until a definite answer keeps both dies' views consistent.

Real-time example

200 ns after requesting L1, the Protocol Layer asks for Active. The Adapter stores it. RDI resolves to L1 at 900 ns. The Adapter then drives Active on RDI, the link exits L1, and only after RDI is Active does the Adapter wake its stack.

If you break it

Switching lp_state_req back to Active mid-handshake: the remote PHY reaches L1 while the local one is still Active, and the next Req.Active looks like a PM exit to one side and a protocol error to the other.

Check it in the spec
  • SpecHold, sink-and-delay, resolution cases §10.1.7, p.535
  • Illustrative200 ns and 900 ns
Power management§10.1.7 p.535–536

2 µs to answer, 1 µs to say no, 2 µs before asking again

A PHY that receives a PM Request answers within 2 µs. If its own Adapter also wants PM, or status is already PM, it sends the PM Response. If both request and status stay Active for 1 µs, it sends {LinkMgmt.RDI.Rsp.PMNAK}. A PHY that receives PMNAK moves to Active.PMNAK and may retry no sooner than 2 µs, unless the remote side sends its own PM Request.

Why

The 1 µs window lets two dies whose idle timers expire at slightly different times both reach PM without a NAK. The 2 µs bound stops a requester waiting forever. The 2 µs back-off stops two PHYs from flooding the sideband with PM Requests while one side stays busy.

Real-time example

Die 0 asks for L1 at t = 0. Die 1's Adapter decides to idle at t = 0.6 µs and requests L1: Die 1's PHY replies Rsp.L1 and both enter L1. If Die 1 had stayed busy until 1 µs, it would have replied PMNAK, and Die 0 could not ask again before about 3 µs.

If you break it

A PHY that NAKs at once wastes most PM opportunities on links with bursty traffic; one that never NAKs leaves the requester stuck when the other side has work.

Check it in the spec
  • Spec2 µs response, 1 µs PMNAK rule, ≥ 2 µs retry §10.1.7, p.535–536
  • SpecRsp.PMNAK is Msgcode 02h, MsgSubcode 02h Table 7-8, p.276
  • DerivedRetry time ≈ 1 µs + transit + 2 µs
Power management§10.1.7 p.536 · §4.5.3.9 p.172

L1 exits through Retrain, L2 through Reset

Exit starts when the Adapter requests Active. From L1, the LTSM goes to MBTRAIN.SPEEDIDLE and RDI shows Retrain. From L2, the LTSM goes to RESET and RDI shows Reset, followed by full training and a fresh Adapter parameter exchange. If a remote Req.Active arrives while in PM, the PHY does pl_clk_req and moves to Retrain to prompt its Adapter.

Why

L1 keeps the trained settings, so a short retrain is enough. L2 allows deeper power-down, which may lose them, so it costs a full bring-up. The Active Request timeout counters start only when the LTSM reaches LINKINIT, so retraining time is not counted against the handshake.

Real-time example

Die 1 wants to send a TLP and requests Active. Its PHY sends Req.Active and starts L1 exit training. Die 0's PHY gets the message in L1, raises pl_clk_req, shows Retrain; Die 0's Adapter requests Active. Both reach LINKINIT, swap Rsp.Active, and show Active.

If you break it

A PHY that starts the Active Request timer at the PM exit request times out during a slow MBTRAIN and sends the link to TRAINERROR for no reason.

Check it in the spec
  • SpecExit flow, Retrain on remote request, timers start at LINKINIT, L2 exit via Reset §10.1.7, p.536 · Figure 10-11, p.538
  • SpecLTSM exits: L1 → MBTRAIN.SPEEDIDLE, L2 → RESET §4.5.3.9, p.172
  • SpecL2 exit causes a fresh Parameter Exchange §10.3.3.8, p.570
Power management§10.1.7 p.535 · §4.5.3.9.1 p.172

The sideband stays awake

In PM the PHY may power down its mainband (for example, turn off the PLL), but the sideband logic and its PLL stay on in L1. The Adapter may clock-gate its own sideband logic once RDI is in PM and nothing is outstanding. In L2, sideband power-down is allowed only if L2SPD was negotiated.

Why

Every PM exit and every link-down request is a sideband message. If the sideband slept, nothing could wake the link except a full reset. L2SPD is the opt-in for systems that accept re-running SBINIT on wake in exchange for lower L2 power.

Real-time example

In L1 the PHY's mainband PLL is off, but its 800 MHz sideband clock still runs. The remote Req.Active arrives as a 64-bit serial packet; the PHY wakes the Adapter with pl_clk_req and starts L1 exit.

If you break it

Gating the sideband receiver in L1 without L2SPD makes the link unable to leave L1 when the remote die wants to.

Check it in the spec
  • SpecSideband and its PLL stay on in L1; Adapter may gate its sideband logic §10.1.7, p.535
  • SpecL2 Sideband Power Down, negotiated §4.5.3.9.1, p.172
  • Spec800 MHz sideband clock §1.1.3, p.43
Handshakes & clock gating§10.1.3 p.530

Gate clocks only in quiet states

Coarse clock gating is allowed when status is Reset, LinkReset, Disabled or PM. It is not allowed in Active, Retrain or LinkError.

Why

In Active data can arrive any cycle with no backpressure. In Retrain the PHY needs the Adapter to see status changes immediately. LinkError is excluded on purpose: a link that is down because of an error should not also be asleep, and the spec expects error handlers to get it out of LinkError if saving power matters.

Real-time example

An idle link in L1 lets both the Adapter and most of the PHY gate their lclk trees. A link stuck in LinkError waiting for software keeps both clocked until software resets it.

If you break it

An Adapter that gates in LinkError misses the PHY's Reset status after the 16 ms residency and never sends NOP→Active.

Check it in the spec
  • SpecPermitted states and the LinkError exclusion §10.1.3, p.530
Handshakes & clock gating§10.1.3.1 p.530

Adapter wakes the PHY before it speaks

The Adapter must complete lp_wake_req/pl_wake_ack before changing lp_state_req or lp_linkerror out of a gated state, and before sending on lp_cfg. For a state change it may move the request without waiting for the ack; for lp_cfg it must wait.

Why

A state request is a level: the PHY will see it whenever its clock returns. A sideband packet is a burst of several cycles on an 8, 16 or 32-bit bus, so all of it must land in clocked flops. The Adapter may keep lp_wake_req high through Active, Retrain and LinkError, where the PHY cannot gate anyway.

Real-time example

A 128-bit register-write packet on a 16-bit lp_cfg takes 8 cycles. If the PHY's clock came back on cycle 3, cycles 0–2 would be lost. Waiting for pl_wake_ack first avoids that.

If you break it

A register write to the PHY during L1 is silently dropped; compliance software reads back stale values.

Check it in the spec
  • SpecRules 1–6 §10.1.3.1, p.530
  • SpecNC = 8, 16 or 32 Table 10-1 (lp_cfg), p.526
  • Derived128 bits ÷ 16 = 8 cycles
Handshakes & clock gating§10.1.3.2 p.530–531

PHY wakes the Adapter before anything it must notice

The PHY does pl_clk_req/lp_clk_ack for: pl_inband_pres changes, LinkError entered on its own from Reset or PM, a remote PM-exit request, any pl_cfg packet, error pulses, and pl_phyinrecenter in a gated state. For exits from Reset or PM to anything but LinkError, it raises pl_clk_req before the status changes and holds it until the status has moved.

Why

A gated Adapter cannot see a level change or a one-cycle pulse. The handshake guarantees its clock is running first. pl_inband_pres may change before the ack (it is a level and will be seen once the clock returns), but it is not guaranteed observed until the handshake completes.

Real-time example

An Adapter gated in Reset waits for training. When the LTSM reaches LINKINIT, the PHY raises pl_clk_req and pl_inband_pres together, and keeps pl_clk_req up until status leaves Reset, as the spec recommends.

If you break it

A PHY that pulses pl_cerror while the Adapter is gated: the error is never logged, and correctable-error counts in software are wrong.

Check it in the spec
  • SpecRules 1–9 §10.1.3.2, p.530–531
  • SpecGated Adapter waits for pl_inband_pres before requesting Active rule 8, p.531
  • SpecError pulses and pl_phyinrecenter need the handshake in gated states Table 10-1, p.524–525
Handshakes & clock gatingTable 10-1 p.525–526

No gating? Still answer the handshake

A side that does not support dynamic clock gating still stages the incoming request for one or more cycles and returns it as the ack. A side whose partner cannot gate may tie its own request to 1.

Why

The requester's logic waits for the ack. If one side skipped the handshake, every partner would need a "my peer does not gate" configuration bit. Turning the request around costs one flop and keeps every Adapter compatible with every PHY.

Real-time example

A test-chip PHY without clock gating: pl_wake_ack = lp_wake_req delayed by one flop. The Adapter's driver code is identical to the one used with a production PHY that gates.

If you break it

Wiring pl_wake_ack = lp_wake_req combinationally creates the zero-cycle path the handshake forbids, and a loop if the Adapter's request also depends on the ack.

Check it in the spec
  • SpecStage and turn around; tie-to-1 permission Table 10-1 (pl_clk_req, lp_clk_ack, lp_wake_req, pl_wake_ack), p.525–526
  • SpecAt least one clock between request and ack §10.1.3.1 rule 2, §10.1.3.2 rule 2, p.530
Handshakes & clock gating§10.3.2 p.563

Stall at a clean boundary before every Active exit

On RDI the PHY must use pl_stallreq/lp_stallack whenever it leaves Active for Retrain, PM, LinkReset or Disabled. The Adapter acks only at a clean boundary: a flit boundary for 256B formats; for 68B formats, after PDS, its zero padding and any parity bytes are sent. While acked, lp_valid and lp_irdy are low.

Why

The PHY must stop sending in a place the remote receiver can recognise. For 68B flits that means the stream has been closed with PDS so the remote side knows where data ends. FDI in Flit mode needs the stall only for PM, because the Adapter itself owns flit boundaries there; on RDI the PHY does not.

Real-time example

The PHY raises pl_stallreq mid-flit. The Adapter finishes the current 4-beat flit (the PHY keeps accepting with pl_trdy, gaps allowed), then raises lp_stallack. The PHY can now send Req.Retrain knowing no partial flit is on the wire.

If you break it

Acking mid-flit for 68B format leaves the remote Adapter with a partial flit and no PDS; it reports a framing error and the retrain loops.

Check it in the spec
  • SpecRDI must use stall for every Active exit; rules 1–10; clean boundary definitions §10.3.2, p.563
  • SpecRecommended: lp_stallack on a free-running clock rule 10, p.563 · Table 10-1, p.525
  • SpecTwo acceptable lower-layer orderings Implementation Note, p.564–565
Handshakes & clock gatingTable 10-1 p.526

Sideband config bus: credits, atomic writes

lp_cfg/pl_cfg carry Chapter 7 packets on an NC = 8, 16 or 32-bit bus. Each credit covers 64 bits of header plus 64 bits of data, even for packets with less. Initial credits are design parameters, so none are returned at reset. Register writes must be atomic: all 32 or 64 bits update in one cycle.

Why

Fixed-size credits make buffer accounting trivial. Design-parameter initial credits avoid a startup exchange on a bus that may be gated. Atomicity matters because NC can be as narrow as 8 bits: without it, software could read a half-written 64-bit register.

Real-time example

NC = 8. A 64-bit register write arrives as 16 byte-wide cycles. The PHY assembles the full packet and updates all 64 bits on one clock, then returns one credit on pl_cfg_crd.

If you break it

A credit return pulsed while the receiver is clock-gated is lost. The sender's counter leaks one credit per occurrence until the bus deadlocks. Credit returns follow the same wake rules as packets.

Check it in the spec
  • SpecCredit size, no init credits, clock-gating rule for returns, atomicity Table 10-1 (pl_cfg*, lp_cfg*), p.526
  • SpecFlow-control rules §7.1.3.1
  • Derived128 bits ÷ 8 = 16 cycles
Errors & link-downTable 10-1 p.523 · §10.3.3.7 p.568

lp_linkerror: a wire, not an encoding

lp_linkerror takes the PHY to LinkError at once and keeps it there while high. No stall handshake is required. The Adapter ORs its own internal fatal conditions with lp_linkerror from every FDI.

Why

Error containment (for example a CXL viral escalation) must be as fast as possible. A request encoding would wait behind whatever request is in progress; a dedicated wire bypasses all of it. The OR makes the path from any Protocol Layer to the PHY a single gate.

Real-time example

A CXL.cachemem stack detects an uncorrectable error mid-transfer. Its lp_linkerror on FDI ORs through the Adapter to RDI on the next cycle. The PHY goes to LinkError and sends {LinkMgmt.RDI.Req.LinkError}. The Adapter cleans its datapath after sampling LinkError for one cycle, whether or not it gets pl_trdy.

If you break it

An Adapter that registers lp_linkerror through its state-request arbiter adds the latency of an in-progress PM handshake to containment.

Check it in the spec
  • SpecDefinition, viral example, OR rule Table 10-1 (lp_linkerror), p.523
  • SpecNo stall needed; datapath cleanup after one cycle §10.3.3.7, p.568
  • SpecRDI LinkError before Adapter LSMs §3.5, p.90 · §10.3.3.8, p.569
Errors & link-down§10.3.3.7 p.569 · §10.3.3.8 p.569

16 ms in LinkError: twice the 8 ms timeout

A PHY that sends a LinkError, LinkReset or Disabled request and gets no answer in 8 ms moves to LinkError. Every lower layer stays in LinkError at least 16 ms before it may exit to Reset.

Why

If the sideband died, the remote die never received the LinkError message. But it will notice something is wrong (its own sideband handshakes time out after 8 ms) and go to LinkError on its own. Staying 16 ms guarantees the local die is still down when that happens, so the two dies cannot end up one up and one down.

Real-time example

Die 0's Adapter asserts lp_linkerror at t = 0, but the sideband lane is broken. Die 1 gets nothing; its pending handshake times out at about 8 ms and it enters LinkError. Die 0 may leave LinkError at 16 ms, after Die 1 is safely down.

If you break it

A 1 ms residency lets Die 0 retrain while Die 1 still believes the link is Active; Die 1 interprets the training patterns as data.

Check it in the spec
  • Spec16 ms minimum residency and its reason §10.3.3.7, p.569
  • Spec8 ms no-response → LinkError §10.3.3.8, p.569
  • SpecLinkError → Reset needs Active request, lp_linkerror = 0, residency met §10.3.3.7, p.569
Errors & link-downTable 10-1 p.524 · §4.5.3.8 p.171

pl_trainerror is a level that outlives the error

pl_trainerror signals a fatal PHY error. The PHY moves status to LinkError and holds pl_trainerror until RDI goes from LinkError to Reset. Meanwhile the LTSM must stay in TRAINERROR as long as RDI is in LinkError.

Why

A fatal error needs software attention and may raise an interrupt, depending on the Uncorrectable Internal Error mask and severity in the Adapter. A level that persists until recovery lets a gated or busy Adapter still see it, and lets software read the cause while the link is held down.

Real-time example

MBTRAIN fails at every speed. The LTSM enters TRAINERROR, the PHY raises pl_trainerror and LinkError. The Adapter logs an Uncorrectable Internal Error. Software reads the PHY's status registers over the still-working sideband, then resets the link.

If you break it

Pulsing pl_trainerror for one cycle: an Adapter that was mid clock-gating handshake never logs the fatal error.

Check it in the spec
  • SpecLevel until LinkError → Reset; escalation by mask and severity Table 10-1 (pl_trainerror), p.524
  • SpecTRAINERROR held while RDI is in LinkError §4.5.3.8, p.171
Management transport§10.1.2 p.529 · Table 10-2 p.527–529

A management path that works with mainband clocks off

When Management Transport over sideband is supported, the RDI config bus and the Table 10-2 signals may run on a separate Mgmt_clk (for example an auxiliary clock). mp_mgmt_pkt/pm_mgmt_pkt mark each transfer as a management packet (MPM) or a link management packet. mp_rxqid/pm_rxqid steer MPMs to the right sideband link and receive queue.

Why

Management (firmware update, telemetry, debug) must reach a chiplet even when its mainband is untrained or powered down. Putting the path on its own clock decouples it from lclk. The extra handshakes (mp_wake_req/pm_wake_ack, pm_clk_req/mp_clk_ack) are independent of RDI state.

Real-time example

A board controller pushes firmware to a chiplet whose mainband is in L2. Traffic flows through the Management Port Gateway on Mgmt_clk over the sideband. RDI pl_state_sts never leaves L2.

If you break it

Delivering pm_param_done (a 2-clock pulse) before mp_clk_ack to a gated gateway: it misses the pulse and never learns how many modules negotiated management transport.

Check it in the spec
  • SpecSeparate Mgmt_clk allowed §10.1.2, p.529
  • SpecPacket steering, RxQ-ID, credits per 64 bits, pulses after mp_clk_ack Table 10-2, p.527–529
Management transportTable 10-2 p.527

The gateway can hold or restart training

mp_stall_after_mbinit_param tells the PHY to stall receive-side training at MBINIT.PARAM using the SBFE stall encoding. mp_mgmt_init_start (a 2-clock pulse) forces the LTSM to RESET, through TRAINERROR if needed, and can take the mainband down.

Why

Management transport is negotiated at MBINIT.PARAM. If the gateway is not ready, letting mainband training race ahead would finish without it. A stall lets the management path catch up. Forcing RESET is the only way to re-run that negotiation once the link is up.

Real-time example

After a management-domain reset the gateway raises mp_mgmt_port_gateway_ready together with mp_stall_after_mbinit_param. The LTSM pauses at MBINIT.PARAM until the gateway drops the stall.

If you break it

A gateway that pulses mp_mgmt_init_start without first dropping mp_mgmt_up violates the spec and leaves the PHY's SB_MGMT_UP flag inconsistent.

Check it in the spec
