UCIe Retimers and Compliance Field Guide

Two topics the spec scatters across six chapters. Retimers carry a UCIe link off the package and must keep two dies, two UCIe links and one external link in step. Compliance is how a die is tested against a known-good Golden Die, using injection and margining registers. Retimer rules are collected here from §1.3, Chapter 3, Chapter 4 and Chapter 9; compliance from Chapter 11 and §9.5.4.

1 · Why these exist

Retimers

UCIe stops at the package edge

UCIe links are short, on-package channels. A UCIe Retimer sits on the package next to a die and drives an Off Package Interconnect (for example an electrical or optical cable) to a second retimer on another package, so two dies on different packages can talk.

Spec§1.3, p.47 · §1.0, p.39

Retimers

Three links pretending to be one

Die 0 ↔ Retimer 0 is one UCIe link, Retimer 1 ↔ Die 1 another, plus the external link. Each die must see what looks like one consistent link, so retimers resolve parameters, link states and flow control between the ends.

Spec§1.3, p.47–48

Compliance

Test against a known-good die

A DUT is packaged with a Golden Die (a known-good UCIe implementation of every layer) on a known-good bridge, interposer or package. Each layer is checked on its own. Support is optional, but without it a device may not join the compliance program.

Spec§11.0, p.579

Compliance

The spec defines hooks, not tests

Chapter 11 defines the hardware the DUT must have (injection, compliance modes, margining). The test setup, channel model, test details and Golden Die details are left to a separate document.

Spec§11.0, p.579

2 · Retimer topology

What a retimer is responsible for

  • Reliable flit transfer across the external link (one of three options, below).
  • Resolving link and protocol parameters with the remote retimer, so both dies end up with the same width, speed, protocol and flit format.
  • Resolving Adapter LSM and RDI states with the remote retimer.
  • Flow control from die to retimer using credits.

Spec§1.3, p.47–48

What is left to the implementation

How retimers talk to each other over the external link (message transfer, parameter resolution, retimer-to-retimer flow control) is implementation-specific. UCIe only defines what each die sees on its own UCIe link.

Spec§1.3, p.48

4 · Credits: the one flow-control rule a die must follow

Die → retimer is credited, retimer → die is not

  • Every retimer has a Receiver Buffer for flits from its local die.
  • It advertises the buffer size in parameter exchange: "Retimer" = 1 and Retimer_Credits, a 9-bit count.
  • 1 credit = 256 B of data, including any FEC and CRC.
  • The die must not send without a credit. These credits sit on top of protocol credits (for example PCIe PH/PD).
  • Data sent to the retimer must be consumable by the remote die with no other dependency.
  • Retimer → die traffic has no UCIe credit flow control.

Spec§1.3, p.48 · §3.2.1.2, p.63–64

00001111bFlit data, no credit (the normal Valid frame)
11110000bNo flit data + 1 credit release
11111111bFlit data + 1 credit release

Bit 0 is sent first. The encodings detect up to three bit flips. At ≤ 48 GT/s a receiver may retrain on any error or correct single-bit errors; above 48 GT/s it must correct single-bit errors.

Spec§4.1.2.1, Table 4-1, p.101

Reset on leaving Active

The die resets its credit counter to the advertised value whenever RDI leaves Active. The retimer drains or dumps its buffer before re-entering Active. Because credits are re-advertised, the first transfer after Active entry cannot be a credit-only frame.

Spec§1.3, p.48 · §4.1.2, p.100

Parity bytes are invisible to the retimer

Runtime-link-testing parity bytes do not consume retimer credits, are not written into the buffer and are not forwarded: the feature characterizes only the local UCIe link.

Spec§3.9, p.96

5 · Keeping both dies in step

Link training with a retimer

1

External link and each UCIe link may come up independently.

2

Each UCIe link trains SBINIT → MBINIT (local parameters) → MBTRAIN at its local data rate.

3

The retimer asks for the remote side's rate and width over the external link.

4

If they differ and the retimer needs a match, it retrains from LINKSPEED. This may repeat.

5

When the configuration suits both ends, the link goes through LINKINIT to ACTIVE.

Spec§4.5.2, Figure 4-32, p.130

Parameter exchange: Stall, don't time out

The Adapter's parameter exchange timeout is 8 ms (−0% / +50%), counted only while RDI is Active, and reset by any Stall message. A retimer resolves capabilities with its remote partner and merges its own before answering its die, sending the Stall message once every 4 ms meanwhile.

Spec§3.2.1.2, p.70

Link states: answer only when the far die has

If Die 0 sends Active Request, Retimer 0 must confirm through Retimer 1 that Die 1 received it and replied Active Status, then reply to Die 0. Stall every 4 ms meanwhile. The external link enters low power only when both dies have.

Spec§3.5, p.90

Retimer and DP/UP bits

A retimer's Adapter sets "Retimer" and clears "DP" and "UP". The dies set DP or UP so the retimer knows whether it faces a downstream or upstream port.

Spec§3.2.1.2, p.64

6 · Retimers as software sees them

Registers

Reached only through the mailbox

Retimer registers live in sideband config and sideband MMIO space, not visible to host software directly. The RP/DSP mailbox reaches the retimer nearest the host; the EP/USP mailbox reaches the far retimer. An EP/USP sets "Sideband mailbox Registers Present" only when paired with a retimer.

Spec§9.3, p.457–458 · Table 9-7, p.465

Identity

Link Capability bit 8

A retimer sets the "Retimer" bit in its UCIe Link Capability register so software can tell it apart. Its Link DVSEC Next Capability is 0h and Register Locator offsets are reserved.

SpecTable 9-8, p.466 · Table 9-5, p.464 · Table 9-13, p.476

Errors

Forwarding across the external link is vendor-specific

A retimer next to an RP/DSP reports errors to it with sideband error messages. A retimer next to an EP/USP reports to its partner retimer by a vendor-specific mechanism.

SpecTable 9-12, p.473–475

Management

Optional management transport

Retimers may join the UCIe management network. If they do, they follow all the generic chiplet rules and can forward management packets between their UCIe side and the retimed side.

Spec§8.2.6, p.391

7 · Compliance setup

The test package

  • Golden Die: known-good UCIe across all layers. Its Adapter supports every flit format and can inject consistent and inconsistent sideband messages; it can force timeouts on sideband messages and state residency timers.
  • DUT: one or more dies that have already passed sort/pre-bond testing.
  • Channel: known-good bridge or interposer (Advanced Package) or package (Standard Package).
  • Compliance software: runs on the Golden Die or on an external controller attached via a test/JTAG port.

Spec§11.0, p.579 · §11.2, p.580 · §11.3, p.581

Layers tested separately

Protocol: PCIe/CXL use their own compliance; Streaming is out of scope. Adapter: injection hooks, required in any Adapter that supports a flit format, retimers included. PHY: margining, BER, lane skew, Tx EQ.

Spec§11.1–11.3, p.580–581

Two preconditions

The sideband must come up without firmware, because it carries all compliance register accesses. Software reads the capability registers before testing any optional feature.

Spec§11.0, p.579

Test/Compliance register block

Register Locator block ID 1h. 8 KB: Adapter registers at D2DOFF (offset 10h, normally 0), PHY registers at PHYOFF (offset 14h, normally 4 KB). Software must read both offsets rather than assume them.

Spec§9.5.4–9.5.4.3, p.507–508

Test flits vs NOP flits

Test flits carry 01b in Byte 1 bits [7:6] of the flit header, go through the Tx retry buffer if Retry is enabled, and are CRC-checked at the receiver like any flit, then cancelled (for example with pl_flit_cancel) so the Protocol Layer never sees them. NOP flits bypass the retry buffer.

Spec§11.2, p.581 · Table 9-73, p.509

Reading the results (Adapter Test Status, 30h)

  • [2:1] Flit Tx Injection: 00b none, 01b in progress (stays here in continuous mode), 10b finished, 11b stopped early.
  • [4:3] Flit Rx Status (RW1C): 01b at least one Test flit received without CRC error.
  • [10:9] Retry Injection: 01b at least one error injected, 10b sequence finished.
  • [11] Number of Retries Exceeded Threshold.
  • Status fields clear on the 0→1 of their enable bit.

9 · PHY compliance: margining and stepping

Getting into @PHY-Compliance

1

Put the Adapter in a compliance mode (01b or 10b) first.

2

Set Compliance Enable (Compliance Control 1 bit 0) in every module.

3

Retrain the link. On the next PHYRETRAIN the PHY enters PHY Compliance. RDI may reach Active but pl_trdy is never asserted.

4

Use the operation trigger and setup registers; TRAINERROR in this mode does not reset them.

Spec§9.5.4.5, p.514 · Table 9-78, p.514

Operations you can trigger

Operation Type: 001b Tx-initiated D2C point test, 010b Tx-initiated eye width sweep, 011b Rx-initiated point training, 100b Rx-initiated width sweep, 101b step from MBTRAIN.RXDESKEW to DATACENTER1 above 32 GT/s (for sweeping Tx EQ). Start with a 0→1 on the trigger bit.

SpecTable 9-78, p.515

Knobs

Disable scrambling; add or subtract an Rx Vref offset (step by one each time); mask even/odd UIs, or UI groups A–D above 32 GT/s; choose per-lane or aggregate compare; enable Track.

SpecTables 9-78 to 9-80, p.514–517

Per module

Registers repeat per module at PHYOFF + 000h, 400h, 800h, C00h. All modules of a link must be in PHY Compliance together.
