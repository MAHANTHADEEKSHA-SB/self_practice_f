UCIe Sideband Field Guide

The sideband is UCIe's always-on control channel: link training messages, register access to the far die, link state handshakes, parameter exchange, error messages and management traffic. The same packet format is used on three hops: FDI config bus, RDI config bus and the sideband wires between dies. This guide covers the packet types, who may send what to whom, flow control on each hop, and why there is no retry.

1 · Why a separate sideband

Before the mainband works

Train the link with something that already works

Mainband training needs both dies to agree on every step. The sideband is a slow (800 MT/s), single-lane-pair link that comes up first in SBINIT and then carries every training handshake.

Spec§7.0, p.268 · §4.5.3.2, p.133

While the mainband sleeps

Wake, manage, and debug

PM exit starts on sideband; it stays on in L1. Register access to the far die, error messages and (optionally) management transport all use it, so software can see a chiplet whose mainband is down.

Spec§7.0, p.268 · §10.1.7, p.535

Simple and clean

BER 1e-27: parity, no retry

At low speed and short reach the sideband is clean enough that no retry is needed. Each packet carries control and data parity; a parity error is a fatal Uncorrectable Internal Error.

Spec§7.1.3.2, p.298

One format, three hops

Same packets on FDI, RDI and the wire

The Protocol Layer, Adapter and PHY exchange the same packet format on their config buses that the PHY sends over the bumps. Only srcid/dstid rules and flow control differ per hop.

Fragmented registers

A register may have bits in the Protocol Layer, the Adapter and the PHY. Each layer implements the bits it does not own as read-only 0, and on a read the upper layer ORs its own value with the response from below. Writes simply have no effect on bits a layer does not own.

4 · Header fields

A header is 64 bits (two 32-bit phases on a 32-bit config bus). Data, when present, is a second 64-bit packet. On the wire, bit 0 of phase 0 goes first.

Register access request
  • Addr[23:0]: for memory and config, {RL[3:0], offset}; RL selects the register locator (Fh = protocol registers shadowed in the Adapter). DMS opcodes use Addr[21:0] as offset in the Spoke's space (up to 4 MB) and always target local registers.
  • BE[7:0]: byte enables, need not be contiguous; BE[7:4] reserved for 32-bit requests.
  • Tag[4:0]: unique per outstanding request; matches the completion.
  • EP: data poison. A receiver must not write poisoned data and returns UR.
  • CR: one end-to-end credit return (remote Adapter credits only).
  • CP / DP: even parity over header (excluding DP) and over data.

SpecTable 7-5 and Table 7-6, p.272–273

Completion
  • Status: 000b Successful Completion; 001b Unsupported Request. A UR from an aborted request carries 64b data = the original request header, so the requester can log it. A timed-out request also completes with UR, without data.
  • Tag, BE returned as in the request (so the requester need not save BE).
  • srcid/dstid reserved on local hops; match by Tag.

SpecTable 7-7, p.274–275

Messages
  • MsgCode[7:0] and MsgSubcode[7:0] identify the message.
  • MsgInfo[15:0] carries extra information, for example 0000h regular / FFFFh Stall on responses, or a credit count.
  • Messages with data carry 64 bits of payload (capabilities, training parameters, results).

Spec§7.1.2.2–7.1.2.3, p.275–291

Management Port Messages (MPMs)

With Management Transport over sideband, MPMs carry encapsulated Management Transport Packets or gateway messages (capabilities, credit return, init done, PM, vendor-defined). They use their own MPM header and RxQ-ID, and are sunk unconditionally into per-RxQ buffers.

6 · Flow control, timeouts and errors

Local loops: FDI and RDI

  • Each transmitter/receiver pair has its own credit loop, at most 32 credits, a design-time parameter (no init credits are sent).
  • One credit = 64-bit header + 64-bit data, whatever the packet actually carries.
  • Requests and messages need a credit. Completions do not, and the receiver must always sink them.
  • Messages must make forward progress and never block behind register access requests.
  • Parity errors on FDI/RDI or in a priority packet: Uncorrectable Internal Error and RDI to LinkError.

Spec§7.1.3.1, p.298 · Table 10-1, p.526

End to end: across the link

  • Remote Adapter/PHY registers are reachable only through the mailbox: one mailbox register, so one outstanding mailbox access at a time.
  • 4 credits for remote register access requests (the extra three allow debug accesses after a timeout). Counter initialized to 4 at reset exit and when RDI goes Reset → Active. Credits come back via the CR bit or {Nop.Crd}; the counter saturates.
  • Link Management requests: one outstanding per MsgCode; each has a response.
  • All requests that expect a response time out after 8 ms. A Retimer that needs more time sends a Stall every 4 ms; a Stall resets the requester's timer.
  • No retry on the wire (BER 1e-27). Parity error = fatal UIE.

Spec§7.0, p.268 · §7.1.3.2–7.1.3.3, p.298–300

7 · Why each rule exists, with real-time examples

Each card gives a sideband rule, the reason, an example, and what breaks without it.

Architecture§7.0 p.268 · §7.1.1 p.269

No direct Protocol Layer to Protocol Layer sideband

The Protocol Layer can access local Adapter and PHY registers over FDI, and remote registers only through the Adapter's mailbox. It may never address the remote Protocol Layer over sideband.

Why

Protocol-to-protocol traffic (config space, MMIO) belongs on the mainband, where protocol ordering and flow control apply. The sideband is for link-level control. Keeping remote access behind one mailbox also keeps the far die's sideband load bounded.

Real-time example

Host software wants the device die's PHY training status. It writes the mailbox Index and Control registers in the host Adapter; the Adapter sends a Configuration Read across the sideband and fills the mailbox Data register with the completion.

If you break it

A Protocol Layer that emits remote-die requests on FDI uses dstid values that are reserved on FDI; the Adapter must reject them.

Check it in the spec
  • SpecMailbox mechanism; FDI only carries register access §7.0, p.268
  • SpecNo PL ↔ PL over sideband §7.1.1, p.269
  • SpecMailbox registers §9.5.1.11–9.5.1.16, p.477–479
Architecture§7.0 p.268

Fragmented registers: OR on the way up

Bits a layer doesn't own are read-only 0 there. On a read, each layer ORs its own bits with the response from the layer below before answering.

Why

Some registers describe things spread across layers (for example a status register with protocol, Adapter and PHY bits). Software sees one register at one address; the hardware assembles it without any layer needing to know the others' bit positions.

Real-time example

A status register with bit 0 in the Adapter and bit 7 in the PHY. The Adapter forwards the read to the PHY, gets 0x80, ORs its 0x01, and returns 0x81 up to the Protocol Layer.

If you break it

A layer that returns X or stale values for bits it doesn't own corrupts the OR and software sees phantom status bits.

Check it in the spec
  • SpecHierarchical decoding §7.0, p.268
  • IllustrativeBit positions
Integrity§7.1.3.2 p.298

Parity only, because the link is that clean

Each packet has even Control Parity (CP) over the header and Data Parity (DP) over data. There is no retry; any parity error is a fatal Uncorrectable Internal Error.

Why

The sideband runs at 800 MT/s over short reach with BER 1e-27 or better. A retry protocol would add buffers and state on a link that, in practice, never errors. Detecting the impossible case and escalating is enough.

Real-time example

At 800 Mb/s and BER 1e-27, the expected time between bit errors is about 1.25e18 seconds, roughly 40 billion years.

If you break it

Computing CP over DP as well, or using odd parity: every packet looks corrupted to a compliant receiver and the link goes to LinkError at bring-up.

Check it in the spec
  • SpecNo retry; parity → fatal UIE §7.1.3.2, p.298
  • SpecCP excludes DP; even parity Table 7-5, p.272 · Table 7-7, p.274
  • DerivedError interval
IntegrityTable 7-1 note a p.269

Priority packets can't alias with normal ones

Priority packets have a different header size and parity position. Their opcodes (11110b, 11111b) plus header bits 5 and 6 are chosen so a single bit error can never turn one format into the other.

Why

Parity catches single-bit errors only if the receiver checks the right bit. If one flip changed the format, the receiver would check parity in the wrong place and might accept a corrupted packet.

Real-time example

Opcode 11011b (message with data) differs from 11111b in one bit, so bits 5 and 6 must also differ: a single flip cannot make a valid-looking priority packet.

If you break it

A future vendor extension that reuses bits 5 and 6 freely could reintroduce aliasing; the spec says new packet types must preserve this property.

Check it in the spec
  • SpecNote a of Table 7-1 p.269
  • DerivedThe opcode-distance example
Flow control§7.1.3.1 p.298

One credit size for everything

On FDI and RDI each credit covers 64 bits of header plus 64 bits of data, even for a packet with no data. Maximum 32 credits; initial credits are design parameters.

Why

Sideband traffic is low-rate; buffer efficiency matters less than simplicity. One credit type means one counter per direction and no fragmentation logic.

Real-time example

A receiver advertising 8 credits needs 8 × 128 bits = 128 bytes of buffer. A burst of 8 Link Management messages (header only) uses all 8 credits.

If you break it

A transmitter that charges half a credit for header-only packets overruns a receiver that sized for full credits.

Check it in the spec
  • SpecCredit size and maximum §7.1.3.1, p.298
  • DerivedBuffer size
Flow control§7.1.3.1 p.298 · §7.1.3.3 p.299

Completions never wait for credits

Transmitters do not check credits before sending Register Access Completions; receivers must always sink them. Completions do not consume end-to-end credits either.

Why

Classic deadlock avoidance: if completions needed credits held by requests that are themselves waiting for completions, both directions could stall. Guaranteeing completions always drain breaks the cycle.

Real-time example

The PHY's request buffer is full of remote reads. Their completions still flow back to the Adapter, freeing tags and letting new requests in.

If you break it

Putting completions in the credited request queue: under load, requests and completions block each other and the sideband hangs.

Check it in the spec
  • SpecCompletion sinking rules §7.1.3.1, p.298 · §7.1.3.3, p.299
  • BackgroundDeadlock reasoning
Flow control§7.1.3.3 p.299

Four end-to-end credits, one mailbox

Each Adapter provisions for at least four remote register access requests; the sender's counter starts at 4 (at reset exit and on RDI Reset → Active) and saturates. The PHY must also provision space for at least one request and completion from each side in addition to local credits.

Why

The mailbox allows one outstanding access, but if that access times out, software may want to issue debug reads without waiting for the lost credit. Four gives headroom. Re-initializing on every RDI Active entry recovers any credits lost while the link was down.

Real-time example

A remote read times out at 8 ms (completed as UR). Software reads the remote PHY's error log next; that request still has a credit, though the first credit has not returned yet.

If you break it

A non-saturating counter that receives (N−4) extra credit returns from a bigger partner overflows and wraps to 0.

Check it in the spec
  • Spec4 credits, init points, saturating counter, extra returns §7.1.3.3, p.299
Flow control§7.1.3.3 p.299

One outstanding Link Management request per MsgCode

Every Link Management request has a response, and a source may have only one outstanding request per MsgCode. All non-vendor messages must sink and never block others.

Why

State machine handshakes are naturally one-at-a-time. Limiting them that way means the receiver's message buffer can be sized at design time (a fixed number of message types), so messages never need credits to be guaranteed.

Real-time example

The PHY may have {LinkMgmt.RDI.Req.L1} (MsgCode 01h) and an Adapter LSM request (MsgCode 03h) outstanding at the same time, but not two RDI requests.

If you break it

Sending Req.L1 and then Req.Active before the L1 response: the partner's single message slot for that MsgCode overflows.

Check it in the spec
  • SpecOne per MsgCode; must sink §7.1.3.3, p.299
  • SpecMsgCodes Table 7-8, p.275–277
Flow control§7.0 p.268

8 ms timeout, Stall every 4 ms

Every sideband request expecting a response times out after 8 ms. A Retimer that needs longer must send a Stall response every 4 ms, and must not stall forever. A Stall resets the requester's timer.

Why

A Retimer often has to ask the die on the far side of an off-package link before it can answer. Stalling at half the timeout guarantees the requester never expires while the Retimer is still working.

Real-time example

Retimer receives {LinkMgmt.Adapter0.Req.Active} at t = 0, forwards it over its external link, and sends Rsp.Active with MsgInfo FFFFh (Stall) at 4 ms and 8 ms. The real response arrives at 9 ms and is forwarded.

If you break it

Stall interval of 8 ms or more: on the +0% tolerance edge the requester times out first.

Check it in the spec
  • SpecTimeout, Stall, no indefinite stall §7.0, p.268
  • SpecStall MsgInfo FFFFh Table 7-8, p.276
Flow controlTable 7-7 p.274–275

UR carries the request header back

If a completer aborts a request, it returns UR with 64 bits of data holding the original request header. A request that times out completes with UR and no data. Poisoned writes are not applied and return UR.

Why

The requester can log exactly which request failed without storing every header it sent, which keeps requester state small.

Real-time example

A Configuration Read to a reserved RL encoding returns UR with the read's header as data; the mailbox status shows the failure and software can see the bad address.

If you break it

Returning UR without data for an aborted request: the requester's header log stays empty.

Check it in the spec
  • SpecStatus encodings Table 7-7, p.274–275
  • SpecReserved RL → UR; EP → UR Tables 7-5, 7-6, p.272–273
Flow control§4.7.1.1 p.178

Multi-module: one sideband for shared traffic

Register accesses and non-training messages use the sideband of the lowest Module ID past SBINIT; training messages go on each module's own sideband.

Why

Training is per module; everything else belongs to the single link above them. Choosing one sideband keeps request/response ordering simple.

Real-time example

Four-module link: {MBTRAIN.*} messages run on all four sidebands in parallel; {AdvCap.Adapter} goes only on module 0's sideband.

If you break it

Spreading register requests over modules for "bandwidth": completions may arrive on a different module and out of order relative to expectations.

Check it in the spec
  • SpecAssignment rules §4.7.1.1, p.178

10 · Verification

Checkers

  • Opcode legal for the hop (FDI: register access only). §7.0 · Table 7-1
  • srcid/dstid legal per Tables 7-2 to 7-4; reserved on completions. p.270–271
  • CP/DP even parity; parity error → UIE + RDI LinkError. §7.1.3
  • Credit counters never negative; completions sent without credit check and always sunk. §7.1.3.1
  • Tag unique among outstanding requests; completion returns Tag and BE. Tables 7-5, 7-7
  • One outstanding LM request per MsgCode; every LM request gets a response. §7.1.3.3
  • E2E credits init 4, saturating; CR bit and Nop.Crd handled. §7.1.3.3
  • 8 ms timeout reset by Stall; Stall interval ≤ 4 ms from Retimers. §7.0

Scenarios

  • Every opcode at NC = 8, 16, 32 with BE patterns (non-contiguous). Table 7-5
  • Remote read/write through the mailbox; completion with UR (reserved RL, EP set, timeout). Table 7-7
  • Fragmented register read across PL, Adapter and PHY. §7.0
  • Two stacks issuing register accesses concurrently. §7.0
  • Injected CP and DP errors on each hop. §7.1.3
  • Credit starvation: receiver holds credits; messages still progress. §7.1.3.1
  • Priority packet chains interrupting long MPMs (PSPT). §4.1.5.2

11 · Test yourself

Interview-style questions.

What are the five sideband packet categories? Basic

Register accesses, messages without data, messages with data, Management Transport messages (MPMs), and Priority Sideband Traffic Packets.

Spec§7.1.1, p.269

How does the Protocol Layer read a register on the far die? Basic

Through the Adapter's sideband mailbox registers: it programs index and control, the Adapter issues the remote request over RDI and the sideband, and puts the completion data and status into the mailbox.

Spec§7.0, p.268 · §9.5.1.11–9.5.1.16

How big is one sideband credit on FDI/RDI? Basic

64 bits of header plus 64 bits of data, regardless of what the packet actually carries. Up to 32 credits per direction.

Spec§7.1.3.1, p.298

Why is there no retry on the sideband? Intermediate

Its BER is 1e-27 or better. Parity detects the extremely rare error, and it is escalated as a fatal Uncorrectable Internal Error.

Spec§7.1.3.2, p.298

Why don't completions need credits? Intermediate

Deadlock avoidance: requests waiting for credits must never block the completions that would free them. Receivers must always sink completions.

Spec§7.1.3.1, p.298 · §7.1.3.3, p.299

What does a UR completion carry? Advanced

For an aborted request, 64 bits of data holding the original request header, so the requester can log it. For a timed-out request, no data.

SpecTable 7-7, p.274–275

Four E2E credits but only one mailbox: why? Advanced

The mailbox allows one outstanding access; the extra credits let software issue debug register accesses after a timeout without waiting for the lost credit to come back.

Spec§7.1.3.3, p.299

How does a Retimer avoid timing out a requester while it waits on its far link? Advanced

It sends the response with the Stall encoding (MsgInfo FFFFh) every 4 ms; each Stall resets the requester's 8 ms timer. It must not stall indefinitely.
