UCIe Retimers and Compliance Field Guide

Two topics the spec scatters across six chapters. Retimers carry a UCIe link off the package and must keep two dies, two UCIe links and one external link in step. Compliance is how a die is tested against a known-good Golden Die, using injection and margining registers. Retimer rules are collected here from §1.3, Chapter 3, Chapter 4 and Chapter 9; compliance from Chapter 11 and §9.5.4.

1 · Why these exist

Retimers

UCIe stops at the package edge

UCIe links are short, on-package channels. A UCIe Retimer sits on the package next to a die and drives an Off Package Interconnect (for example an electrical or optical cable) to a second retimer on another package, so two dies on different packages can talk.

Spec§1.3, p.47 · §1.0, p.39

Retimers

Three links pretending to be one

Die 0 ↔ Retimer 0 is one UCIe link, Retimer 1 ↔ Die 1 another, plus the external link. Each die must see what looks like one consistent link, so retimers resolve parameters, link states and flow control between the ends.

Spec§1.3, p.47–48

Compliance

Test against a known-good die

A DUT is packaged with a Golden Die (a known-good UCIe implementation of every layer) on a known-good bridge, interposer or package. Each layer is checked on its own. Support is optional, but without it a device may not join the compliance program.

Spec§11.0, p.579

Compliance

The spec defines hooks, not tests

Chapter 11 defines the hardware the DUT must have (injection, compliance modes, margining). The test setup, channel model, test details and Golden Die details are left to a separate document.

Spec§11.0, p.579

2 · Retimer topology

What a retimer is responsible for

  • Reliable flit transfer across the external link (one of three options, below).
  • Resolving link and protocol parameters with the remote retimer, so both dies end up with the same width, speed, protocol and flit format.
  • Resolving Adapter LSM and RDI states with the remote retimer.
  • Flow control from die to retimer using credits.

Spec§1.3, p.47–48

What is left to the implementation

How retimers talk to each other over the external link (message transfer, parameter resolution, retimer-to-retimer flow control) is implementation-specific. UCIe only defines what each die sees on its own UCIe link.

Spec§1.3, p.48

4 · Credits: the one flow-control rule a die must follow

Die → retimer is credited, retimer → die is not

  • Every retimer has a Receiver Buffer for flits from its local die.
  • It advertises the buffer size in parameter exchange: "Retimer" = 1 and Retimer_Credits, a 9-bit count.
  • 1 credit = 256 B of data, including any FEC and CRC.
  • The die must not send without a credit. These credits sit on top of protocol credits (for example PCIe PH/PD).
  • Data sent to the retimer must be consumable by the remote die with no other dependency.
  • Retimer → die traffic has no UCIe credit flow control.

Spec§1.3, p.48 · §3.2.1.2, p.63–64

Bit 0 is sent first. The encodings detect up to three bit flips. At ≤ 48 GT/s a receiver may retrain on any error or correct single-bit errors; above 48 GT/s it must correct single-bit errors.

Spec§4.1.2.1, Table 4-1, p.101

Reset on leaving Active

The die resets its credit counter to the advertised value whenever RDI leaves Active. The retimer drains or dumps its buffer before re-entering Active. Because credits are re-advertised, the first transfer after Active entry cannot be a credit-only frame.

Spec§1.3, p.48 · §4.1.2, p.100

Parity bytes are invisible to the retimer

Runtime-link-testing parity bytes do not consume retimer credits, are not written into the buffer and are not forwarded: the feature characterizes only the local UCIe link.

Spec§3.9, p.96

5 · Keeping both dies in step

Link training with a retimer

1

External link and each UCIe link may come up independently.

2

Each UCIe link trains SBINIT → MBINIT (local parameters) → MBTRAIN at its local data rate.

3

The retimer asks for the remote side's rate and width over the external link.

4

If they differ and the retimer needs a match, it retrains from LINKSPEED. This may repeat.

5

When the configuration suits both ends, the link goes through LINKINIT to ACTIVE.

Spec§4.5.2, Figure 4-32, p.130

Parameter exchange: Stall, don't time out

The Adapter's parameter exchange timeout is 8 ms (−0% / +50%), counted only while RDI is Active, and reset by any Stall message. A retimer resolves capabilities with its remote partner and merges its own before answering its die, sending the Stall message once every 4 ms meanwhile.

Spec§3.2.1.2, p.70

Link states: answer only when the far die has

If Die 0 sends Active Request, Retimer 0 must confirm through Retimer 1 that Die 1 received it and replied Active Status, then reply to Die 0. Stall every 4 ms meanwhile. The external link enters low power only when both dies have.

Spec§3.5, p.90

Retimer and DP/UP bits

A retimer's Adapter sets "Retimer" and clears "DP" and "UP". The dies set DP or UP so the retimer knows whether it faces a downstream or upstream port.

Spec§3.2.1.2, p.64

6 · Retimers as software sees them

Registers

Reached only through the mailbox

Retimer registers live in sideband config and sideband MMIO space, not visible to host software directly. The RP/DSP mailbox reaches the retimer nearest the host; the EP/USP mailbox reaches the far retimer. An EP/USP sets "Sideband mailbox Registers Present" only when paired with a retimer.

Spec§9.3, p.457–458 · Table 9-7, p.465

Identity

Link Capability bit 8

A retimer sets the "Retimer" bit in its UCIe Link Capability register so software can tell it apart. Its Link DVSEC Next Capability is 0h and Register Locator offsets are reserved.

SpecTable 9-8, p.466 · Table 9-5, p.464 · Table 9-13, p.476

Errors

Forwarding across the external link is vendor-specific

A retimer next to an RP/DSP reports errors to it with sideband error messages. A retimer next to an EP/USP reports to its partner retimer by a vendor-specific mechanism.

SpecTable 9-12, p.473–475

Management

Optional management transport

Retimers may join the UCIe management network. If they do, they follow all the generic chiplet rules and can forward management packets between their UCIe side and the retimed side.

Spec§8.2.6, p.391

7 · Compliance setup

The test package

  • Golden Die: known-good UCIe across all layers. Its Adapter supports every flit format and can inject consistent and inconsistent sideband messages; it can force timeouts on sideband messages and state residency timers.
  • DUT: one or more dies that have already passed sort/pre-bond testing.
  • Channel: known-good bridge or interposer (Advanced Package) or package (Standard Package).
  • Compliance software: runs on the Golden Die or on an external controller attached via a test/JTAG port.

Spec§11.0, p.579 · §11.2, p.580 · §11.3, p.581

Layers tested separately

Protocol: PCIe/CXL use their own compliance; Streaming is out of scope. Adapter: injection hooks, required in any Adapter that supports a flit format, retimers included. PHY: margining, BER, lane skew, Tx EQ.

Spec§11.1–11.3, p.580–581

Two preconditions

The sideband must come up without firmware, because it carries all compliance register accesses. Software reads the capability registers before testing any optional feature.

Spec§11.0, p.579

Test/Compliance register block

Register Locator block ID 1h. 8 KB: Adapter registers at D2DOFF (offset 10h, normally 0), PHY registers at PHYOFF (offset 14h, normally 4 KB). Software must read both offsets rather than assume them.

Spec§9.5.4–9.5.4.3, p.507–508

Test flits vs NOP flits

Test flits carry 01b in Byte 1 bits [7:6] of the flit header, go through the Tx retry buffer if Retry is enabled, and are CRC-checked at the receiver like any flit, then cancelled (for example with pl_flit_cancel) so the Protocol Layer never sees them. NOP flits bypass the retry buffer.

  • [10:9] Retry Injection: 01b at least one error injected, 10b sequence finished.

9 · PHY compliance: margining and stepping

Getting into @PHY-Compliance

1

Put the Adapter in a compliance mode (01b or 10b) first.

2

Set Compliance Enable (Compliance Control 1 bit 0) in every module.

3

Retrain the link. On the next PHYRETRAIN the PHY enters PHY Compliance. RDI may reach Active but pl_trdy is never asserted.

4

Use the operation trigger and setup registers; TRAINERROR in this mode does not reset them.

Spec§9.5.4.5, p.514 · Table 9-78, p.514

Operations you can trigger

Operation Type: 001b Tx-initiated D2C point test, 010b Tx-initiated eye width sweep, 011b Rx-initiated point training, 100b Rx-initiated width sweep, 101b step from MBTRAIN.RXDESKEW to DATACENTER1 above 32 GT/s (for sweeping Tx EQ). Start with a 0→1 on the trigger bit.

10 · Why each rule exists

Retimer§3.2.1.2 p.70

Stall every 4 ms while resolving

A retimer must resolve capabilities with its remote partner before answering its die, and send the Stall form of the message every 4 ms while it waits. The die's 8 ms timer resets on each Stall.

Why

The external link may take far longer than 8 ms to come up or to fetch the other die's capabilities. Without Stall the local die would time out and take RDI to LinkError. Sending at half the timeout guarantees the timer never expires while the retimer is still working.

Real-time example

An optical link takes 30 ms to lock. Retimer 0 sends a Stall to Die 0 roughly every 4 ms (seven or eight of them) and then the merged capabilities.

If you break it

Die 0 logs Adapter Timeout 0001b (parameter exchange) and the link goes to LinkError. The retimer must also not stall forever: it is responsible for not stalling the link indefinitely.

Check it in the spec
  • SpecTimeout and Stall §3.2.1.2, p.70
  • SpecNot indefinitely §1.3, p.48
Retimer§3.5 p.90

Answer a state request only after the far die has

For Adapter LSM requests, the retimer forwards the request, waits until the far die has responded, and only then responds to its own die.

Why

If Retimer 0 said Active to Die 0 on its own, Die 0 could start sending protocol traffic while Die 1 is still in Reset, and those flits would have nowhere to go. Waiting makes both dies reach each state together.

Real-time example

Die 0 sends Active Request; Retimer 0 relays through Retimer 1; Die 1 replies Active Status; only then does Retimer 0 reply Active Status to Die 0.

If you break it

One die in Active and the other not: traffic stalls or is dropped, and the external link may be put to sleep while one side is still active.

Check it in the spec
  • SpecRetimer state resolution §3.5, p.90
Retimer§1.3 p.48

No credit, no send

The die must not send data to the retimer without a credit. One credit is 256 B including FEC and CRC. Data in the buffer must be consumable by the far die without any other dependency.

Why

The retimer cannot push back on the die any other way: there is no ready signal on the wires. A fixed buffer and credits stop overflow; the no-dependency rule stops a deadlock where buffered data waits on something stuck behind it.

Real-time example

Retimer_Credits = 64 (16 KB). Die 0 bursts 64 flits; with no credits left it idles until Retimer 0 forwards data and returns credits on the Valid wire.

If you break it

Retimer receiver buffer overflow: Uncorrectable Error Status bit 1, Header Log 2 [6:4] = 010b, link down.

Check it in the spec
  • SpecCredit rules §1.3, p.48
  • SpecOverflow encoding Table 9-33, p.486
Retimer§1.3 p.48 · §4.1.2 p.100

Credits reset whenever RDI leaves Active

The die restores its credit counter to the advertised value whenever RDI leaves Active; the retimer drains or dumps its buffer before re-entering Active.

Why

A retrain can drop credit-return frames in flight, leaving the two sides disagreeing about the count. Resetting both to a known value on every exit from Active is simpler and safer than reconciling.

Real-time example

A retrain happens with 10 credits outstanding. On return to Active, Die 0 starts again at 64 and Retimer 0's buffer is empty.

If you break it

A die that keeps its old count slowly loses credits after each retrain; a retimer that keeps old data mixes pre-retrain flits into the new stream.

Check it in the spec
  • SpecReset and drain §1.3, p.48
  • SpecNo credit-only first frame §4.1.2, p.100
Retimer§3.9 p.96

Parity bytes stay on the local link

Runtime-link-testing parity bytes use no retimer credits, are not buffered and are not forwarded to the remote retimer.

Why

Parity measures the health of one UCIe link. Forwarding it would mix two links' results, and charging credits for it would steal buffer space from real traffic.

Real-time example

Software enables parity on Die 0 → Retimer 0 to check UCIe Link 0 alone; Die 1 never sees those bytes.

If you break it

A retimer that counts parity against credits gives the die fewer credits than it advertised.

Check it in the spec
  • SpecParity and retimers §3.9, p.96
Retimer§4.5.2 p.130

Match speed and width by retraining from LINKSPEED

If the retimer needs both UCIe links at the same rate and width, it retrains its local link from LINKSPEED after learning the remote configuration. This may happen several times.

Why

Each UCIe link trains on its own channel and may settle at a different rate or width. A retimer without deep buffering usually cannot bridge a mismatch, so it forces a common configuration before LINKINIT.

Real-time example

UCIe Link 0 trains at 32 GT/s, Link 1 only at 24 GT/s. Retimer 0 retrains Link 0 down to 24 GT/s before letting it go to ACTIVE.

If you break it

The faster side outruns the slower one and fills the retimer's buffer and the external link.

Check it in the spec
  • SpecSpeed/width match §4.5.2, Figure 4-32, p.130
  • Derivedbuffering reason
Compliance§11.0 p.579

The sideband must work without firmware

For compliance, the DUT's sideband is expected to come up without firmware initialization.

Why

Compliance software sets up every test and reads every result through sideband register accesses. If the sideband needed vendor firmware, the Golden Die could not test a DUT on its own.

Real-time example

A bare DUT is powered on; the Golden Die reads its PHY Capability over the sideband before any firmware has run.

If you break it

The DUT cannot be tested in the standard setup.

Check it in the spec
  • SpecSideband role §11.0, p.579
ComplianceTable 9-72 p.509

Compliance mode changes at the next Retrain

Writes to Compliance Mode take effect after the next RDI entry to Retrain. In modes 01b and 10b, a transition to LinkError does not reset any registers.

Why

Switching modes in the middle of Active traffic would leave the Adapter half in one mode and half in another. Retrain is a clean boundary. Keeping registers through LinkError lets a test cause errors on purpose and still read the setup and results.

Real-time example

Software writes 10b, then sets Retrain. After the retrain, the Adapter brings RDI to Active without parameter exchange and waits for injection triggers.

If you break it

Expecting the mode to apply immediately: the next test runs in normal mode.

Check it in the spec
  • SpecCompliance Mode, Force Link Reset Table 9-72, p.509
Compliance§11.2 p.581

Test flits use the retry buffer; NOP flits do not

Test flits (header Byte 1 [7:6] = 01b) pass through the Tx retry buffer when Retry is on, are CRC-checked and trigger Retry on errors, but are never forwarded to the Protocol Layer.

Why

The point is to exercise Retry without a working Protocol Layer. Flits that skip the retry buffer (like NOPs) could not be replayed, so they cannot test it.

Real-time example

With Protocol Layers held in Reset, the DUT injects 1000 Test flits while Retry Injection flips one bit every 50 flits; the Golden Die naks, the DUT replays.

If you break it

A receiver that forwards Test flits hands garbage to the Protocol Layer.

Check it in the spec
  • SpecTest flit rules §11.2, p.581
  • SpecFlit Type field Table 9-73, p.509
Compliance§9.5.4.5 p.514

All modules enter PHY Compliance together

Every module of a link must be in PHY Compliance at the same time; behavior is undefined otherwise. Each module has its own copy of the registers.

Why

Modules of one link share training state and the Adapter. Half the link in compliance and half in mission mode would leave training and data flow inconsistent. Per-module registers let each module be margined separately.

Real-time example

A two-module Standard Package link: software sets Compliance Enable at PHYOFF + 000h and + 400h before retraining.

If you break it

Undefined link behavior and meaningless results.

Check it in the spec
  • SpecModule rules §9.5.4.5, p.514

12 · Test yourself

Interview-style questions.

What does one retimer credit represent? Basic

256 bytes of data in the retimer's receiver buffer, including any FEC and CRC. Retimer_Credits is a 9-bit value in parameter exchange.

Spec§1.3, p.48 · §3.2.1.2, p.64

How does a retimer return credits to its die? Basic

On the Valid wire: 11110000b for no data + 1 credit, 11111111b for data + 1 credit.

SpecTable 4-1, p.101

The external link takes 50 ms to come up. Why doesn't the die's 8 ms parameter exchange timer fire? Intermediate

The retimer sends the Stall form of the capability message every 4 ms while it resolves with its partner, and each Stall resets the die's timer.

Spec§3.2.1.2, p.70

Name the three options for reliability across the off-package link. Intermediate

Tunnel the protocol's own FEC/CRC in Raw Format; the retimer provides its own FEC, CRC and Retry (three independent links); or retimer FEC with the protocol's own CRC and Replay.

Spec§1.3, p.47–48

How do Test flits differ from NOP flits in compliance testing? Intermediate

Test flits use header Byte 1 [7:6] = 01b, go through the retry buffer when Retry is enabled and are CRC-checked, so they can exercise Retry; NOP flits bypass the retry buffer. Neither reaches the Protocol Layer.

Spec§11.2, p.581 · Table 9-73, p.509

How does the PHY enter PHY Compliance, and what stops mission traffic? Advanced

Adapter first in a compliance mode, then set Compliance Enable in every module and retrain; the PHY enters compliance on the next PHYRETRAIN. It never asserts pl_trdy in this mode, even if RDI is Active.

Spec§9.5.4.5, Table 9-78, p.514
