1 · What the Logical PHY does

The spec lists its jobs: link initialization and power states (the LTSM), byte-to-lane mapping, redundancy remapping, sideband messaging, scrambling and patterns, and width degrade. This page covers the data-path ones.

Width

One byte per lane

Every lane carries one whole byte per 8 UI, bit 0 first. Wide RDI beats become parallel lanes, not serial bits on one lane.

Spec§4.1.1, p.98

Framing

Valid marks the bytes

A Valid lane, 4 UI high then 4 UI low per 8-UI block, says which 8 UI carry data. No headers or symbols on the wire.

Spec§4.1.2, p.100

Yield

Route around bad bumps

Advanced Package repairs up to two data lanes per 32 using redundant lanes, plus one clock/track lane and the Valid lane. Standard Package halves width instead.

Spec§4.3, p.107–118

2 · Bytes to lanes

Byte 0 goes on lane 0, byte 1 on lane 1, and so on; within a byte, bit 0 is sent first. When the width changes, the rule is the same: one byte per lane per 8 UI. Pick a width to see where a 256B flit's bytes go.

RDI byte k = lane k. RDI byte order (flit byte 0 on RDI byte 0) and lane order line up, so the PHY needs no knowledge of flit formats: a 64B RDI beat on a x64 module is exactly one 8-UI Valid frame. Multi-module and degraded links keep "ascending bytes on ascending active lanes and module IDs".

Spec§4.1.1, p.98 · §10.3.1, p.559–561 · §4.7.1, p.175

3 · Valid framing and clock gating

8-UI blocks, aligned forever

  • For each 8-bit transfer, Valid is high for the first 4 UI and low for 4 UI.
  • In Active, every transfer starts an integer multiple of 8 UI after the rising edge of the first transfer's Valid. The receiver tracks this alignment.
  • An invalid Valid encoding is a framing error: the PHY raises pl_error and retrains.

Spec§4.1.2, p.100 · Table 10-1 (pl_error), p.524

Retimers return credits on Valid

Valid bits (bit 0 first, right to left)Meaning
0000 0000no data, no credit
0000 1111data, no credit
1111 0000no data, 1 credit
1111 1111data, 1 credit

Each credit = 256B. The encodings guarantee detection of 3 bit flips. At ≤ 48 GT/s a receiver may retrain on any bit error or correct single-bit errors; above 48 GT/s it must correct single-bit errors.

Spec§4.1.2.1 and Table 4-1, p.101

Clock gating with a postamble

When Valid goes low, the forwarded clock keeps toggling for a fixed postamble, then stops: 16 UI (8 cycles) at half-rate clocking, 32 UI (8 cycles) at quarter-rate. Not gated if free-running clock was negotiated or the partner requested Runtime Recalibration.

Spec§4.1.3, p.101 · §5.11

Free-running clock mode

The forwarded clock keeps toggling even with Valid low. Must be supported (to turn off dynamic clock gating for normal operation or debug) and negotiated before mainband training. Always used above 32 GT/s.

Spec§4.1.4, p.101 · §4.5.3.3.1, p.137

4 · Sideband serial format

  • One serial data + clock pair per direction per module, 800 MT/s single data rate.
  • Messages are a 64-bit header, optionally with 32 or 64 bits of data. Every serial packet is 64 UI; 32-bit data is padded with zeros in the MSBs.
  • Packets are separated by at least 32 UI of low. A message with data = header, 32 UI low, data, 32 UI low.
  • PMO (Performant Mode, negotiated in MBINIT.PARAM SBFE): no 32-UI gap; packets back to back. Receivers must still accept gaps.
  • PSPT (Priority Sideband Packet Transfer, needs PMO): a pending priority packet may interrupt a normal packet at an 8-UI boundary after 8 UI of idle. Opcode 11111b ends a priority chain and resumes the normal packet; 11110b says another priority packet follows.

Spec§4.1.5–4.1.5.2.1, p.102–104 · §5.13, p.254

Who shares the sideband

Link management packets (training, RDI and Adapter state messages) and Management Port Messages (MPMs) share each sideband. Arbitration is implementation-specific but must not delay link management packets into timeouts; an MPM with data must finish within 512 UI (with PMO) or 768 UI (without).

Spec§4.8, p.182 · §8.2.5.1.2

5 · Lane reversal and Lane ID

Every device must support data lane reversal within a module: local physical data lane 0 connects to remote lane N−1, lane 1 to N−2, and so on (N = 8, 16, 32 or 64). On Advanced Package the redundant lanes reverse too. Track, Valid, Clock and sideband are never reversed.

Every logical data and redundant lane has a unique Lane ID (x64 Advanced: 0–63 data, 64–67 redundant; x32: 0–31 and 64–65). MBINIT.REVERSALMB sends each lane's ID in an unscrambled 16-bit pattern so the receiver can see which transmitter lane it is connected to.

Spec§4.2–4.2.1, p.104–107 · Table 4-7, p.151

Why reversal exists

Two identical dies placed face to face on a package, or one die rotated 180°, see each other's lanes in mirror order. Supporting reversal in silicon means the package designer does not need crossing routes, which on Advanced Package interposers with 25–55 µm bump pitch would cost routing layers.

Backgroundrouting reasoning · Specbump pitch, Table 1-2, p.40

6 · Lane repair (Advanced) and width degrade (Standard)

Advanced Package: each group of 32 data lanes has two redundant lanes (TRD0/TRD1 for lanes 0–31, TRD2/TRD3 for 32–63). One failure shifts toward TRD0; two failures shift the lower one toward TRD0 and the upper one toward TRD1. Click up to two lanes below to see the mapping for lanes 0–31.

Limits

Up to two data lanes per group of 32 (four per x64 module). If TRD0 (or TRD2) is itself faulty, no lane in that group can be repaired; if TRD1 (or TRD3) is faulty, one can. Unused redundant lanes are tri-stated and their receivers disabled.

Spec§4.3, p.107–108

Clock, Track, Valid

One broken lane among clock (P/N) and track can be remapped onto the redundant clock/track lane (RDCK). Valid has its own redundant lane (RDVLD). Both are detected and repaired in MBINIT.

Spec§4.3.4–4.3.6, p.115–118

Standard: halve the width

x16 → x8 using logical lanes 0–7 or 8–15, whichever half has no faults; x8 → x4 using 0–3 or 4–7. If faults are in both halves, width degrade cannot help. Disabled lanes are tri-stated.

Spec§4.3.7, p.118 · Table 4-9, p.155

7 · Multi-module links

  • Permitted configurations: one, two or four modules. Each has a Module ID, advertised in MBINIT.PARAM.
  • Each module trains on its own sideband through LINKSPEED step 2; the Multi-module PHY Logic (MMPL) then resolves one outcome for all.
  • All modules run at the same speed and width. If a module fails, MMPL degrades to the next permitted configuration (fewer modules, or lower speed), using the flowcharts in Figures 4-47 and 4-48.
  • The MMPL swizzles bytes so the remote receivers see bytes laid out from LSB to MSB in ascending Module ID and Lane ID across all active lanes, even if the partner's Module IDs differ.

Spec§4.7–4.7.1, p.175–178

Which sideband carries what

Training messages (Tables 7-9 and 7-11) go on each module's own sideband. Register accesses, RDI/Adapter link management and other non-vendor messages (Tables 7-8, 7-10) use one sideband: the lowest Module ID whose LTSM is past SBINIT. Retimer credits ride on the Valid of the lowest Module ID in Active. In both cases the receiver may see them arrive on a different module ID.

Spec§4.7.1.1, p.178

Choosing between fewer modules and lower speed. For a speed difference, MMPL compares bandwidth: with CMLS = common maximum speed and HMLS = highest maximum speed of the next lower module count, if HMLS/2 > CMLS it drops modules; otherwise all modules slow to CMLS. The "HMLS/2 > CMLS" case also rescues a link where some modules fail even 4 GT/s (CMLS = 0): those are disabled instead of the whole link going to TRAINERROR.

Spec§4.7.1, p.177 · Figures 4-47 and 4-48

8 · Why each rule exists, with real-time examples

Each card gives a data-path rule, the reason, an example, and what breaks without it.

Mapping§4.1.1 p.98

Whole bytes per lane, not bits striped across lanes

Each byte travels on one lane over 8 UI, bit 0 first; byte k on lane k.

Why

A whole byte per lane means the receiver deserializes each lane independently with a simple 1:8 shift register and no cross-lane bit reassembly. It also makes lane skew affect only byte position, which deskew handles per lane. And it lines up with the 8-UI Valid block exactly.

Real-time example

x64 at 16 GT/s: in each 8-UI block (0.5 ns) all 64 lanes deliver one byte: 64 bytes, one RDI beat at 2 GHz. A 256B flit takes four blocks, 2 ns.

If you break it

A PHY that sends MSB first reverses every byte at the far end; the CRC fails on every flit.

Check it in the spec
  • SpecBit and byte order §4.1.1, Figures 4-1, 4-2, p.98–99
  • BackgroundDeserializer reasoning
Mapping§4.1.1 p.98 · §4.3.7 p.118

Narrower links keep one byte per lane

On x32, x16 or a degraded x8, bytes still go one per lane in ascending order; the flit just takes more 8-UI blocks.

Why

The same serializer and deserializer work at every width. Width becomes a parameter of how many blocks a flit takes, not a different bit layout, which keeps width degrade a configuration change rather than new logic.

Real-time example

x16 Standard: a 256B flit takes 16 blocks. After degrade to x8 it takes 32 blocks, twice the time.

If you break it

Leaving a disabled lane's slot in the byte order (skipping a byte) shifts every following byte after degrade.

Check it in the spec
  • SpecFigures 4-3 to 4-5 p.99–100
  • DerivedBlock counts
Framing§4.1.2 p.100

Valid is 1111 0000, every 8 UI, on a fixed grid

Valid is high for the first 4 UI and low for the next 4 of each data block, and in Active every transfer starts a multiple of 8 UI after the first one.

Why

A fixed grid lets the receiver know where a byte boundary is without any symbol alignment. The half-high, half-low shape gives an edge in every block, and its fixed pattern makes corruption easy to detect: anything other than the allowed patterns is a framing error.

Real-time example

Valid for three back-to-back blocks reads 11110000 11110000 11110000. A noise hit that turns one block into 11010000 is caught as a framing error; the PHY raises pl_error and retrains.

If you break it

A transmitter that starts a burst 4 UI off the grid after an idle gap: the receiver mis-frames every byte.

Check it in the spec
  • SpecValid shape and 8-UI grid §4.1.2, p.100
  • SpecFraming errors trigger retrain §4.5.3.7.2, p.170
Framing§4.1.2.1 p.101

Retimer credits ride on Valid's spare half

Toward its local die, a Retimer uses the upper 4 UI of Valid to return a 256B credit: 0000 1111 data only, 1111 0000 credit only, 1111 1111 both.

Why

A Retimer must tell the die how much buffer space it has without stealing data bandwidth or sideband latency. Valid's low half is otherwise always 0, so it can carry one bit per block for free. The four codes are far enough apart to detect three bit flips.

Real-time example

x64 at 16 GT/s: one credit can return every 0.5 ns block, far faster than flits (one per 2 ns) consume them, so credits never become the bottleneck.

If you break it

The first transfer after entering Active must not be "credit only" (1111 0000); it would break the receiver's 8-UI alignment start. The spec notes this is fine because credits are re-advertised on every Active entry.

Check it in the spec
  • SpecTable 4-1 and error handling rules p.101
  • SpecFirst-transfer note §4.1.2, p.100
  • DerivedCredit and flit rates
Framing§4.1.2.1 p.101

Above 48 GT/s, correct; at or below, you may just detect

At ≤ 48 GT/s a Retimer-encoding receiver may retrain on any bit error or correct single-bit errors. Above 48 GT/s it must correct single-bit errors.

Why

Above 48 GT/s the raw BER is 1e-12, a million times worse than 1e-15 below. Single-bit errors on Valid would become frequent, and retraining on each one would cost far more than correcting it.

Real-time example

At 64 GT/s the Valid lane carries 6.4e10 bits per second; at BER 1e-12 that is one Valid bit error roughly every 16 seconds per direction, too often to retrain each time.

If you break it

A detect-only receiver at 64 GT/s retrains several times a minute.

Check it in the spec
  • SpecThe rule §4.1.2.1, p.101
  • SpecBER by speed Tables 1-1, 1-2, p.40
  • DerivedError interval
Framing§4.1.3 p.101

Gate the clock, but only after a postamble

After Valid falls, the forwarded clock keeps running for 16 UI (half-rate) or 32 UI (quarter-rate), 8 clock cycles either way, then stops. Required whenever the clock must stop after toggling with Valid, in any LTSM state.

Why

The receiver's deserializer and FIFOs are clocked by the forwarded clock. Stopping it the moment Valid drops would strand the last bytes inside the receive pipeline. Eight extra cycles flush them.

Real-time example

16 GT/s with an 8 GHz half-rate clock: the postamble costs 1 ns of clock activity after each burst, which is cheap compared with the power saved during idle.

If you break it

Gating the clock on Valid's falling edge: the last byte of every burst never leaves the receiver's deserializer; the next burst pushes it out late, misaligned.

Check it in the spec
  • SpecPostamble lengths and exceptions §4.1.3, p.101
  • BackgroundPipeline-flush reason
  • Derived8 cycles at 8 GHz = 1 ns
Sideband§4.1.5 p.102

Every sideband packet is 64 UI, plus a 32 UI gap

Header and data each go as 64-UI serial packets, with at least 32 UI low between packets (unless PMO is negotiated).

Why

A fixed packet size makes the serial receiver trivial: count 64 UI. The low gap gives an unambiguous start-of-packet edge without a preamble, which matters on a link that is also used during training before anything is calibrated.

Real-time example

A register write with 64-bit data: 64 UI header + 32 UI + 64 UI data + 32 UI = 192 UI = 240 ns at 800 MT/s. With PMO: 128 UI = 160 ns.

If you break it

A PMO transmitter that starts back-to-back sends before it has sent and received the SBFE response with PMO = 1: the partner's receiver may not yet be in PMO mode.

Check it in the spec
  • SpecPacket format and gaps; PMO entry rule §4.1.5–4.1.5.1, p.102
  • DerivedTimes
Sideband§4.1.5.2.1 p.103–104

Priority packets can cut in, at 8-UI boundaries

With PSPT, a transmitter may interrupt a normal packet at an 8-UI multiple, insert 8 UI of idle, then a priority packet. Opcode 11111b resumes the normal packet next; 11110b chains another priority packet.

Why

A long management message can occupy the sideband for hundreds of nanoseconds. Some packets must not wait behind it. The 8-UI idle marks the interruption so the receiver knows the next 64 UI are a priority packet, not the rest of the normal one.

Real-time example

A 64-UI normal packet is 32 UI in when a priority packet arrives. Sideband: 32 UI normal, 8 UI idle, 64 UI priority (opcode 11111b), then the remaining 32 UI of the normal packet.

If you break it

A receiver that does not track "interrupted" state treats the resumed tail as a new packet header.

Check it in the spec
  • SpecPSPT rules; needs PMO; receiver tracking §4.1.5.2–4.1.5.2.1, p.103–104
  • SpecPriority packet format §7.1.2.6
Repair§4.3.3 p.109–113

Shift toward the spare, don't swap in the spare

Repair shifts every logical lane between the fault and the redundant lane by one physical position (left toward TRD0 or right toward TRD1). Only the faulty physical lane is dropped.

Why

A swap would need a long wire from any lane to the spare and a 32:1 mux. Shifting needs only a 2:1 or 3:1 mux per lane to its neighbours, and keeps each logical lane physically close to its normal bump: short routes, low skew.

Real-time example

Lane 29 fails: logical lanes 0–29 move one bump left (lane 0 onto TRD0), lanes 30 and 31 stay. Physical lane 29 is tri-stated.

If you break it

Applying the shift on the transmitter but not the matching inverse on the receiver: logical lanes 0–29 arrive one lane off.

Check it in the spec
  • SpecPseudocode and Figures 4-12 to 4-15 §4.3.1, §4.3.3.1, p.107–110
  • BackgroundMux and routing reasoning
Repair§4.3 p.107–108

Two spares per 32 lanes, and TRD0 matters most

Each group of 32 data lanes can repair at most two lanes. One failure always uses TRD0; with two, the lower uses TRD0 and the upper TRD1. If TRD0 is bad, nothing in that group can be repaired.

Why

Shift-left is the single-failure path, so TRD0 is the first spare used. Splitting a x64 module into two independent groups lets it survive two failures in each half, not just two in total.

Real-time example

Failures on lanes 5, 20 and 40: lanes 5 and 20 use group 0's two spares, lane 40 uses TRD2. A fourth failure on lane 10 would exceed group 0's two and send REPAIRMB to TRAINERROR.

If you break it

Counting repair capacity per module (4) instead of per group (2 + 2) accepts three failures in lanes 0–31 that cannot be repaired.

Check it in the spec
  • SpecGroup limits and spare-failure note §4.3, p.107–108
  • SpecUnrepairable → TRAINERROR §4.5.3.3.6, p.154
Repair§4.2 p.104

Reverse data lanes only

Data lanes (and redundant data lanes on Advanced) may be reversed. Clock, Track, Valid and sideband must never be reversed.

Why

Reversal is detected by sending lane IDs over data lanes, which needs a working clock, valid and sideband first. If those could also be reversed, there would be nothing trustworthy to detect the reversal with.

Real-time example

A rotated die on a x32 Advanced link: data lanes 0–31 and redundant lanes reverse; the clock, Valid and sideband bumps sit in mirror-symmetric positions so they connect straight.

If you break it

A package that swaps clock P and N as part of a reversal: REPAIRCLK sees a broken clock on a perfectly good link.

Check it in the spec
  • SpecReversal rule §4.2, p.104
  • DerivedDependency reasoning (from training order in §4.5.3.3)
Multi-module§4.7.1 p.175–177

Bytes ascend by Module ID, whatever the partner's IDs are

The transmitting MMPL arranges bytes so that the remote receivers see them from LSB to MSB in ascending Module ID and Lane ID across all active lanes.

Why

Dies may be placed so that local module 0 faces remote module 1. If each side just used its own numbering, RDI bytes would arrive scrambled. Making the transmitter responsible (it knows the partner's IDs from MBINIT.PARAM) keeps RDI byte order identical on both dies.

Real-time example

Die A's M0 connects to Die B's M1 and vice versa. Die A's MMPL puts RDI bytes 0–15 on the module connected to Die B's M0, so Die B receives them on its M0 in the right order.

If you break it

Swizzling at the receiver instead: both sides swizzle (or neither does), and bytes 0–15 swap with 16–31.

Check it in the spec
  • SpecMMPL swizzle rule, Figures 4-43 to 4-46 §4.7.1, p.175–176
  • SpecByte mapping at RDI unchanged §10.3.1, p.561
Multi-module§4.7.1 p.177

Fewer modules or lower speed: pick more bandwidth

If modules differ in achievable speed, compare HMLS/2 (the next lower module count at its best speed) with CMLS (all modules at the common speed). Drop modules if HMLS/2 > CMLS, else slow all modules to CMLS.

Why

Both choices lose bandwidth; the rule keeps whichever loses less. It also handles modules that fail even at 4 GT/s: CMLS = 0, so they are disabled instead of the whole link failing.

Real-time example

Four modules: three pass 32 GT/s, one only 8 GT/s. CMLS = 8. Two modules at 32 GT/s give HMLS/2 = 16 > 8, so drop to two modules at 32 GT/s: 2 × 32 = 64 units of bandwidth instead of 4 × 8 = 32.

If you break it

Always slowing all modules to the weakest one leaves a four-module link at 8 GT/s, half the bandwidth it could have.

Check it in the spec
  • SpecPseudocode and flowcharts §4.7.1, p.177 · Figures 4-47, 4-48
  • DerivedBandwidth comparison
Multi-module§4.7.1.1 p.178

Shared traffic uses the lowest live module

Register accesses and link-level messages use the sideband of the lowest Module ID whose LTSM is past SBINIT; Retimer credits use the Valid of the lowest Module ID in Active. Receivers must accept them on any module.

Why

One RDI and one Adapter sit above all modules, so a single message stream is needed for link-level traffic. "Lowest live" is a deterministic choice that survives a module being disabled. Because the two dies may number modules differently, the receiver cannot insist on a particular module.

Real-time example

Module 0 is disabled after training. Register traffic automatically moves to module 1's sideband; nothing in the Adapter changes.

If you break it

Hard-wiring register traffic to module 0's sideband makes the link unmanageable after module 0 is disabled.

Check it in the spec
  • SpecAssignment rules §4.7.1.1, p.178

11 · Verification

Checkers

  • Lane k carries RDI byte k (per active-lane order), bit 0 first. §4.1.1
  • Valid: 1111 0000 per data block; all transfers on the 8-UI grid. §4.1.2
  • Retimer Valid codes only from Table 4-1; first Active transfer not "credit only". §4.1.2–4.1.2.1
  • Clock stops exactly 8 cycles after Valid falls (unless free-running or recal). §4.1.3
  • Sideband: 64-UI packets, ≥ 32 UI gaps unless PMO; PSPT interrupts on 8-UI boundary after 8 UI idle. §4.1.5
  • Repair mapping matches pseudocode for 0, 1, 2 failures per group, with and without reversal. §4.3.3
  • Unused redundant and failed lanes tri-stated / disabled. §4.3
  • Multi-module: same speed and width on all modules; received byte order ascending. §4.7.1

Scenarios

  • Exhaustive single-lane repair over 0–63; all pairs within each group; TRD0 / TRD1 faulty. §4.3
  • Reversal × repair combinations for x64 and x32. §4.3.3.3–4
  • x16 Standard faults in lower half, upper half, both halves. §4.3.7
  • Two- and four-module links with mismatched Module IDs; module disable mid-life. §4.7.1
  • Speed mismatch across modules hitting both branches of HMLS/2 > CMLS. §4.7.1
  • Single-bit Valid errors at 32 and 64 GT/s with a Retimer. §4.1.2.1
  • PSPT chains (11110b … 11111b) interrupting a long MPM. §4.1.5.2.1

12 · Test yourself

Interview-style questions.

Which bit of a byte goes on the wire first, and which lane carries byte 5? Basic

Bit 0 first. Byte 5 goes on lane 5 (of the active lanes, in ascending order).

Spec§4.1.1, p.98

What does the Valid lane look like for one 8-UI data block? Basic

High for 4 UI, low for 4 UI. Transfers stay on an 8-UI grid from the first transfer in Active.

Spec§4.1.2, p.100

Which signals may be lane-reversed? Basic

Data lanes, and on Advanced the redundant data lanes. Never clock, track, valid or sideband.

Spec§4.2, p.104

Lanes 3 and 27 fail in a x64 Advanced module. Show the repair. Intermediate

Both in group 0. Lower (3): logical lanes 0–3 shift left, lane 0 onto TRD0. Upper (27): logical lanes 27–31 shift right, lane 31 onto TRD1. Logical lanes 4–26 stay. Physical lanes 3 and 27 are tri-stated.

Spec§4.3.3.2, p.111

Why does the clock run for 8 more cycles after Valid falls? Intermediate

To flush the receiver's deserializer pipeline, which runs on the forwarded clock. 16 UI at half-rate clocking, 32 UI at quarter-rate.

Spec§4.1.3, p.101

How does a Retimer return credits without using the sideband? Intermediate

On the Valid lane's otherwise-unused second 4 UI: 1111 0000 = credit only, 1111 1111 = data plus credit, 0000 1111 = data only. Each credit is 256B.

SpecTable 4-1, p.101

Four modules: three reach 32 GT/s, one only 8 GT/s. What does the MMPL do? Advanced

CMLS = 8, HMLS of the two-module configuration = 32, HMLS/2 = 16 > 8, so it drops to two modules at 32 GT/s rather than running all four at 8 GT/s.

Spec§4.7.1, p.177

Why must the transmitter, not the receiver, swizzle bytes across modules? Advanced

So that both RDIs see the same byte order with exactly one side doing the work. The transmitter knows the partner's Module IDs from MBINIT.PARAM and lays bytes out so the receiver sees ascending Module ID and Lane ID.

Spec§4.7.1, p.175

When can a priority sideband packet interrupt a normal one, and how does the receiver know? Advanced

With PSPT (which requires PMO): at an 8-UI multiple of the normal packet, after inserting 8 UI of idle. The receiver tracks that the normal packet was interrupted; opcode 11111b means the normal packet resumes next, 11110b means another priority packet follows.

Spec§4.1.5.2.1, p.103–104
