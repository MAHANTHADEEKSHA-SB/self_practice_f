UCIe Link Training (LTSM) Field Guide

The Link Training State Machine takes a UCIe link from power-on to ACTIVE: bring up the sideband, check and repair clock, valid and data lanes at 4 GT/s, switch to the target speed, calibrate and center, verify, and hand over to the Adapter. It also runs retrains, power states and error recovery. This guide walks every state in order, explains why each step exists, and shows the sideband handshakes that drive it.

Die 0 / UCIe Module Die 1 / Module Partner, RDI status sideband messages

1 · Why link training exists

Four problems the LTSM solves. Every state maps to at least one of them.

Two independent dies

Agree on everything, step by step

The dies come out of reset at different times, from different vendors, maybe at different maximum speeds. Every sub-state ends with a request/response pair on sideband, so neither die moves on until the other is ready.

Spec§4.5.3.4 intro, p.155 · §4.5.3, p.131

Manufacturing defects

Find and route around bad bumps

Micro-bumps open or short. Training checks clock, track, valid and every data lane with known patterns, then repairs (Advanced Package, using redundant lanes) or narrows the link (Standard Package).

Spec§4.5.3.3.3–4.5.3.3.6, p.146–155 · §4.5.3.4.13, p.167

Signal integrity at speed

Set Vref, center the clock, deskew

Margins shrink as speed rises. The LTSM first gets a working link at 4 GT/s, then moves to the target speed and calibrates: Tx self-cal, Rx clock cal, valid and data centering, Vref, per-lane deskew, then a final link check.

Spec§4.5.3.4, p.155–167

Change over time

Retrain, recalibrate, degrade

Temperature and voltage drift. PHYRETRAIN re-runs training on errors or request, LINKSPEED can degrade speed or width, and Runtime Recalibration uses the Track lane to adjust while data keeps flowing.

Spec§4.5.3.7, p.168 · §4.6, p.173

3 · Training triggers and RESET

What starts mainband training

  • Software writes 1 to Start UCIe Link Training in the UCIe Link Control register.
  • The Adapter makes a NOP → Active transition on RDI while status is Reset.
  • The SBINIT pattern (two iterations of 64-UI clock pattern + 32-UI low) is seen on any sideband receiver pair (when management transport is not up).
  • With management transport up: {SBINIT done req} from the partner, or software Retrain Link in a Management Port structure.

Hardware may retry training an implementation-specific number of times, then waits in RESET for a new trigger. If software- or RDI-triggered training fails, or the link drops from up to down on a PHY timeout, the PHY must raise a fatal error to the Adapter on RDI.

Spec§4.5, p.124–125

RESET: at least 4 ms, every time

  • Minimum 4 ms on every entry, for PLLs and other initialization.
  • Exit needs stable supplies, an 800 MHz sideband clock, stable PHY and Adapter clocks, mainband clock at the slowest rate (2 GHz for 4 GT/s), SoC not holding reset, and a training trigger.
  • All mainband transmitters tri-stated; receivers may be off; sideband receivers enabled.
  • Without management transport up, sideband register accesses arriving in RESET may be completed as Unsupported Requests, with credits returned.

Spec§4.5.3.1, p.132–133

4 · SBINIT: bring up the control channel

Everything after this point is coordinated over the sideband, so it comes first. It runs at 800 MT/s with the 800 MHz sideband clock.

1

Send repeating 64-UI clock pattern (1010…) + 32-UI low on sideband data, with the sideband clock strobing during the 64 UI. Advanced Package drives both TXDATASB and TXDATASBRD, and both clocks.

2

The partner samples every data/clock combination (4 on Advanced). Detection = 128 UI of clock pattern seen.

3

On detection, send four more iterations, then stop and enable the sideband for messages. If nothing is detected, alternate 1 ms sending / 1 ms quiet; at 8 ms, TRAINERROR.

4

Send {SBINIT Out of Reset} until the same message is received (8 ms timeout). On Advanced it carries the chosen data/clock assignment; both sides then use that "functional sideband".

5

{SBINIT done req} / resp. When sent and received, go to MBINIT.

7 · The test primitives everything is built from

MBINIT and MBTRAIN reuse four operations. They differ in who drives the sweep and who logs results.

Tx-initiated point test (§4.5.1.1)
  1. {Start Tx Init D to C point test req} with pattern, mode and compare setup; partner arms comparators, responds.
  2. {LFSR clear error req/resp}: both reset LFSRs and results.
  3. Tx sends the pattern for the set number of cycles; Rx compares every UI.
  4. {Tx Init D to C results req/resp}: Tx reads the partner's log.
  5. {End Tx Init D to C point test req/resp}.

Spec§4.5.1.1, p.125–126

Eye width sweep and Rx-initiated variants

An eye width sweep repeats the point test across PI (clock phase) settings to find the passing range. Rx-initiated versions let the receiver drive the test and keep its own results, then share them, used where the receiver is optimizing (Vref, deskew).

Spec§4.5.1.2–4.5.1.4, p.127–130

Patterns
  • LFSR: G(X) = X23+X21+X16+X8+X5+X2+1 (same as PCIe), lane-dependent seed (lane mod 8).
  • VALTRAIN: four 1s, four 0s.
  • Per Lane ID: 16-bit pattern carrying the lane number; never scrambled.
  • Burst mode (burst/idle/iteration counts) or continuous mode.

Spec§4.4.1, p.120 · Table 4-5, p.126 · Table 4-7, p.151

Two comparison modes

Per-lane: a sticky error bit per lane once errors exceed the threshold; used to find which lanes to repair (N = 68 for x64 Advanced, 34 for x32, 16 or 8 for Standard). Aggregate: any-lane errors per UI counted in a 16-bit counter; used for module-level margining.

Spec§4.4, p.119–120

8 · PHYRETRAIN, TRAINERROR and PM

Retrain: four ways in, one negotiation

  • Adapter-directed: RDI request Retrain → stall handshake → {LinkMgmt.RDI.Req.Retrain}.
  • PHY-initiated: Valid framing error → pl_error with the bad data → stall → Req.Retrain.
  • Remote request: partner's Req.Retrain → stall → Rsp.Retrain.
  • From LINKSPEED: Runtime Link Test Control changed.

Then both send {PHYRETRAIN.retrain start req} with a retrain encoding; mismatches resolve to the more severe one (try it on the right). All modules of a link must resolve the same way.

9 · Runtime Recalibration

1

Receiver enables its Track buffers and sends {RECAL.track pattern init req}.

2

Partner responds and starts the Track pattern with the forwarded clock (re-enabling a gated clock if needed).

3

Receiver recalibrates and sends {RECAL.track pattern done req}, or, if TARR was negotiated and it wants help, sends {RECAL.track tx adjust req} with a delay correction in 1/64 UI steps.

4

Partner may adjust its Tx and answers; it must avoid the 8 ms timeout (Stall every 4 ms recommended).

Data keeps flowing: mainband data with correct valid framing must still be sampled and processed during recalibration. TARR (Tx Adjustment during Runtime Recalibration) lets the transmitter absorb drift, so receivers need less margin and less power. On unterminated links the idle Track alternates low and high across iterations to limit aging.

Spec§4.6, p.173–175 · §4.5.3.3.1 (TARR), p.138

10 · Why each rule exists, with real-time examples

Each card gives a training rule, the reason behind it, a worked example, and what breaks without it.

Flow control§4.5 p.124

8 ms per state, reset by Stall

Every state except RESET, ACTIVE, L1/L2 and TRAINERROR times out after 8 ms (per sub-state), going to TRAINERROR and then RESET. RDI sideband handshakes also time out at 8 ms. A Stall-encoded message resets the timer. Tolerance is −0%/+50%.

Why

A die that died or hung must not leave its partner waiting forever. Per sub-state keeps the bound tight even though MBTRAIN has 13 sub-states. Stall lets a slow but healthy partner (typically a Retimer waiting on its far link) keep the link alive.

Real-time example

Die 1 stops answering in MBTRAIN.RXDESKEW because its firmware crashed. Die 0 times out between 8 and 12 ms later, enters TRAINERROR, then RESET, and waits for a new trigger.

If you break it

A timer that spans all of MBTRAIN allows 13 × 8 ms ≈ 100 ms of hang before recovery; a timer that ignores Stall kills every Retimer link.

Check it in the spec
  • SpecTimeout rule, Stall reset, tolerance §4.5, p.124
  • Derived8 ms × 1.5 = 12 ms maximum
Flow control§4.5.3.4 p.155

Every sub-state ends with "sent and received"

A module leaves a sub-state only after it has sent its done/end request and received the partner's response. Modules enter every MBTRAIN sub-state, even ones with nothing to do.

Why

This keeps both dies in lock-step through 20-plus sub-states without any shared timing. Visiting every sub-state means the two state machines can never skip to different places.

Real-time example

Die 0 needs no deskew; Die 1 does. Die 0 enters RXDESKEW, sends its end request at once, and waits there until Die 1 has finished and responded. Both exit to DATATRAINCENTER2 together.

If you break it

A PHY that skips RXDESKEW when it has nothing to do sends a DATATRAINCENTER2 message that the partner, still in RXDESKEW, does not expect; one side times out.

Check it in the spec
  • SpecEnter each sub-state; exit through the handshake §4.5.3.4, p.155
Flow control§4.5.3.1 p.132

RESET lasts at least 4 ms

On every entry to RESET the PHY stays at least 4 ms, so PLLs stabilize and initialization completes, before any exit conditions are considered.

Why

Mainband and sideband clocks must be stable before training patterns mean anything. A fixed floor also makes the two dies' timing predictable after a TRAINERROR, so retries do not race.

Real-time example

An L2 exit or a TRAINERROR recovery always costs at least 4 ms before SBINIT. This is why L2 exit is far slower than L1 exit, which never visits RESET.

If you break it

Leaving RESET at 1 ms: SBINIT patterns are sent from an unlocked PLL and the partner fails detection.

Check it in the spec
  • Spec4 ms minimum; exit conditions §4.5.3.1, p.132
Sideband§4.5.3.2 p.133–134

Keep sending after detection

After a module detects the partner's SBINIT pattern, it sends four more iterations before stopping. If it sees nothing, it alternates 1 ms sending and 1 ms quiet, for up to 8 ms.

Why

The two dies leave RESET at different times. If one stopped as soon as it detected the other, the late die might never see a pattern. The extra iterations cover that. The 1 ms on/off cycle is so a die that started early keeps re-offering the pattern while the other wakes up.

Real-time example

Die 0 leaves RESET 2.5 ms before Die 1. Its patterns in the first two windows go unheard; in its third sending window Die 1 is listening and detects it. Die 1 sends four more iterations; Die 0 detects those, and both stop.

If you break it

Stopping immediately after detection leaves the late die sending into silence until its 8 ms timeout.

Check it in the spec
  • SpecSteps 3–5 §4.5.3.2, p.134
  • Illustrative2.5 ms skew
Sideband§4.5.3.2 p.134–135

Advanced: four ways to make the sideband work

Advanced Package has redundant sideband data and clock. The receiver tries all four data × clock combinations and picks by fixed priority: DATASB/CKSB, then DATASB/CKSBRD, then DATASBRD/CKSB, then DATASBRD/CKSBRD. The choice travels in {SBINIT Out of Reset} and both sides use it.

Why

Without a sideband nothing else can be trained or repaired, so it needs its own redundancy. Any one good data lane plus any one good clock lane is enough. A fixed priority makes both sides' choices predictable.

Real-time example

CKSB has an open bump. Results: [0]=0, [1]=1, [2]=0, [3]=1 → pattern xx10 → use DATASB with CKSBRD.

If you break it

A receiver that picks the first combination it happened to detect, instead of the priority order, can disagree with what its own Out of Reset message advertised.

Check it in the spec
  • SpecPseudocode and assignment §4.5.3.2, p.134–135
Mainband init§4.5.3.3 p.136–155

Prove it at 4 GT/s first

All of MBINIT, plus VALVREF and DATAVREF in MBTRAIN, run at the lowest rate, 4 GT/s. Only then does SPEEDIDLE switch to the negotiated speed.

Why

At 4 GT/s the eye is wide enough that an untrained link works. That makes it the right place to find opens, shorts and reversed wiring, and to get Vref close, before tighter calibration at speed. A failure at 4 GT/s is a real defect, not a tuning problem.

Real-time example

At 4 GT/s a UI is 250 ps; at 32 GT/s it is 31 ps. A lane with a marginal bump can pass at 4 GT/s and still fail LINKSPEED at 32 GT/s; that is what REPAIR and speed degrade are for.

If you break it

Training repair at full speed: a marginal but intact lane and an open lane look the same, so the PHY wastes redundant lanes on lanes that just needed centering.

Check it in the spec

  • DerivedUI times
Mainband init§4.5.3.3.1 p.137–139

Partner picks the common maximum rate

Each module sends its maximum supported data rate in {MBINIT.PARAM configuration req}; the partner answers with the highest rate both support. The value must account for everything needed at that rate (BER, CRC/Retry, clock phase support). All parameters except Module ID must match across modules.

Why

A die must not advertise a rate it can only reach electrically but not reliably, for example a rate whose BER needs Retry when its Adapter has none. Matching parameters across modules is required because one RDI cannot run modules at different speeds.

Real-time example

Die 0 supports 32 GT/s, Die 1 supports 16 GT/s. Die 1 answers 16 GT/s. pl_max_speedmode = 0 (≤ 32 GT/s), so the Adapter may later advertise 68B Flit Mode.

If you break it

Two modules of one link answering different rates: the recommended action is an Internal Error, TRAINERROR, LinkError and pl_trainerror.

Check it in the spec
  • SpecParameters, max-rate rule, multi-module rule §4.5.3.3.1, p.137–139
  • SpecRetry requirement by BER §3.8, p.93
Mainband init§4.5.3.3.3–4.5.3.3.5

Clock and valid before data

REPAIRCLK checks clock and track lanes, REPAIRVAL checks valid, and only then does REVERSALMB test data lanes. REVERSALMB is entered only if clock and valid are functional.

Why

Data is sampled with the forwarded clock and framed by valid. If the clock is broken, every data lane would appear to fail and the PHY would wrongly try to repair all of them. Fixing dependencies first gives clean per-lane results.

Real-time example

RCKP has an open. REPAIRCLK sees no pattern on it, repairs the clock onto the redundant clock lane; then REVERSALMB sees 68 lanes of correct Per Lane ID patterns.

If you break it

Testing data first with a broken clock: 68 out of 68 lanes fail and the module goes to TRAINERROR, though only one bump was bad.

Check it in the spec
  • SpecOrder and entry condition §4.5.3.3.5, p.151
  • SpecClock repair result interpretation §4.5.3.3.3, p.147
Mainband init§4.5.3.3.5 p.151–153

Lane reversal is detected by majority

The Tx sends 128 iterations of the unscrambled Per Lane ID pattern on all N lanes. A lane passes with ≥ 16 consecutive good iterations. If most lanes pass, no reversal. Otherwise the Tx applies reversal and tests again; if most now pass, reversal stays for the life of the link; if not, TRAINERROR.

Why

Package routing sometimes has to cross lanes over (die rotation). Per Lane ID patterns make each lane self-identifying. Majority voting tolerates a few lanes that are simply broken and will be repaired next.

Real-time example

x64 Advanced with the lanes crossed over: almost every receiver lane k sees the ID of transmitter lane 63−k, so most lanes fail. The Tx applies reversal and retests: 67 of 68 pass. Reversal is kept; the one failing lane goes to REPAIRMB.

If you break it

Scrambling the Per Lane ID pattern destroys its lane identity; reversal detection becomes random.

Check it in the spec
  • SpecSequence, majority, 16 of 128, not scrambled §4.5.3.3.5, p.151–153
  • IllustrativeThe lane counts
Training at speed§4.5.3.4.3 p.158

SPEEDIDLE picks the rate from where you came

From DATAVREF: the highest common rate. From L1: the speed of the last ACTIVE. From LINKSPEED or PHYRETRAIN (degrade): the next lower rate, unless already at 4 GT/s, then TRAINERROR. Width is whatever MBINIT.REPAIRMB or MBTRAIN.REPAIR last set.

Why

One idle state handles every frequency change, so the calibration that follows (TXSELFCAL onward) is the same path for first training, L1 exit and degrade. L1 exit restores the old speed, so a short power-saving trip does not cost bandwidth.

Real-time example

A 32 GT/s link fails LINKSPEED and has no repair resources: exit to speed degrade → SPEEDIDLE picks 24 GT/s → TXSELFCAL … LINKSPEED again.

If you break it

Restoring the maximum rate on L1 exit after an earlier degrade re-enters a speed already known to fail.

Check it in the spec
  • SpecRate rules and width rule §4.5.3.4.3, p.158
  • SpecSpeed encodings 4–64 GT/s Table 10-1 (pl_speedmode), p.525
Training at speed§4.5.3.4.5–4.5.3.4.11

Valid before data, deskew before final centering

At speed the order is: Rx clock calibration, Valid centering (and optional Vref), data centering (and optional Vref), optional per-lane deskew, then DATATRAINCENTER2 to recenter on the aggregate data.

Why

Valid frames data, so it must be right first. Deskew moves each lane's sampling point, which shifts the aggregate eye, so the clock has to be recentered afterwards; that is the only purpose of DATATRAINCENTER2.

Real-time example

Die 1 deskews lanes 40–47 by +3/64 UI. Die 0's recentering in DATATRAINCENTER2 then moves its Tx clock phase by about +1/64 UI to sit in the middle of the new combined eye.

If you break it

Skipping recentering after deskew leaves the link at the edge of the eye; it passes LINKSPEED but fails after a few degrees of temperature drift.

Check it in the spec
  • SpecSub-state purposes §4.5.3.4.5–4.5.3.4.11, p.158–164
  • IllustrativeThe deskew amounts
Training at speed§4.5.3.4.12–13 p.164–168

LINKSPEED: repair, narrow, or slow down

LINKSPEED runs a 4K UI LFSR point test at the final phase. On errors: repair if Advanced and redundant lanes suffice; width-degrade if Standard and the failures fit in one half; otherwise degrade speed. A speed-degrade request overrides an outstanding repair request.

Why

The order keeps as much bandwidth as possible: a repair loses nothing, a width degrade halves bandwidth, a speed step loses less on Advanced (32 → 24 GT/s is 25%) but affects every lane. Letting speed degrade win avoids two dies taking different paths.

Real-time example

x16 Standard at 32 GT/s: lanes 10 and 13 fail. Both are in lanes 8–15, so the link degrades to x8 on lanes 0–7 (lane map 001b) and goes back through TXSELFCAL.

If you break it

Lanes 3 and 12 fail on x16 Standard: they are in different halves, so width degrade is impossible; the link must drop speed instead.

Check it in the spec
  • SpecLINKSPEED steps 3–5 §4.5.3.4.12, p.164–167
  • SpecREPAIR rules and lane map codes §4.5.3.4.13, p.167 · Table 4-9, p.155
Training at speed§4.5.3.4.12 p.165–167

Multi-module: MMPL decides for everyone

In a multi-module link each module reports done, error or degrade to the Multi-module PHY Logic, which resolves one outcome and tells every module which response to send. A mismatch between expected and received response sends all modules to TRAINERROR.

Why

All modules must run at the same speed and width under one RDI. Letting each module decide alone could leave one at 32 GT/s and another at 24 GT/s.

Real-time example

Four modules at 32 GT/s; module 2 has unrepairable errors. MMPL may resolve to speed degrade for all four, or (per the Section 4.7 flowchart) disable module 2 and run the other three.

If you break it

A module that exits to LINKINIT on its own "done" while the others go to SPEEDIDLE: the Adapter sees an RDI that never reaches Active.

Check it in the spec
  • SpecMMPL resolution, mismatch rule, Retimer stall 4 ms §4.5.3.4.12 step 5, p.165–167
  • SpecResolution flowchart §4.7
Retrain & errorsTables 4-10 to 4-12 p.169

The worse problem wins

In PHYRETRAIN both modules send a retrain encoding: 001b no lane errors (→ TXSELFCAL), 100b repairable (→ REPAIR), 010b unrepairable (→ SPEEDIDLE). If they differ, both resolve to the more severe: speed degrade over repair over none.

Why

Each die only sees its own receive errors. Taking the more severe request fixes whichever direction is worse, and because the rule is symmetric, both dies compute the same result.

Real-time example

Die 0's receivers are clean (001b); Die 1 sees errors it can repair (100b). Both resolve to 100b and go to MBTRAIN.REPAIR. Die 0's transmitter applies the repair Die 1 asked for.

If you break it

Resolving to the less severe (001b) would retrain without repair, and Die 1 would see the same errors again.

Check it in the spec

  • SpecRuntime Link Test Status mapping Table 4-10, p.169
Retrain & errors§4.5.3.7.2 p.170

PHY retrain starts with pl_error

On a Valid framing error the PHY asserts pl_error with the bad flit or chunk on RDI, completes the stall handshake, then sends {LinkMgmt.RDI.Req.Retrain}. RDI goes to Retrain when the response arrives.

Why

The Adapter must discard the damaged bytes before they reach CRC checks or the Protocol Layer, and the transmitter must be quiet at a flit boundary before training patterns replace data.

Real-time example

See the RDI guide's "Retrain (framing error)" scenario for the cycle-level waveform.

If you break it

Retraining without the stall handshake cuts a flit in half on the wire; with 68B flits the remote shifter loses alignment.

Check it in the spec
  • SpecSteps 1–6 §4.5.3.7.2, p.170
  • Specpl_error rules Table 10-1, p.524
Retrain & errors§4.5.3.8 p.171–172

TRAINERROR holds while RDI is in LinkError

TRAINERROR tri-states the transmitters. Entry uses a sideband handshake when the sideband works. Exit to RESET is quick if there is no error escalation, but the PHY must stay in TRAINERROR as long as RDI is in LinkError. In-progress sideband packets finish before RESET.

Why

LinkError means software has to look at the error first. Retraining underneath it would bring the link back up before software is ready. Finishing sideband packets avoids sending half a packet into a partner that is about to reset.

Real-time example

An unrepairable REPAIRMB failure goes to TRAINERROR; RDI is not in LinkError, so the LTSM returns to RESET and may retry. A viral error from CXL holds RDI in LinkError; the LTSM sits in TRAINERROR until software releases it.

If you break it

Leaving TRAINERROR while RDI is in LinkError: the PHY retrains and the remote die sees training patterns from a link that is officially down.

Check it in the spec
  • SpecEntry handshake, exit rules §4.5.3.8, p.171–172
Retrain & errors§4.4.1 p.120 · §4.5.3.5 p.168

Scramble with a known LFSR, reset in LINKINIT

Data in ACTIVE is scrambled with the PCIe LFSR polynomial (X23+X21+X16+X8+X5+X2+1), with a lane-dependent seed. The LFSR is reset on entry to LINKINIT.

Why

Scrambling spreads the spectrum and avoids long runs of identical bits, which helps clock recovery margins and EMI. Different seeds per lane avoid identical patterns on neighbouring lanes (crosstalk). Resetting in LINKINIT gives both dies a common starting point before the first scrambled flit.

Real-time example

After a Retrain, both dies pass through LINKINIT again, reset their LFSRs, and the first post-retrain flit descrambles correctly without any sync pattern.

If you break it

Resetting the scrambler on RDI Active instead of LINKINIT entry: if the two dies see Active a few cycles apart, the first flits descramble to garbage.

Check it in the spec
  • SpecLFSR and seeds §4.4.1, p.120 · Table 4-4
  • SpecReset in LINKINIT; scrambled in ACTIVE §4.5.3.5–4.5.3.6, p.168
  • BackgroundSpectrum and crosstalk reasons
Retrain & errors§4.6 p.173–175

Recalibrate without stopping traffic

Runtime Recalibration uses the Track lane while ACTIVE; mainband data with correct valid framing must still be processed. With TARR, the receiver can ask the partner's transmitter to shift by n/64 UI.

Why

A full retrain stops traffic for microseconds or more. Drift is slow and small, so a side-channel measurement plus a small Tx adjustment keeps the eye centered with no interruption. TARR moves the work to the transmitter, which already did most adjustments in training, so receivers need less built-in margin.

Real-time example

Die temperature rises 30 °C under load. Every few milliseconds Die 0 requests a Track pattern, measures a 2/64 UI drift, and sends {RECAL.track tx adjust req}; Die 1 shifts its Tx clock. No flit is delayed.

If you break it

Pausing data during Track recalibration violates the spec and adds latency spikes every recalibration period.

Check it in the spec
  • SpecTrack sequence, TARR, data continues §4.6, p.173–175
  • IllustrativeTemperature, period, drift amount

14 · Test yourself

Interview-style questions.

List the top-level LTSM states in bring-up order. Basic

RESET → SBINIT → MBINIT → MBTRAIN → LINKINIT → ACTIVE. Plus PHYRETRAIN, L1/L2 and TRAINERROR off the main path.

SpecFigure 4-33, p.131

Which states have no 8 ms timeout? Basic

RESET, ACTIVE, L1/L2 and TRAINERROR. All others time out after 8 ms, counted per sub-state, and the timer resets on a Stall message.

Spec§4.5, p.124

Why is MBINIT done at 4 GT/s? Basic

Lowest speed, widest eye: an untrained link works, so clock, valid and data lanes can be checked for opens, shorts and reversal, and Vref set, before the harder calibration at the target speed.

SpecTable 4-6, p.131

How does SBINIT cope with two dies leaving reset at different times? Intermediate

A die that detects the pattern sends four more iterations before stopping; a die that detects nothing alternates 1 ms sending and 1 ms quiet for up to 8 ms. Then both exchange {SBINIT Out of Reset} until each has received it.

Spec§4.5.3.2, p.134

Why are clock and valid repaired before data lanes? Intermediate

Data is sampled with the forwarded clock and framed by valid. With a broken clock every data lane would look broken. REVERSALMB is only entered if clock and valid work.

Spec§4.5.3.3.5, p.151

What does DATATRAINCENTER2 do that DATATRAINCENTER1 didn't? Intermediate

Recenters the clock on the aggregate data after the partner performed per-lane deskew in RXDESKEW, which shifted the combined eye.

Spec§4.5.3.4.11, p.164

LINKSPEED finds errors. What are the three outcomes and their order of preference? Advanced

Repair (Advanced, if redundant lanes are enough) or width degrade (Standard, if failures are in one half) → MBTRAIN.REPAIR; otherwise speed degrade → SPEEDIDLE at the next lower rate (TRAINERROR if already 4 GT/s). A speed-degrade request overrides an outstanding repair request. A Runtime Link Test Control change instead sends it to PHYRETRAIN.

Spec§4.5.3.4.12, p.164–167

Die 0 sends retrain encoding 001b, Die 1 sends 100b. Where do they go? Advanced

Both resolve to 100b and go to MBTRAIN.REPAIR. The more severe request always wins: 010b (speed degrade) over 100b (repair) over 001b.

SpecTable 4-12, p.169

Where does each of L1 exit and L2 exit land, and why the difference? Advanced

L1 → MBTRAIN.SPEEDIDLE, restoring the last ACTIVE speed: settings survive, so only speed-dependent calibration repeats. L2 → RESET: deeper power-down may lose state, so full training (≥ 4 ms RESET included) and a fresh Adapter parameter exchange follow.

Spec§4.5.3.9, p.172 · §4.5.3.4.3, p.158

Why must the LTSM stay in TRAINERROR while RDI is in LinkError? Advanced

LinkError means software has to handle the error first (for example DPC). Retraining underneath would bring the link up before software allows it. Once RDI leaves LinkError, the LTSM may go to RESET.

Spec§4.5.3.8, p.171
