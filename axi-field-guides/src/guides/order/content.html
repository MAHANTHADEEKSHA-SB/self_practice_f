AXI IDs & Ordering Field Guide

AXI gets its performance from letting transactions overtake each other, and its correctness from saying exactly when they may not. This guide covers transaction IDs and how interconnects extend them, the Unique ID indicator, the ordering model (Memory locations, Peripheral regions, observation, completion, early responses), write data ordering from AXI3's WID to Resource Planes, and read interleaving and chunking. It includes an ordering resolver, waveforms, a scoreboard design, verification checks and interview questions.

1 · Why AXI has IDs

An ID is a promise of order for a group of transactions and a promise of freedom between groups.

Performance

Don't wait for the slow one

Transactions with different IDs may complete in any order, so a fast SRAM read doesn't wait behind a DRAM miss. One physical port acts as several logical in-order ports.

Spec§A5.1, p.90

Simplicity

In order where it matters

Same-ID responses come back in request order, so a Manager that needs order just reuses one ID and needs no reorder logic.

Spec§A5.3, p.93 · §A5.3.4, p.95

Scalability

Interconnects keep IDs unique

Each interconnect level appends Manager-port bits, so Managers never coordinate their ID values, and responses find their way back.

Spec§A5.4, p.99

Memory model

Ordering is defined by observation

The model says what another agent can observe and when, not just which response comes first. That is what software barriers and drivers rely on.

Spec§A5.3.3–A5.3.4, p.94–95

2 · IDs through a fabric

Example: three Managers with 4-bit IDs into a 3:1 interconnect. The Subordinate sees 6-bit IDs; the top two bits name the Manager port.

Reflection

A Subordinate must return BID = AWID and RID = ARID. A Subordinate without ID signals cannot be connected to a Manager that has them.

Spec§A5.1.1, p.90 · §A5.5, p.100 · §A5.6, p.101

Omitting IDs

A Manager that never reorders, or has one outstanding transaction, may omit IDs (ID width 0); the Subordinate ties its AxID inputs LOW. A Subordinate that never reorders need not use ID values, but must still reflect them.

Spec§A5.1.1, p.90

ID remapping

An interconnect may compress or remap IDs, but any manipulation must keep the ordering requirements of the original IDs.

Spec§A5.3.6, p.96

4 · The ordering model

The model guarantees order only for requests on the same channel, with the same ID, to the same destination. Everything else is free unless the Manager waits for a response first.

No ordering guarantee between:

  • transactions from different Managers
  • reads and writes
  • transactions with different IDs
  • transactions to different Peripheral regions
  • transactions to different Memory locations

If a Manager needs order between any of these, it must wait for the first transaction's response before issuing the second.

Spec§A5.3, p.93

Device vs Normal

Device = AxCACHE[1] LOW, Normal = AxCACHE[1] HIGH. Device may target Peripheral regions or Memory; Normal targets Memory, and a Normal access to a Peripheral completes but with an IMPLEMENTATION DEFINED result.

Spec§A5.3.2, p.94

Observation and completion

  • Peripheral: DRW1 is observed by DRW2 when DRW1 reaches the Subordinate first.
  • Memory: W1 observed by W2 if W2 takes effect after W1; R1 observed by W2 if R1 read a write W3 that came before W2; W1 observed by R2 if R2 returns W1's data or a later write's.
  • Write completion: the B handshake (with BCOMP if present). Read completion: the RLAST handshake.

Spec§A5.3.3, p.94

What a Manager is promised (same Manager, same ID)

  • Before completion: Device writes (and Device reads) to one Peripheral region arrive in order. Writes to one Memory location with the same cacheability are observed in order; reads too, once one has observed a write.
  • From completion: a read, or a Non-bufferable write, is observable to any later request from any Manager. A Bufferable write is observable by Domain: Non-shareable (issuer only), Shareable (its Domain), System (all).
  • Responses: same-ID reads complete in order; same-ID writes complete in order.

Spec§A5.3.4, p.94–95

Subordinates and interconnects

  • Peripheral execution order is IMPLEMENTATION DEFINED (normally arrival order).
  • Memory, same cacheability and location: W→W same ID ordered; anything received after a completion response is ordered after that transaction.
  • Interconnect: same-ID requests to the same/overlapping locations (or same Peripheral region for Device) are issued in order; same-ID responses returned in order.

Spec§A5.3.5–A5.3.6, p.95–96

Early read response

For Normal reads, an intermediate component may answer from local memory if it is up to date with all earlier writes to the same or overlapping address, and only after all earlier same-ID reads have been answered.

Spec§A5.3.7, p.96

Early write response

For Bufferable writes with no downstream observers. The responder must still propagate the write, keep same-ID response order, and order later accesses to the same location (Normal) or region (Device) behind it until the downstream response arrives. A Device Bufferable write must be pushed on without waiting for other traffic.

Spec§A5.3.7, p.96–97

Mixing memory types

No ordering between Cacheable and Device/Normal Non-cacheable requests, but same-ID responses are still in order. Device vs Normal Non-cacheable to the same location: ordered unless Device_Normal_Independence is True. Ordered_Write_Observation adds address-independent W→W order for same-ID writes.

Spec§A5.3.8–A5.3.9, p.97–98

      6 · The Unique ID indicator

      A one-bit promise from the Manager: "no other transaction of mine with this ID is in flight on this channel". Downstream components can then skip ordering checks and tracking for it.

      Rules

      • AxIDUNQ HIGH ⇒ no outstanding same-ID transaction on that channel from this Manager.
      • After a request with AxIDUNQ HIGH, no new same-ID request until it completes.
      • BIDUNQ equals AWIDUNQ on the single or Completion response; RIDUNQ equals ARIDUNQ on every beat. For Atomics with read data, RIDUNQ follows AWIDUNQ.
      • Outstanding = from the AxVALID cycle until the final response is accepted (with BCOMP if present); an Atomic until both responses.
      • Optional unless a transaction type requires it (for example chunked reads).

      Spec§A5.2, Tables A5.3–A5.4, p.91–92 · §A5.6.2.2, p.103

      Why it helps

      An interconnect normally has to track every outstanding ID to keep same-ID responses in order across Subordinates (scenario "Same ID, two targets"). A unique request has nothing to be ordered against, so it can go straight through with no table entry, and the response can be returned as soon as it arrives. That cuts tracking logic, especially for Managers that already order at source, like many CPUs.

      Spec§A5.2, p.91 · Background on interconnect tracking

      7 · Write data and read data ordering

      Write data

      W follows AW order

      • A Manager sends write data in the order it issued the requests.
      • On credited interfaces the rule is per Resource Plane: data on different planes may overtake and interleave.
      • A Subordinate returns BID equal to AWID; an interconnect returns same-AWID responses from different Subordinates in request order.
      • AXI3 allowed interleaving W beats of different IDs, tagged with WID. AXI4 removed WID and interleaving.

      Spec§A5.5, p.100 · H.c §A5.2.2, p.A5-81

      Read data

      Reorder by ID, interleave by beat

      • RID equals ARID; same-ARID data from different Subordinates reaches the Manager in request order.
      • Read data reordering depth: how many accepted requests a Subordinate may send data for; 1 = in order. Static, documented, not discoverable.
      • Beats of different IDs may interleave (including Atomics). Read_Interleaving_Disabled lets an interface promise or request no interleaving.
      • Chunking: return 128-bit chunks of one transaction in any order (next card).

      Spec§A5.6–A5.6.1, p.101

      8 · Why each rule exists, with real-time examples

      IDs§A5.1 p.90

      Same ID in order, different IDs free

      All transactions with one ID stay ordered; there is no restriction between different IDs.

      Why

      The Manager knows which of its transactions depend on each other. Letting it express that with an ID means the system only pays for ordering where it's needed.

      Real-time example

      A CPU uses one ID for its in-order instruction fetch stream and a pool of IDs for data misses. An 80 ns DRAM miss doesn't block a 5 ns L3 hit on another ID.

      If you break it

      Reordering same-ID responses hands data to the wrong load; forcing order across IDs kills memory-level parallelism.

      Sources
      • Spec§A5.1, p.90 · §A5.3, p.93
      • Illustrativelatencies
      IDs§A5.4 p.99

      Interconnects widen IDs

      The interconnect appends Manager-port bits to AWID/ARID and uses them to route BID/RID back, removing them on the way.

      Why

      Two Managers using the same ID value must not be ordered against each other, and the Subordinate must be able to tell them apart in its responses. Appending the port number does both without any coordination between Managers.

      Real-time example

      8 Managers with 6-bit IDs through two levels of 4:1 crossbars: 6 + 2 + 2 = 10-bit IDs at the memory controller.

      If you break it

      An interconnect that truncates IDs to fit a narrow Subordinate merges unrelated streams into false ordering, or worse, misroutes responses.

      Sources
      • Spec§A5.4, p.99 · §A5.3.6, p.96
      • Derivedwidth arithmetic
      Ordering model§A5.3 p.93

      Need order? Wait for the response

      Outside the guaranteed cases, a Manager that needs order must wait for the first transaction's response before issuing the second.

      Why

      Reads and writes travel on different channels and can be routed differently; different Managers share nothing. The completion response is the only event the Manager can see that proves the first transaction is observable.

      Real-time example

      A driver writes a DMA descriptor to memory, then a doorbell register on a different Subordinate. It must wait for the descriptor write's BRESP before writing the doorbell, or the DMA may fetch the old descriptor.

      If you break it

      Races that appear only under load, when the descriptor write sits in a queue longer than the doorbell write.

      Sources
      • Spec§A5.3, p.93 · §A5.3.4, p.95
      • Illustrativedriver
      Ordering model§A5.3.4 p.95

      Bufferable completion is scoped by Domain

      A Bufferable write's completion guarantees observability only within its Domain: Non-shareable to the issuer, Shareable to its Domain, System to all.

      Why

      An early response comes from a point that only some observers pass through. A Non-shareable write answered by a Manager-private buffer is visible to that Manager, but another Manager reading memory directly would miss it.

      Real-time example

      A DMA writes a buffer as Non-shareable Normal Non-cacheable Bufferable and gets early BRESPs from its local write buffer. A CPU in another cluster may not see the data yet; marking the write System, or using a Non-bufferable final write, fixes it.

      If you break it

      Software relying on BRESP of Non-shareable writes for cross-Manager handoff reads stale data.

      Sources
      • Spec§A5.3.4, p.95
      • IllustrativeDMA example
      Ordering model§A5.3.8 p.97

      Device vs Normal Non-cacheable

      With Device_Normal_Independence False (default), Device and Normal Non-cacheable requests with the same ID to the same location are observed in issue order. True lets them pass each other.

      Why

      Some systems route Device and Normal traffic through different paths (a strongly ordered peripheral path and a memory path) and cannot cheaply keep them ordered. Making it a declared property lets those systems be honest, and lets Managers that care refuse to connect.

      Real-time example

      A GPU writes a command buffer Normal Non-cacheable, then kicks it with a Device write to the same 4 KB control page using the same ID. With independence True, the kick could overtake the commands.

      If you break it

      Manager False + Subordinate True is listed as incompatible.

      Sources
      • Spec§A5.3.8, Tables A5.5–A5.6, p.97 · Table B4.2, p.309
      • IllustrativeGPU example
      Early responses§A5.3.7 p.96–97

      An early responder inherits the ordering duty

      After an early write response, the responder must order later accesses to the same location (Normal) or region (Device) behind the write, until its own downstream response arrives.

      Why

      The Manager believes the write is done. If a later read to the same address overtook the buffered write, the Manager would read old data after being told its write completed.

      Real-time example

      A system cache gives an early BRESP for a write to 0x1000 and forwards it to DRAM. A read to 0x1000 arrives 10 cycles later; the cache must serve it from the buffered data or hold it until the DRAM write is done.

      If you break it

      Read-after-write hazards that only appear when the early-response path is enabled.

      Sources
      • Spec§A5.3.7, p.96–97
      • Illustrativecache
      Early responses§A5.3.7 p.97

      Device Bufferable writes must keep moving

      A component that gave an early response to a Device Bufferable write must propagate it without waiting for any other transaction.

      Why

      The Manager may be waiting for the peripheral's reaction to this write (an interrupt, a status change) before it sends anything else. If the buffer waited for more traffic to batch with, both sides would wait forever.

      Real-time example

      A driver writes "start" to a peripheral (Device Bufferable), then polls its status with reads to another region. If the buffer held "start" until another write came, the polling would never end.

      If you break it

      Deadlock between software polling and a lazy write buffer.

      Sources
      • Spec§A5.3.7, p.97
      • Illustrativedriver
      Data ordering§A5.5 p.100

      No write data interleaving

      Write data follows request order, one transaction at a time, except across Resource Planes on credited interfaces.

      Why

      Without interleaving, W beats can be matched to their AW by arrival order alone, so W needs no ID. Every Subordinate gets simpler. Planes are the exception because their purpose is to stop one class of traffic blocking another.

      Real-time example

      An AXI3 memory controller with write interleaving depth 4 needed four reassembly buffers; the AXI4 version needs one W FIFO.

      If you break it

      An AXI3-to-AXI4 bridge must de-interleave WID-tagged data, buffering whole bursts if needed.

      Sources
      • Spec§A5.5, p.100 · H.c §A5.2.2, p.A5-81
      • Illustrativebuffer counts
      Data ordering§A5.6.1 p.101

      Every multi-ID Manager must accept interleaving

      Read data of different IDs may interleave. Read_Interleaving_Disabled is an optimisation, but any Manager that issues different IDs must be designed to accept interleaved data.

      Why

      Interleaving lets a Subordinate send whichever data is ready. If some Managers couldn't cope, every Subordinate and interconnect would need to know which Manager is behind each request.

      Real-time example

      A DMA with 4 IDs keeps 4 small per-ID write pointers into its line buffer; RID selects which pointer advances on each beat.

      If you break it

      A Manager that assumes "all beats of one burst arrive together" corrupts data the first time it meets an interleaving Subordinate.

      Sources
      • Spec§A5.6.1, p.101
      • IllustrativeDMA
      Options§A5.2 p.91

      Unique ID: a promise that saves tracking

      AxIDUNQ HIGH promises no same-ID transaction is in flight, and no new one will be until this completes.

      Why

      The expensive part of an AXI interconnect is tracking outstanding IDs to keep same-ID order across Subordinates. Many Managers already know their IDs are unique; the bit lets them say so.

      Real-time example

      A CPU with 64 outstanding misses, each with its own ID and IDUNQ set. The interconnect can route all 64 to different memory channels without a 64-entry ordering table.

      If you break it

      Asserting IDUNQ while a same-ID request is outstanding lets the interconnect reorder what should have been ordered.

      Sources
      • Spec§A5.2, p.91–92
      • Illustrativenumbers
      Options§A5.6.2 p.102–104

      Chunking needs a unique ID

      ARCHUNKEN is allowed only on a unique-in-flight ARID, for aligned, full-width, ≥128-bit INCR/WRAP reads of a few opcodes.

      Why

      Chunks of one transaction arrive out of order. If another same-ID read were outstanding, the Manager could not tell where one transaction ended and the next began. The 128-bit, aligned, full-width restrictions make every chunk a whole, naturally aligned slice.

      Real-time example

      A 512-bit AXI port bridged to CHI receives a 64-byte line as four 128-bit DAT flits in any order; with chunking, it forwards each as it arrives instead of buffering the line.

      If you break it

      Chunked data mixed with a second same-ID read gets assembled into the wrong transaction.

      Sources
      • Spec§A5.6.2.2, p.103–104
      • BackgroundCHI data flits

      10 · Real silicon: what the theory turns into

      Three ways an interconnect keeps same-ID order

      • Single destination per ID: a same-ID request to a different Subordinate waits until the earlier ones finish. Cheap; costs throughput when a Manager reuses one ID across targets.
      • Reorder buffer: forward everything, buffer early responses until older same-ID ones arrive. Fast; costs buffer area (outstanding × burst size).
      • ID compression: map many Manager IDs onto few Subordinate IDs, keeping the original ordering. Saves Subordinate tracking; serialises the merged IDs.

      12 · Verification

      Scoreboard design

      • One queue per (direction, ID) at the Manager side: push on AR/AW handshake, pop on RLAST/B. A response must match the queue head for its ID.
      • Read beats: per-ID beat counter; RID selects the queue, so interleaving needs no special case.
      • Through an interconnect: map Manager ID to Subordinate ID by the port-bit rule; check order per original ID, not per extended ID.
      • Memory model per location for observation checks: last-writer table updated at the point of observation, not at BRESP.
      • Chunked reads: collect chunks by RCHUNKNUM/RCHUNKSTRB; compare the whole transaction at RLAST.

      Background · rules from §A5.3–A5.6, p.93–106

      Assertions

      • BID / RID only for an outstanding AWID / ARID. §A5.5–A5.6, p.100–101
      • Same-ID: responses in request order. §A5.3.4, p.95
      • W count per AW in order (no interleaving on Valid-Ready). §A5.5, p.100
      • AxIDUNQ ⇒ no outstanding same ID; no same-ID issue while a unique one is outstanding; xIDUNQ echoes. §A5.2, p.91–92
      • Read_Interleaving_Disabled Subordinate ⇒ RID constant from first beat to RLAST. Table A5.8, p.101
      • Chunking rules: eligibility, RCHUNKV constant, RCHUNKNUM ≤ ARLEN, RCHUNKSTRB ≠ 0. §A5.6.2.2, p.103–104

      Scenarios and coverage

      • Same ID to two Subordinates with the far one slower.
      • All IDs in use; ID reuse right after completion.
      • Maximal interleaving: a different RID on every beat.
      • Early-response components with read-after-write to the same line.

      • Coverage: outstanding per ID (1…max), number of distinct IDs in flight, reorder distance (how many older responses a new one overtook), interleave switch count per burst.

      13 · Test yourself

      Use the ordering resolver to check.

      What does the AXI ID guarantee, and what doesn't it? Basic

      Same-ID transactions on one channel stay ordered and their responses return in issue order. Different IDs have no ordering between them; responses may come in any order and read data may interleave.

      Spec§A5.1, p.90 · §A5.3, p.93

      Why are IDs wider at a Subordinate than at a Manager? Basic

      The interconnect appends bits that identify the Manager port, so IDs from different Managers are unique and responses can be routed back. It strips those bits from BID/RID on the way back.

      Spec§A5.4, p.99

      Can write data of two transactions be interleaved in AXI4? In AXI3? In Issue L? Basic

      AXI3: yes, using WID. AXI4: no; WID removed and W follows AW order. Issue L: no on Valid-Ready; on a credited interface, yes across different Resource Planes.

      SpecH.c §A5.2.2, p.A5-81 · §A5.5, p.100

      A Manager writes X to address A and then reads A with the same ID, both outstanding. Is the read guaranteed to see X? Intermediate

      No. Reads and writes have no ordering guarantee between them, even with the same ID. The Manager must wait for the write's BRESP before issuing the read.

      Spec§A5.3, p.93

      Same-ID reads go to two Subordinates. Whose job is it to return the data in order, and how? Intermediate

      The interconnect's. It can hold the second request until the first completes, or reorder the responses in a buffer. The Subordinates only order their own same-ID responses.

      Spec§A5.6, p.101 · §A5.3.6, p.96

      What does a Bufferable write's BRESP guarantee? Intermediate

      Not completion at the endpoint. It guarantees observability according to the write's Domain: to the issuing Manager (Non-shareable), to the Shareable Domain, or to everyone (System).

      Spec§A5.3.4, p.95

      What is the read data reordering depth? Intermediate

      The maximum number of accepted requests for which a Subordinate might send read data, a static design value. 1 means in order. A Manager has no way to discover it at run time.

      Spec§A5.6, p.101

      When must AxIDUNQ not be asserted, and what does BIDUNQ do? Intermediate

      Not when a same-ID transaction from this Manager is outstanding on that channel. After asserting it, the Manager must not reuse the ID until that transaction completes. BIDUNQ equals AWIDUNQ on the single or Completion response.

      Spec§A5.2, p.91

      A system cache gives an early BRESP. What must it still do? Advanced

      Propagate the write downstream before discarding its copy; respect same-ID response order; order later accesses to the same Memory location (or Peripheral region for Device) behind the write until the downstream response arrives; and for Device Bufferable, forward it without waiting on other traffic.

      Spec§A5.3.7, p.96–97

      List the conditions for ARCHUNKEN. Why must the ID be unique? Advanced

      Size = data width or Length 1; Size ≥ 128 bits; 16-byte aligned; INCR or WRAP; ReadNoSnoop, ReadOnce, ReadOnceCleanInvalid or ReadOnceMakeInvalid; unique in-flight ARID. Chunks arrive out of order, so a second same-ID read would make it impossible to tell which chunks belong to which transaction.

      Spec§A5.6.2.2, p.103

      How did the "guarantees before completion" change from H.c to Issue L? Advanced

      H.c ordered same-location writes regardless of memory type and said this implied Device/Normal ordering. Issue L requires the same cacheability, removes ordering between Cacheable and Device/Non-cacheable requests, and makes Device vs Normal Non-cacheable ordering depend on Device_Normal_Independence (default: ordered).

      SpecH.c §A6.5.1, p.A6-88 · §A5.3.4, p.94–95 · §A5.3.8, p.97

      Design a scoreboard that survives read interleaving and an interconnect that widens IDs. Advanced

      Keep one FIFO of expected transactions per original Manager ID. At the Subordinate side, strip the port bits to find the Manager and original ID. For each R beat, use RID to pick the FIFO head and its beat counter; compare data and pop at RLAST. Check that each response matches its FIFO head, which enforces same-ID order without assuming anything about different IDs.

      Background · §A5.4, p.99 · §A5.6.1, p.101
