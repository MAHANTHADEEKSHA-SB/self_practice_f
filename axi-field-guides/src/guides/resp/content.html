AXI Responses, Exclusives & Atomics Field Guide

Every AXI transaction ends with a response, and three features build on that response to make synchronisation work: single- and multi-copy atomicity, exclusive accesses with their monitor, and Atomic transactions that carry the operation to the data. This guide covers BRESP and RRESP with every encoding, the Busy indicator and Consistent DECERR, the exclusive sequence and its rules, the four Atomic types and AWATOP, and the request Opcodes on AxSNOOP. It includes an exclusive-monitor simulator, waveforms, verification checks, interview questions and what changed from AXI3 and AXI4.

1 · Why responses, exclusives and atomics

Completion

The response is the only proof

A Manager learns that a transaction happened, and whether it worked, only from its response: one B per write-channel transaction, one RRESP per read beat. The ordering model is built on these completion points.

Spec§A3.3, p.61 · §A5.3.3, p.94

Errors

Fail cleanly, never hang

Errors don't shorten transactions. SLVERR and DECERR say what went wrong while every beat still completes, so the fabric stays consistent.

Spec§A3.3.2, p.62

Synchronisation

Semaphores without locking the bus

An exclusive read–write pair succeeds only if nobody wrote the location in between, and the bus stays fully shared meanwhile. AXI3's locked transfers blocked everyone; AXI4 dropped them.

Spec§A6.3, p.110 · H.c §A7.3, p.A7-99

Scalability

Send the operation to the data

Atomic transactions perform add, swap, compare-and-swap and friends at the memory or cache, so a hot counter is locked for a few cycles near the data instead of a round trip.

Spec§A6.4, p.113

Write responses

One Completion response per write-channel transaction. Persist CMOs and MTE Match add a second response; BCOMP then marks which one is the Completion, HIGH on exactly one.

Spec§A3.3.1, p.61

Read responses

One response per beat, may differ beat to beat, all Length beats always sent. When data isn't valid the Manager may still sample RDATA, so a Subordinate must not rely on the response code to hide sensitive data.

Spec§A3.3.2, p.62–63

Busy and Consistent DECERR

BBUSY/RBUSY (2 bits) report Subordinate load so Managers can throttle speculation. Consistent_DECERR promises DECERR on all or none of the beats in each cache line, so one beat is enough to check.

Spec§A3.3.2–A3.3.3, p.63–65

4 · Single-copy and multi-copy atomicity

Single-copy atomicity size

No one sees half an update

  • The minimum number of bytes a transaction updates atomically. Larger transactions update in blocks of at least that size.
  • Not fixed by AXI; components that communicate form a single-copy atomic group (for example a 32-bit group with peripherals, and a 64-bit group of CPU, DSP and DRAM).
  • A transaction is never more atomic than the alignment of its start address. Byte strobes don't change the atomicity size.
  • Modifiable transforms must not split an atomic-sized access.

Spec§A6.1 and Figure A6.1, p.108 · §A4.2.2, p.70

Multi-copy atomicity

Everyone sees writes the same way

  • Writes to one location are observed in the same order by all agents, and a write observable by one agent is observable by all.
  • Achieved with a single Point of Serialization per address (invalidating cached copies before the new value is visible) and no forwarding buffers upstream of agents.
  • Multi_Copy_Atomicity must be True for Issue G and later.

Spec§A6.2, Table A6.1, p.109

5 · Exclusive accesses

A load-exclusive / store-exclusive pair. The bus is never locked; the Subordinate's monitor just watches whether anybody wrote the location in between.

1

Exclusive read (ARLOCK HIGH). A monitoring Subordinate records the address against the ARID and answers EXOKAY on every beat. Without a monitor it answers OKAY: data valid, nothing monitored; the Manager should then skip the write. §A6.3.1–A6.3.2, p.110–111

2

Read must complete before the write part starts. §A6.3.2, p.111

3

Exclusive write (AWLOCK HIGH) to the same address with AWID = the read's ARID and matching attributes (Table A6.5). §A6.3.1, p.110 · Table A6.5, p.112

4

Success: still monitored for that ID ⇒ memory updated, EXOKAY. Failure: written by someone, monitor moved by another exclusive read with the same ID, or attributes differ ⇒ not updated, OKAY. §A6.3.4, p.112

5

No write part? Fine: the monitor keeps watching until the next exclusive read with that ID moves it. One address per ID. §A6.3.1, p.111

Restrictions (else UNPREDICTABLE)

  • Address aligned to Size × Length.
  • Total bytes a power of 2: 1 to 128.
  • Length ≤ 16.
  • Domain not Shareable.
  • Opcode ReadExclusive / WriteExclusive.
  • AWTAGOP not Match.
  • AxCACHE chosen so both requests reach the monitor.

Spec§A6.3.3, p.111

The monitor

  • Recommended: one monitor unit per exclusive-capable Manager ID.
  • Watches at least Size × Length bytes, may watch up to 128, which can fail an exclusive because a neighbouring byte was written.
  • An exclusive read's beats are all EXOKAY or none; OKAY and EXOKAY are never mixed in one transaction.
  • A non-monitoring Subordinate answers OKAY to an exclusive write and updates the location.
  • Manager True + Subordinate False on Exclusive_Accesses: exclusives always fail, no deadlock.

Spec§A6.3.3–A6.3.4, p.111–112 · Table A6.4, p.110

Rules that keep Atomics simple

  • One ID for request, B and R, so it must fit both AWID and RID.
  • Unique in flight: AtomicStore against write-channel traffic with the same ID; Load/Swap/Compare against both channels. Hence no ordering with other transactions.
  • AWLOCK LOW, AWSNOOP 0; any AWCACHE/AWDOMAIN valid for the interface.
  • Length > 1 needs full-width Size; strobes HIGH inside the data window, LOW outside; all Atomics count as Regular.
  • Whole location updated atomically, regardless of the component's single-copy atomicity size.

Spec§A6.4.3–A6.4.5, p.114–117 · §A6.4, p.113

Structure and dependencies

  • Read beats: from AWLEN and AWATOP; AtomicCompare with Length > 1 returns half the beats.
  • Subordinate may wait for all W before R, or send all R before taking any W. The Manager must cope with both.
  • RVALID waits for the AW handshake only. The Manager must not wait for RVALID before WVALID.
  • B only after all W beats and when the result is observable. Either response may serve as "visible".

Spec§A6.4.7–A6.4.9, Figure A6.5, p.118–121

Support and errors

  • Supporting Atomics means all operations, sizes and endiannesses.
  • BROADCASTATOMIC tie-off lets a Manager stop issuing them.
  • A Subordinate supporting them only in some regions or types gives an error elsewhere. An interconnect without support needs every Manager configured not to issue them.
  • Device Atomics must reach the endpoint; Cacheable ones may be done in the interconnect or passed on.
  • On a write error the Subordinate still sends every R beat; recommended: error on both R and B.

Spec§A6.4.8, p.119 · §A6.4.10, p.121–122

9 · Why each rule exists, with real-time examples

Responses§A3.3.2 p.62

Errors don't end bursts early

All Length beats are always completed, whatever the response.

Why

Every component on the path counts beats. If an error shortened a burst, all of them would need a separate way to resynchronise. Keeping the count fixed means errors are just data.

Real-time example

A 16-beat read hits a powered-down SRAM bank after beat 9. Beats 10–16 come back SLVERR with junk data; the CPU's line-fill logic still counts 16 and raises the error once.

If you break it

A Subordinate that sends only one error beat hangs the R channel.

Sources

  • Illustrativeexample
ResponsesTables A3.28, A3.31

SLVERR vs DECERR

SLVERR: reached an endpoint, which failed. DECERR: never reached a point where data exists, typically no Subordinate at that address.

Why

Software reacts differently. DECERR usually means a bad pointer or a missing device (a programming error). SLVERR means the device is there but unhappy (powered down, read-only, FIFO overrun), which a driver may be able to fix.

Real-time example

A write to an unmapped hole: the interconnect's default Subordinate returns DECERR. A write to a read-only OTP register: the OTP controller returns SLVERR.

If you break it

Debugging gets much harder: a firmware engineer chasing a "decode error" in an address map when the real cause is a powered-down block.

Sources
  • SpecTables A3.28, A3.31, p.62–63

Responses§A3.3.2 p.63

Error data may still be sampled

When a response says data is not valid, the Manager might still sample RDATA, so the Subordinate must not rely on the response to hide sensitive data.

Why

Managers often latch RDATA every beat for timing and look at RRESP afterwards. Whatever is on the wires during an error beat effectively leaves the Subordinate.

Real-time example

A key-storage block refuses a Non-secure read with SLVERR but drives the key on RDATA. A Non-secure CPU that captured RDATA has the key.

If you break it

A security leak through error responses. Drive zeros, or anything harmless, on error beats.

Sources
  • Spec§A3.3.2, p.63 · Table B4.1, p.308
  • Illustrativekey block
Exclusive§A6.3 p.110–112

OKAY means "failed" for an exclusive write

An exclusive write succeeds only with EXOKAY; OKAY means memory was not updated (or the Subordinate has no monitor).

Why

The response code space was kept compatible: a Subordinate that knows nothing about exclusives naturally answers OKAY, which tells the Manager it got no exclusivity guarantee.

Real-time example

On Arm, STXR writes 0 to its status register on EXOKAY and 1 otherwise; the spin-lock loop retries on 1.

If you break it

A bridge that maps EXOKAY to OKAY on the way back makes every exclusive look failed and spin-locks livelock.

Sources
  • Spec§A6.3.2, p.111 · Table A3.28, p.62
  • BackgroundArm LDXR/STXR
Exclusive§A6.3.3 p.111

Aligned, power-of-two, ≤ 128 bytes, ≤ 16 beats

The exclusive's bytes form one naturally aligned power-of-two block of at most 128 bytes.

Why

A monitor tracks a granule, not an arbitrary range. Natural alignment means the block always fits inside one granule, so one comparator per ID is enough.

Real-time example

An exclusive pair on a 16-byte (LDXP/STXP) structure at 0x1010 is fine; at 0x1018 it straddles a 16-byte boundary and is UNPREDICTABLE.

If you break it

UNPREDICTABLE: some monitors succeed, some fail, some corrupt.

Sources
  • Spec§A6.3.3, p.111
  • BackgroundLDXP/STXP
ExclusiveTable A6.5 p.112

Read and write must match

If ID, address, length, size, burst, lock, AxCACHE[1:0], protection, domain, Opcode or MMU fields differ between the exclusive read and write, the write may fail.

Why

The monitor identifies the pair by ID and address in the Subordinate's view. A changed attribute could route the write to a different monitor, or represent a different address space entirely.

Real-time example

A width converter makes the read Size 8 Length 1 and the write Size 4 Length 2 (allowed for exclusives if the bytes match) but changes AxCACHE[0] differently on each: the monitor may treat them as different.

If you break it

Exclusives that fail forever only in one path through the fabric.

Sources

Atomic§A6.4.4 p.116

Atomics use a unique ID

AtomicStore: no other outstanding write-channel transaction with that ID. Load, Swap, Compare: none on either channel.

Why

An Atomic has a B and possibly an R with one ID. If other transactions shared it, the same-ID ordering rules would tie the Atomic's R to unrelated reads and its B to unrelated writes, creating cross-channel ordering AXI otherwise never has.

Real-time example

A CPU reserves ID 0x3F for Atomics and issues one at a time on it; all other traffic uses 0x00–0x3E.

If you break it

An interconnect may deadlock trying to order an Atomic's R behind a read that is waiting for something the Atomic holds.

Sources
  • Spec§A6.4.4, p.116
  • IllustrativeID choice
Atomic§A6.4.7 p.118

R and W may happen in either order

The Subordinate may wait for all W before R, or send all R before taking W. The Manager must handle both.

Why

Some Subordinates read first (they need the old value before they can do anything); some take the operand first. Allowing both means neither design is penalised, as long as the Manager never makes W wait for R or R wait for W.

Real-time example

A DDR controller reads the line, returns the old value at once and then waits for the operand; a system cache that already holds the line takes W first and returns R and B together.

If you break it

A Manager that holds WVALID until it sees R deadlocks against a Subordinate that waits for W.

Sources
  • Spec§A6.4.7, p.118 · §A6.4.9, p.120
  • Illustrativedesigns
Atomic§A6.4.10 p.121–122

All or nothing support

A component that supports Atomics supports every operation, size and endianness; a path that can't handle them must not receive them.

Why

A Manager can't know which operation a program will use. Partial support would force run-time negotiation. Instead, support is a static property, BROADCASTATOMIC turns issuing off, and unsupported regions give an error.

Real-time example

An SoC whose peripheral interconnect lacks Atomics ties BROADCASTATOMIC LOW on the CPU port that leads there; the CPU then performs LDADD as an exclusive loop internally.

If you break it

An Atomic reaching a component that can't parse AWATOP is treated as a plain write of the operand: silent corruption.

Sources
  • Spec§A6.4.10, p.121–122
  • BackgroundCPU fallback behaviour
System§A6.1 p.108

Atomicity never exceeds alignment

A transaction's single-copy atomicity guarantee is never greater than the alignment of its start address.

Why

An unaligned 8-byte access may straddle two memory words, banks or even Subordinates. Making it atomic would need a lock across both; the spec simply doesn't promise it.

Real-time example

A 64-bit pointer at 0x1004 is updated by one CPU and read by another; the reader may see 4 new bytes and 4 old ones. At 0x1008 it is atomic in a 64-bit group.

If you break it

Torn reads of shared data structures, which software must avoid with alignment.

Sources

Where the monitors live

  • Local monitor inside the CPU for Non-shareable exclusives (no bus monitor needed).
  • Global monitor in the memory controller or on-chip SRAM for exclusives that reach the bus; one entry per exclusive-capable ID is recommended.
  • Shareable exclusives are handled through the coherent interconnect (CHI), which is why AXI forbids Shareable exclusives.
  • Default Subordinate in every interconnect: answers DECERR for unmapped addresses, with the full beat count.

13 · Verification

Assertions

  • EXOKAY only for exclusive requests; never mixed with OKAY within one exclusive read. Tables A3.28, A3.31 · §A6.3.4, p.112
  • DEFER/UNSUPPORTED only for WriteDeferrable; OKAYDIRTY only for ReadShared; TRANSFAULT only with PRI. Tables A3.28, A3.31
  • Exclusive: aligned to Size × Length, power-of-two bytes ≤ 128, Length ≤ 16, not Shareable. §A6.3.3, p.111
  • No exclusive write with an ID whose exclusive read is still outstanding. §A6.3.2, p.111
  • Atomic: AWLOCK LOW, AWSNOOP 0; unique ID per §A6.4.4; R beat count from AWLEN and type; strobes exactly the data window. §A6.4.3–A6.4.7, p.114–118
  • BCOMP HIGH on exactly one B per write-channel transaction. §A3.3.1, p.61
  • Consistent_DECERR: all or none DECERR per cache line. Table A3.32, p.64

Reference model and scenarios

  • Monitor model like section 6, keyed by (Manager port, ID), with the Subordinate's granule; predict EXOKAY/OKAY and memory update.
  • Atomic model per operation and endianness, all sizes; check returned old value and new memory value; Compare with lower- and upper-half addresses.
  • Scenarios: N Managers racing exclusives on one address; exclusive interleaved with Atomics to the same address; Atomic R-before-W and W-before-R Subordinates; errors on W but not R.
  • Coverage: every response code per channel; exclusive success/fail × cause; AWATOP all 8 ops × 2 endian × sizes; Compare sizes 2–32 × INCR/WRAP.

14 · Test yourself

What do OKAY and EXOKAY mean on an exclusive read and on an exclusive write? Basic

Read: EXOKAY = monitored; OKAY = Subordinate doesn't support exclusives (data still valid). Write: EXOKAY = succeeded and memory updated; OKAY = failed, not updated (or no monitor, in which case it was updated).

SpecTables A3.28, A3.31, p.62–63 · §A6.3.2, §A6.3.4, p.111–112

SLVERR vs DECERR? Basic

SLVERR: reached an endpoint that failed (read-only, powered down, FIFO overrun). DECERR: never reached a point where data exists, typically no Subordinate at the address; usually generated by the interconnect's default Subordinate.

SpecTables A3.28, A3.31, p.62–63

A Subordinate hits an error on beat 3 of 8. What does it send? Basic

All 8 beats. Beat 3 onwards (or whichever beats are affected) carry an error response; the burst is never shortened.

Spec§A3.3.2, p.62

Why did AXI4 remove locked transfers? Basic

Few components needed them, and they made interconnects complex and QoS guarantees hard because a locked sequence blocks all other Managers from the region. Exclusive accesses give semaphores without locking.

SpecH.c §A7.3, p.A7-99

List the restrictions on an exclusive access. Intermediate

Aligned to Size × Length; power-of-two total of 1–128 bytes; Length ≤ 16; not Shareable; Opcode ReadExclusive/WriteExclusive; AWTAGOP not Match; AxCACHE such that both requests reach the monitor; attributes matching between read and write.

Spec§A6.3.3, p.111 · Table A6.5, p.112

Can an exclusive fail even though nobody wrote the exact bytes? Intermediate

Yes: the monitor may watch up to 128 bytes, so a write to a neighbouring byte fails it; another exclusive read with the same ID moves the monitor; or read and write attributes differed.

Spec§A6.3.3–A6.3.4, p.111–112

Encode AtomicLoad, big-endian, signed maximum. Intermediate

AWATOP = 0b10_1_100 = 0x2C: AtomicLoad (10), big-endian (1), SMAX (100).

SpecTables A6.8–A6.9, p.117–118

What is the ID rule for Atomic transactions and why? Intermediate

One ID for request, B and R, and it must be unique in flight: no other same-ID write-channel transaction for AtomicStore, none on either channel for the others. This removes any ordering link between Atomics and other traffic.

Spec§A6.4.4, p.116

Describe an AtomicCompare of 4-byte values at 0x104 on a 64-bit channel. Advanced

8 bytes outbound (compare + swap), AWSIZE 8 bytes, AWADDR 0x104 aligned to 4. 0x104 is the upper half of the 8-byte window 0x100–0x107, so the swap value goes in the lower bytes, the compare value in the upper bytes, and AWBURST is WRAP (Length 1 and an unaligned-to-Size WRAP are allowed here). Read data returns 4 bytes.

Spec§A6.4.3, p.115 · Figure A6.2, p.116

How does a Manager know whether an AtomicCompare swapped? Advanced

Only by comparing the returned original value with its compare value. Responses carry no outcome.

Spec§A6.4.8, p.119

Why is "Domain not Shareable" a restriction on AXI exclusives? Advanced

Shareable locations may be cached coherently by several agents, so an exclusive must be resolved by the coherence protocol rather than a single endpoint monitor. AXI keeps exclusives to Non-shareable and System locations, which reach a monitor at the endpoint.

Spec§A6.3.3, p.111 · Background on coherent exclusives

What changed in responses between AXI4 and Issue L? Advanced

Optional 3-bit width with DEFER, TRANSFAULT and UNSUPPORTED on B and PREFETCHED, TRANSFAULT and OKAYDIRTY on R; BCOMP for two-response writes; Busy indicators; Consistent_DECERR; and the clarification that Managers may sample RDATA on error beats.
