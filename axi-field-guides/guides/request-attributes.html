AXI Request Attributes Field Guide

Address, size and length say what to access. The request attributes say how the system may treat the access: who may answer a write, whether it may be split, merged, cached or prefetched, which address space and privilege it belongs to, how urgent it is. This guide covers AxCACHE and the twelve memory types, protection and physical address spaces including RME, GDI and MEC, regions and QoS. It includes decoders, waveforms, verification checks, interview questions, and what changed from AXI3 and AXI4.

1 · Why requests carry attributes

An interconnect, a system cache and a memory controller all want to optimise traffic. The attributes tell each of them which optimisations are safe for this request.

Correctness for devices

Peripherals have side effects

Reading a status register can clear it; writing a FIFO pushes data. These must not be prefetched, merged, split or cached. Device memory types forbid all of that.

Spec§A4.1, p.67 · §A4.3.1, p.71–72

Performance for memory

Normal memory can be optimised freely

Modifiable requests may be split, merged, widened or prefetched; cacheable ones may be served from caches; Bufferable writes may be answered early.

Spec§A4.2, p.68–70

Security

Privilege and address spaces

Privileged/unprivileged, Secure/Non-secure, and with RME the Root and Realm spaces (plus SA and NSP with GDI) let firewalls and memory encryption tell accesses apart. Same address, different space, can be different memory.

Spec§A4.5, p.77–80 · §A4.6, p.81

Quality of service

Who goes first

AxQOS ranks requests when nothing else forces an order; QoS accept lets a busy Subordinate say which requests it will take now.

Spec§A4.8, p.86–87

2 · Who reads which attribute

Every component between Manager and memory looks at a different subset.

Two kinds of Subordinate. A Memory Subordinate must handle every transaction type correctly. A Peripheral Subordinate documents its own access method; any other access must still complete protocol-correctly, but the peripheral need not keep working correctly afterwards.

Spec§A4.1, p.67

3 · AxCACHE: four bits, two of them swapped

Bits [0] and [1] mean the same on reads and writes. Bits [2] and [3] carry "Allocate" (this access should allocate) and "Other Allocate" (another kind of access might have allocated the line), in opposite positions on AR and AW.

Spec§A4.2, p.68

Why the swap

In AXI3, bit 2 was Read-Allocate and bit 3 Write-Allocate on both channels. AXI4 kept the bit positions for compatibility but changed the meaning: on a read, the write-allocate bit now says "this line might be in a cache because of something else". Issue L names the bits for what they mean on each channel, which is why the names swap.

SpecH.c §A4.2, p.A4-63 · §A4.3.2, p.A4-65–A4-66 · §A4.2, p.68

[0] Bufferable

Write: if LOW and [3:2] are 0b00, the response comes from the final destination. If HIGH, it may come from an intermediate point once the observability rules are met. Read: matters only for Normal Non-cacheable (Modifiable, [3:2] = 0): HIGH allows data from a write still on its way.

Spec§A4.2.1, p.68–69 · Table B4.3, p.312

[1] Modifiable

LOW: Non-modifiable, no split or merge, Size/Length/Burst/address/protection fixed (Length > 16 may still be split). HIGH: may be split, merged, prefetched, widened; never into another 4 KB space or a split atomic access.

Spec§A4.2.2, p.69–70

[2], [3] Allocate and Other Allocate

Either set: the line might be in a cache, so look it up. Allocate set: allocating is recommended. Only Other Allocate set: allocating is not recommended. Both clear: no lookup needed.

Mismatched attributes

All Managers must agree on cacheability of a region: Non-cacheable ⇒ [3:2] = 0b00 for everyone; Cacheable ⇒ at least one of [3:2] set. Allocation hints may differ. Normal Non-cacheable may be accessed as Device; a Bufferable region may be accessed without Bufferable behaviour.

Spec§A4.3.2, p.74

Changing attributes

To change a region to an incompatible type: all Managers stop, one Manager does the cache maintenance, all restart with the new attributes.

Spec§A4.3.3, p.74

Protocol errors

Software protocol error: mismatched shareability or cacheability. Data may be corrupted, but only in that 4 KB region, and the system must not deadlock. Hardware protocol error: anything else, no recovery guaranteed.

Spec§A4.4, p.76

    Privilege and instruction

    AXI distinguishes only privileged vs unprivileged. The instruction bit is a hint that may be wrong for mixed fetches; mark data unless known to be an instruction access.

    Spec§A4.5.2, p.78

    RME and GDI

    RME adds Root and Realm spaces and affects CMOs and MPAM. GDI (Issue L) adds System Agent and Non-secure Protected for non-PE data flows; PEs may not access them except for CMOs to the PoPA. GDI requires RME and PAS_WIDTH 3.

    Spec§A4.5.4–A4.5.5, p.79–80

    Memory Encryption Contexts

    AxMECID (16 bits) picks an encryption context per Realm. Zero in Secure, Non-secure and Root; any value in Realm, SA, NSP. Don't-care for most CMOs; must be 0 for DVM Complete. Caches store the MECID with the data and write it back with it.

    Spec§A4.6, Tables A4.10–A4.14, p.81–83

    7 · Region and QoS

    AxREGION

    A decode the Subordinate doesn't have to do

    • 4 bits, up to 16 regions, produced by the interconnect's address decoder; default 0 when a Subordinate has one region.
    • Constant within any 4 KB space.
    • Not a new address space; only on interfaces downstream of a decode.
    • The Subordinate must answer correctly for unsupported regions (error or alias) and keep same-ID ordering across regions.

    Spec§A4.7, p.84–85

    AxQOS and QoS accept

    Priority when the rules allow a choice

    • 4-bit AxQOS; higher = more important (recommended). Exact use is system-defined; interconnects often overwrite it from registers.
    • Default policy: pick the higher QoS, but only where AXI ordering doesn't already force an order.
    • VAxQOSACCEPT: the Subordinate accepts QoS ≥ this level without delay; lower ones may wait a long time, recommended not forever.

    Spec§A4.8, p.86–88

    8 · Why each rule exists, with real-time examples

    Rule, reason, worked example, and what breaks when it's ignored.

    Bufferable§A4.2.1 p.68

    Who may answer a write

    Non-bufferable (and [3:2] = 0): the response must come from the final destination. Bufferable: an intermediate point may respond.

    Why

    A posted write that an intermediate buffer acknowledges lets the CPU move on in a few cycles instead of waiting for the full round trip. Some writes need the round trip, though: the driver must know the device has really seen the value before the next step.

    Real-time example

    A write to a PCIe-attached device's register takes about 1 µs to reach it. Device Bufferable: the CPU sees BRESP from the local buffer in ~20 ns. Device Non-bufferable: it waits the full 1 µs.

    If you break it

    A buffer that answers Non-bufferable writes early breaks "write then read back to confirm" driver sequences and interrupt-clear races.

    Bufferable§A4.3.5 p.75

    Device B, then Device NB, same ID

    A Device Non-bufferable write after Device Bufferable writes with the same ID to the same device completes only after those writes are visible.

    Why

    Same-ID writes to one Subordinate are ordered, and the Non-bufferable one must reach the destination before it is answered. So its response proves the earlier ones arrived. You get posted-write speed and a cheap way to confirm.

    Real-time example

    A driver writes 8 descriptor-ring registers as Device Bufferable, then the doorbell as Device Non-bufferable with the same ID. One full round trip instead of nine.

    If you break it

    A different ID, or a different device, gives no guarantee. That's a common driver bug when an interconnect remaps IDs per Manager thread.

    Bufferable§A4.3.4 p.74–75

    Buffers must drain, even under pressure

    Bufferable writes must reach their destination in a timely manner. Merging a new write must not reset the drain timer, and reading forwarded data must not reset its timeout.

    Why

    A CPU that polls or repeatedly writes one location could otherwise pin a write in a buffer forever. The other side, a device waiting for that value, would never see it.

    Real-time example

    A spin loop writes a progress counter every 50 ns into a write-combining buffer with a 1 µs drain timer. If each merge reset the timer, the counter would never leave the buffer.

    If you break it

    Livelock that shows up only under tight software loops.

    Modifiable§A4.2.2 p.69

    Non-modifiable means "exactly as sent"

    No split, no merge. Address, Size, Length, Burst and protection unchanged. AxCACHE may only go from Bufferable to Non-bufferable; ID and QoS may change.

    Why

    A peripheral may react differently to one 8-byte access than to two 4-byte ones, for example a 64-bit timer that latches its high word on a 64-bit read. Keeping the shape lets the peripheral see exactly what software asked for.

    Real-time example

    A 64-bit read of a timer at 0x5000 through a 32-bit downsizer must become two reads. The spec allows it, because downsizing below Size is impossible otherwise, and lets the component flag the change through an IMPLEMENTATION DEFINED mechanism for debug.

    If you break it

    Torn reads of multi-word registers, double side effects from split FIFO accesses.

    Sources
    • Spec§A4.2.2 and Table A4.3, p.69

    Modifiable§A4.2.2 p.69–70

    Modifiable has limits too

    Modifiable requests may be split, merged, widened or prefetched, but never into a different 4 KB space, never splitting a single-copy-atomic access, never changing AxLOCK or protection attributes, never reducing visibility.

    Why

    The 4 KB limit keeps decode correct. The atomicity limit keeps a CPU's naturally aligned 64-bit store from being seen half-done. Protection must not change because it decides who may access the memory at all.

    Real-time example

    An upsizer may widen a 4-byte read at 0x7FFC to a 16-byte read at 0x7FF0, but not to 0x7FF0–0x800F, which would cross into the next 4 KB page.

    If you break it

    Prefetching into another page can touch a read-sensitive device mapped there, or trigger a security fault on an address the program never used.

    Modifiable§A4.2.2 p.69

    Two exceptions for Non-modifiable

    A Non-modifiable request with Length > 16 may be split. An exclusive Non-modifiable request may change Size and Length if the total bytes stay the same.

    Why

    Long bursts must pass through AXI3-era components and QoS-limited paths. Exclusive accesses must survive width conversion while still covering exactly the monitored bytes.

    Real-time example

    An exclusive 8-byte load (Size 8, Length 1) through a 32-bit downsizer becomes Size 4, Length 2: still 8 bytes, still one exclusive access.

    If you break it

    Splitting an exclusive into two separate exclusives breaks the monitor; changing total bytes breaks exclusivity.

    Allocation & types§A4.2.3 p.70

    Lookup if either allocate bit is set

    AxCACHE[3:2] ≠ 0b00 ⇒ the line might be cached, so look it up. Allocation itself is only a recommendation.

    Why

    Correctness depends only on "could it be in a cache?". Whether to allocate is a performance hint. Separating them means a wrong hint can only cost performance, never correctness.

    Real-time example

    A streaming read with ARCACHE 0b1011 (Write-Back No-Allocate) still looks up the system cache (a CPU might have the line dirty) but doesn't evict useful lines to store the stream.

    If you break it

    Skipping the lookup on a "No-Allocate" read returns stale DRAM data when the line is dirty in a cache.

    Allocation & types§A4.3.2 p.74

    Agree on cacheability, not on hints

    All Managers must use the same cacheability for a region; allocation hints may differ; Device access to Normal Non-cacheable is fine.

    Why

    If one Manager reads a region as cacheable and another writes it as Non-cacheable, the writer bypasses the cache that the reader is hitting. Allocation hints don't cause this problem, so they can differ.

    Real-time example

    A GPU writes a buffer as Normal Non-cacheable; the CPU maps the same pages Write-Back. The CPU reads stale cached data: a software protocol error, contained to those 4 KB regions.

    If you break it

    Silent data corruption. The protocol only promises no deadlock and no damage outside the region.

    Sources
    • Spec§A4.3.2, p.74 · §A4.4.1, p.76

    Errors & changes§A4.4 p.76

    Software vs hardware protocol errors

    Software protocol errors (mismatched attributes) may corrupt data in that 4 KB region but must not deadlock. Hardware protocol errors (everything else) carry no guarantees.

    Why

    Software bugs are expected and must not take the whole SoC down; hardware must still make progress. Hardware protocol violations mean a component is broken, and requiring recovery from those would make every component pay for every other component's bugs.

    Real-time example

    A user process maps a peripheral as Normal memory: the peripheral may misbehave, but it must still answer every transaction so the interconnect doesn't hang.

    If you break it

    A peripheral that stops responding to unexpected Modifiable accesses turns a software bug into a system hang.

    Sources
    • Spec§A4.4, p.76 · §A4.1, p.67
    Protection§A4.5.3 p.79

    Same address, different space

    Requests with the same address but a different physical address space may decode to different memory.

    Why

    Secure firmware, a hypervisor's Realm, and Non-secure Linux can each own memory at the same physical address. The PAS acts like extra address bits, so caches and firewalls must include it in their tags and checks.

    Real-time example

    A system cache that tags lines without the PAS would let a Non-secure read of 0x8000_0000 hit a line filled by a Secure access to 0x8000_0000.

    If you break it

    Cross-world data leaks: a security vulnerability, not just a bug. Note that Modifiable transforms must never change protection attributes.

    Sources
    • Spec§A4.5.3, p.79 · §A4.2.2, p.70

    Protection§A4.6.2 p.82–83

    MECID: preserved, stored, written back

    Components that pass a request on must preserve AxMECID where it applies; caches must store it with the data and supply it on write-back.

    Why

    The memory encryption engine picks the key from the MECID. If a cache wrote back a Realm's dirty line with the wrong or no MECID, the data would be encrypted with another Realm's key and become unreadable, or readable by the wrong Realm.

    Real-time example

    Realm A writes with MECID 0x0012; the line is evicted later during Realm B's activity. The write-back must still carry 0x0012.

    If you break it

    Data corruption at the encryption point. With GDI, MECID mismatches in SA and NSP must be masked so data never leaks between contexts.

    Region & QoS§A4.7.2 p.84

    AxREGION constant within 4 KB

    The region identifier must not change within any 4 KB space.

    Why

    Bursts never cross 4 KB, so a region that is constant per 4 KB is constant per burst. The Subordinate can select its logical interface once per request.

    Real-time example

    A decoder that maps region 1 to 0x9000_0000–0x9000_07FF (2 KB) would violate this: a 4 KB-aligned burst could start in region 1 and run into region 0.

    If you break it

    The Subordinate applies one region's behaviour (say, read-only) to data meant for another.

    Sources
    • Spec§A4.7.2, p.84
    • Illustrativemap
    Region & QoS§A4.8.1 p.86

    Ordering beats QoS

    Pick the higher QoS only when no AXI ordering rule already decides the order.

    Why

    QoS is a performance hint; ordering is correctness. A high-QoS read must not overtake a same-ID read whose data the Manager expects first.

    Real-time example

    A display controller (QoS 14) and a CPU (QoS 4) both target DDR. The arbiter favours the display, but within the display's own same-ID stream it keeps request order.

    If you break it

    Reordering same-ID traffic for QoS returns data out of order to a Manager that relies on ID ordering.

    12 · Verification

    Assertions

    • AxCACHE is one of the Table A4.4 values for its channel (no reserved encodings). Table A4.4, p.71
    • Interconnect: a Non-modifiable request leaves with the same ADDR, SIZE, LEN, BURST, PROT/PAS/NSE/INST/PRIV; AxCACHE differs at most in bit 0 going 1→0. §A4.2.2, p.69
    • Interconnect: any output request has the same 4 KB page as its input. §A4.2.2, p.70
    • Interconnect: AxLOCK and protection never change. §A4.2.2, p.70
    • Buffer: no early BRESP when AWCACHE[0] = 0 and AWCACHE[3:2] = 0. §A4.2.1, p.68
    • PROT_Present ⇒ no AxPAS, no AxINST/AxPRIV. AxPAS ∉ {6, 7}; SA/NSP only with GDI_Support. §A4.5.1, p.77 · Table A4.7, p.79
    • AxMECID = 0 for Secure, Non-secure, Root; DVM Complete MECID = 0. Table A4.14, p.82 · p.83
    • AxREGION constant across a 4 KB space (for decoders). §A4.7.2, p.84

    • All 10 legal AR and 10 legal AW AxCACHE values × burst type × Length > 16.
    • Each memory type × response source (endpoint vs buffer) × read forwarding.
    • AxPROT 8 values (or AxPAS 6 values × PRIV × INST) × MECID zero/non-zero.
    • QoS: all 16 values; accept level crossing while requests wait; region 0–15 including unsupported ones.

    13 · Test yourself

    Use the decoders above to check your answers.

    What do the four AxCACHE bits mean, and which two swap between AR and AW? Basic

    [0] Bufferable, [1] Modifiable on both. On AR, [2] Allocate and [3] Other Allocate; on AW, [2] Other Allocate and [3] Allocate.

    Spec§A4.2, p.68

    Device Non-bufferable vs Device Bufferable: what's the difference? Basic

    Only for writes: Device Bufferable may get its response from an intermediate point and must reach the destination in a timely manner. Reads are identical: data from the final destination. Both are Non-modifiable, no prefetch, no merge.

    Spec§A4.3.1, p.71–72

    What may an interconnect do to a Modifiable transaction, and what may it never do? Basic

    Split, merge, fetch more on reads, write a larger range with strobes, change address/size/length/burst, change AxCACHE without reducing visibility, change ID and QoS. Never: change AxLOCK or protection attributes, cross into another 4 KB space, or split a single-copy-atomic access.

    Spec§A4.2.2, p.69–70

    When must a transaction be looked up in a cache? Basic

    Whenever AxCACHE[3:2] is not 0b00. Allocation is only a hint; lookup is a requirement.

    Spec§A4.2.3, p.70

    A driver needs to know that its last eight posted register writes reached the device. How? Intermediate

    Issue the writes Device Bufferable, then one Device Non-bufferable write with the same AXI ID to the same device. Its response comes from the device and, through same-ID ordering, implies the earlier writes are visible.

    Spec§A4.3.5, p.75

    ARCACHE = 0b1010. What memory type is it? Intermediate

    Write-Through No-Allocate, or equally Write-Through Write-Allocate: on a read the write-allocate hint has no effect, so Table A4.4 gives both the same ARCACHE. It must be looked up and allocation is not recommended for this read.

    SpecTable A4.4, p.71 · §A4.3.1, p.72–73

    Can a Non-modifiable transaction ever be split? Intermediate

    Yes, in two cases: Length greater than 16 (into shorter bursts with adjusted addresses), and when downsizing below Size makes it unavoidable. An exclusive Non-modifiable access may also change Size and Length if the total bytes stay the same.

    Spec§A4.2.2, p.69

    What is a software protocol error and what must the system guarantee? Intermediate

    Accesses to one location with mismatched shareability or cacheability. Data may be corrupted, but only within that 4 KB region, and the system must not deadlock; transactions must keep progressing.

    Spec§A4.4.1, p.76

    How is Realm PAS signalled with AxPROT, and with AxPAS? Advanced

    AxPROT[1] = 1 with AxNSE = 1 (needs RME_Support and PROT_Present), or AxPAS = 0b011. An interface has one set or the other, not both.

    SpecTable A4.7, p.79 · §A4.5.1, p.77

    Under GDI, a cache holds a System Agent PAS line tagged MECID 5. A partial write with MECID 9 to that line arrives. What happens? Advanced

    The cached data is masked to an IMPLEMENTATION SPECIFIC value (all ones recommended), the partial write is merged into it, and the cached MECID becomes 9. A read with a mismatched MECID returns masked data.

    Spec§A4.6.3, p.83

    How did AxCACHE change from AXI3 to AXI4 to Issue L? Advanced

    AXI3: Bufferable, Cacheable, Read-Allocate, Write-Allocate, same positions on both channels. AXI4: bit 1 renamed Modifiable (same function) and RA/WA redefined so the opposite-direction bit means "might be allocated by another transaction"; lookup needed if [3:2] ≠ 0. Issue L: same encodings, bits named Allocate/Other Allocate per channel; Bufferable meaning on writes corrected.

    SpecH.c §A4.2–A4.3, p.A4-63–A4-66 · §A4.2, p.68 · Table B4.3, p.312

    Why must AxREGION be constant within 4 KB, and who generates it? Advanced

    Because no burst crosses 4 KB, a per-4 KB constant region is constant for the whole burst. The interconnect's address decoder generates it for a Subordinate with multiple logical interfaces; otherwise it is the default 0.

    Spec§A4.7.2, p.84
