AXI Caches & CMOs Field Guide

AXI doesn't snoop, but it lives in systems full of caches. This guide covers how AXI requests say which caches they must touch (Domains plus memory type), I/O coherency, caching Shareable lines in a system cache, the hint transactions (Prefetch, stash, deallocating reads, InvalidateHint), and cache maintenance operations, including write-with-CMO, persistence, PoPA and PoPS. It includes cache-lookup decoders, waveforms, verification checks, interview questions and what changed from AXI4 and ACE.

1 · Why AXI needs to talk about caches

Visibility

Somebody must see the write

Data can be cached at many points. Every request must say how far it has to go to be visible to the agents that care, without AXI itself snooping.

Spec§A8.1, p.132 · §A8.3, p.134

Three coherency styles

Non-cacheable, software, hardware

AMBA supports Non-cacheable sharing, software coherency with cache maintenance, and hardware coherency with snooping (CHI). AXI supports all three through a Domain on every location.

Spec§A8.3, p.134

I/O coherency

AXI agents next to CHI caches

A DMA or NIC on AXI can read and write coherently through a CHI interconnect, without having a snoopable cache of its own.

Spec§A8.4, p.137

Performance

Hints and stashing

Prefetch, stash and deallocation hints move data to where it will be used, or out of the way, without affecting correctness.

Spec§A8.6–A8.9, p.142–152

2 · Where the caches sit

3 · Domains

System (AxDOMAIN 11)

Visible to every Manager that can access it, by never caching it: System requests are Non-cacheable. Required for Device. Simple, not fast.

Spec§A8.3.1, p.134

Non-shareable (00)

Not required to be visible to others; no hardware coherency. Sharing needs CMOs (software coherency). Clean Non-shareable lines must not be written back on eviction, and Dirty data must not be passed to another cache on a read.

Spec§A8.3.2, p.134

Shareable (01 or 10)

Visible to all Managers that also mark it Shareable: snoop local caches, look up caches that may hold others' Shareable data. INCR or WRAP only, not FIXED. 0b10 recommended; older issues used 01 Inner / 10 Outer Shareable.

Spec§A8.3.3–A8.3.4, p.134–135

Which caches does a request touch?

No AxDOMAIN on the interface? Non-cacheable requests are assumed System. For Cacheable requests Issue L gives two different answers: the first paragraph of §A8.3.4 says Non-shareable, the list after Table A8.5 says Shareable. CMOs without AxDOMAIN are assumed Non-shareable. Pin this down in your system's integration spec rather than relying on either sentence.

5 · Cache lines and Shareable lines

Cache line sized transactions

  • Cache_Line_Size 16 to 2048 bytes, default 64; 64 for CHI compatibility. One common size for any system that shares caches.
  • A line must fit in 16 transfers or fewer on interfaces that carry line-sized transactions.
  • Must be line sized and Regular: ReadShared, ReadClean, CleanShared, CleanInvalid, MakeInvalid, CleanSharedPersist, ReadNoSnoop with MTE Fetch, WriteNoSnoopFull, WriteUniqueFull, WriteBackFull, WriteEvictFull, CMO, WriteZero, WriteUniqueFullStash, WriteFullCMO, StashOnceShared/Unique, Prefetch, InvalidateHint.
  • Size × Length = line size; writes have every strobe set.

Spec§A8.2, Table A8.2, p.133

Caching Shareable lines (system cache below CHI)

  • States: Clean, Dirty, Shareable Clean, Shareable Dirty.
  • ReadShared (may return Dirty with OKAYDIRTY) and ReadClean (must be Clean) fill upstream caches.
  • WriteBackFull (Shareable Dirty evict) and WriteEvictFull (Shareable Clean evict; must never update memory).
  • WriteNoSnoopFull: Non-shareable full-line Dirty write, not allocated upstream. WriteUniqueFull: I/O coherent full-line write.
  • Shareable_Cache_Support must be False on I/O coherent interfaces; BROADCASTSHAREABLE LOW converts everything to Non-shareable equivalents (WriteEvictFull is dropped).

Spec§A8.5, p.138–141 · §A8.4, p.137

6 · Hint transactions

All of these may be ignored or answered early without breaking correctness. That is what makes them hints.

Attributes

Line sized, Regular, Non-shareable or Shareable, never System (so never Device). Cacheable/Shareable for a CMO should match the location's normal attributes; allocation hints need not.

Spec§A9.3, p.156

Write with CMO

WritePtlCMO (≤ a line, not FIXED) and WriteFullCMO (line, Regular). The CMO part is always cacheable and Shareable, covers the whole line. May be split into the write then the CMO (same ID on AW, or after the write response).

Spec§A9.6, p.160–162

Persistence, PoPA, PoPS

CSP/CSDP on AW get two B responses (BCOMP, BPERSIST) in any order, or one combined. PoPA (RME) and PoPS (poison scrubbing, Issue L) have their own CMOs and tie-offs.

Spec§A9.8–A9.10, p.164–171

8 · Why each rule exists, with real-time examples

Domains§A8.3.2 p.134

Never write back a Clean Non-shareable line

Evicting Clean Non-shareable data with a write-back is not permitted; Dirty data isn't passed between caches on a Non-shareable read.

Why

Another Manager may have written a newer Dirty copy into a downstream cache. A Clean line arriving later would overwrite it with older data. Passing Dirty upward would create a second copy that is responsible for a write-back and could later overwrite a newer update.

Real-time example

A GPU L2 holds a Clean copy of 0x4000; a DMA writes 0x4000 into the system cache (now Dirty). If the GPU's eviction wrote its Clean copy back, the DMA's data would be lost.

If you break it

Lost updates that look like software coherency bugs.

Sources

DomainsTable A8.7 p.136

Device is System; System is Non-cacheable

Device requests must use the System Domain, and System Domain requests are Non-cacheable.

Why

A device register must be visible to everybody immediately and must never sit in a cache. Tying Device to System, and System to Non-cacheable, makes "visible to all" a structural property rather than a promise someone has to keep.

Real-time example

An interrupt controller register access with AxDOMAIN = 00 is illegal; a checker should flag it before a cache tries to allocate it.

If you break it

Status bits read from a stale cached copy.

Sources
  • Spec§A8.3.1, p.134 · Table A8.7, p.136
Cache lines§A8.5.1 p.140

WriteEvictFull never reaches memory

Data from a WriteEvictFull (a Shareable Clean eviction) must not update memory, and Shareable Clean lines must not be exposed outside the Shareable Domain.

Why

Within the Shareable Domain, another cache may hold the line Dirty with newer data. The Clean evicted copy is only useful as a cache fill; writing it to memory could overwrite newer data that hasn't been written back yet.

Real-time example

A CPU evicts a Clean shared line into the system cache with WriteEvictFull; a second CPU still holds it Unique Dirty. The system cache may keep it as Shareable Clean, but must never write it to DRAM.

If you break it

Stale data overwriting fresh data in memory.

Sources
  • Spec§A8.5.1, p.140 · Table B4.2, p.309
Hints§A8.7.5 p.147

StashOnce IDs are kept apart

A StashOnce must not share an ID with outstanding non-StashOnce write-channel transactions.

Why

A component that doesn't support stashing should be able to answer a StashOnce instantly. If it shared an ID with a pending write, answering early would put the B responses out of order.

Real-time example

A NIC uses ID 7 for StashOnce and IDs 0–6 for packet writes. Any bridge can drop StashOnce with an immediate OKAY.

If you break it

An early StashOnce response overtakes a same-ID write response: an ordering violation.

Sources
  • Spec§A8.7.5, p.147
  • IllustrativeIDs
Hints§A8.6 p.142

Prefetch isn't ordered with CMOs

A Prefetch must not be used to signal that a line can be fetched into a managed or visible cache.

Why

A Prefetch may be overtaken by, or overtake, a CMO for the same line. If it allocated into a cache that software manages with CMOs, stale data could reappear right after software invalidated it.

Real-time example

Prefetch into a memory controller's row buffer is fine; prefetch into a CPU-visible system cache line that a driver is about to invalidate is not.

If you break it

Software coherency silently broken by a performance feature.

Sources
  • Spec§A8.6, p.142 · Table B4.1, p.308
Hints§A8.9 p.151

InvalidateHint can expose old data

Because the hint may drop a Dirty line without writing it back, care is needed to avoid exposing previously overwritten values.

Why

If a scrubbing write (say, zeroing a key buffer) is still Dirty in a cache and an InvalidateHint drops it, memory still holds the old secret.

Real-time example

Crypto software zeroes a 64-byte key buffer, then issues InvalidateHint. Without a clean in between, DRAM still holds the key.

If you break it

Security leak. Clean after the scrubbing write, or restrict the hint to non-sensitive ranges.

Sources
  • Spec§A8.9, p.151
  • Illustrativecrypto example
CMOs§A9.1 p.154

CMOs on the write channels

CMOs may travel on read or write channels; write channels are recommended for new designs.

Why

A CMO has no data to return, so B fits it naturally. On the write channels it can also be combined with a write (WritePtlCMO, WriteFullCMO) and can carry the two-response persistence protocol.

Real-time example

A storage controller flushing a log record to persistent memory: one WriteFullCMO with CSP instead of a write, wait for B, then a CSP on AR.

If you break it

Read-channel CMOs can't express CSDP, CIPA or CIS, and can't combine with data.

Sources
  • Spec§A9.1, p.154 · §A9.5–A9.6, p.158–161 · Table A9.11, p.163
CMOs§A9.8.4 p.165

Two responses for persistence

CSP and CSDP on the write channels get a Completion response and a Persist response, in either order, or both in one transfer.

Why

Reaching persistent media can take far longer than reaching visibility. Separating them lets the interconnect free tracking at visibility and still tell software when the data is durable.

Real-time example

Completion after 300 ns when the line hits the memory controller's queue; Persist after 2 µs when the NVDIMM confirms.

If you break it

A Manager that waits for "the" B and treats the first one as persistent loses data on power failure.

Sources
  • Spec§A9.8.4, p.165–166
  • Illustrativetimings
CMOs§A9.10 p.170

CleanInvalidStorage for poison scrubbing

CIS cleans and invalidates every cache and buffer up to the Point of Physical Storage, so the next read comes from memory.

Why

To clear poison, software writes a good value and reads it back. If the write stayed in a cache, the read-back would "pass" while memory still has the fault. CIS forces the write all the way out and makes the read-back honest.

Real-time example

A server RAS daemon: write 0 to the poisoned line, WriteFullCMO with CIS, then read: still poisoned ⇒ persistent fault, retire the page.

If you break it

Persistent faults misreported as fixed.

Sources

12 · Verification

Assertions

  • Legal AxSNOOP/AxDOMAIN pair (Tables A7.3–A7.4) and memory type/Domain (Table A8.7). p.126–136
  • Line-sized Opcodes: Size × Length = Cache_Line_Size, Regular, all strobes. §A8.2, p.133
  • CMOs: never System; no W data for stand-alone CMO; MakeInvalid never on AW. §A9.3, §A9.5, p.156–159
  • Stash: target enables LOW on non-stash; NID/LPID zero when disabled; no line crossing. §A8.7.2–A8.7.4, p.145–146
  • Unique ID for Prefetch, InvalidateHint; StashOnce IDs separate. §A8.6.1, §A8.7.5, §A8.9.1
  • PCMO: exactly one BCOMP and one BPERSIST per CSP/CSDP (or one combined). §A9.8.4, p.166
  • PREFETCHED only with RRESP_WIDTH 3, never on exclusive reads. §A8.6.2, p.143

Scoreboarding caches

  • Model per line: state (I, Clean, Dirty, SC, SD) plus memory value; drive Table A8.8 must/must-not hit as assertions.
  • For each CMO, after its response check: no in-scope copy is Dirty (cleans) or valid (invalidates), memory holds the latest write.
  • Software-coherency tests that follow Figure A9.3, plus negative tests that break the order to make sure the testbench notices.
  • Coverage: Opcode × Domain × line state; CMO type × channel; Persist response order (before, after, combined); stash with/without targets × Basic/True.

13 · Test yourself

What are the three Domains and what does each guarantee? Basic

System: visible to all, achieved by never caching (Non-cacheable; Device must use it). Non-shareable: no visibility requirement, software must use CMOs to share. Shareable: visible to all agents that mark it Shareable, via snooping and lookup.

Spec§A8.3.1–A8.3.3, p.134

What does an I/O coherent Manager do and not do? Basic

It reads and writes Shareable data through a coherent interconnect (ReadOnce, WriteUnique*), but it can't be snooped, so it must not cache Shareable data. Shareable_Cache_Support must be False.

Spec§A8.4, p.137

Hint vs CMO: what's the difference in obligation? Basic

Hints (Prefetch, stash, deallocating reads, InvalidateHint) may be ignored or answered early. A CMO must be actioned by every cache that holds the line in its scope.

Spec§A8.7, p.144 · §A8.9, p.151 · §A9.1, p.154

Which caches does a Normal Cacheable Non-shareable CMO apply to? A Normal Non-cacheable Shareable one? Intermediate

In-line caches; peer caches.

SpecTable A9.1, p.156

Why may a Shareable Clean line evicted with WriteEvictFull never update memory? Intermediate

Another cache in the Shareable Domain may hold a newer Dirty copy. Writing the Clean data to memory could overwrite data that hasn't been written back yet.

Spec§A8.5.1, p.140

Explain the two B responses for a CleanSharedPersist on AW. Intermediate

Completion (BCOMP): observable, follows normal ordering. Persist (BPERSIST): reached the PoP, no ordering requirements. Either order, or one transfer with both set.

Spec§A9.8.4, p.165–166

Why can a StashOnce be answered immediately by a component that doesn't stash? Intermediate

StashOnce IDs can't be shared with outstanding non-StashOnce writes, so an early response can't violate same-ID ordering, and stashing is only a hint.

Spec§A8.7.5, p.147

Describe the five stages for sharing a buffer with a non-coherent DMA. Where is the CPU's view unpredictable? Advanced

1 coherent access; 2 clean; 3 non-coherent access; 4 invalidate; 5 coherent access. Between the clean and the invalidate, observation of the line is UNPREDICTABLE.

Spec§A9.11.1, Figure A9.3, p.172–173

A processor CMO instruction targets a Device location but must reach all caches. What does the Manager issue? Advanced

A Normal Cacheable Shareable CMO, the most pervasive kind, because CMOs can't be System/Device.

Spec§A9.11, p.172 · §A9.3, p.156

What is the Point of Physical Storage and which CMO targets it? Advanced

The furthest point a write can propagate, after all caches and buffers, normally the memory interface. CleanInvalidStorage (AWCMO 101, Issue L) cleans and invalidates everything up to it so a read-back really tests memory, used for poison scrubbing.

Spec§A9.10, p.170

What changed for AxDOMAIN between ACE and Issue L? Advanced

ACE: 01 Inner Shareable, 10 Outer Shareable. Issue L: both mean Shareable, 10 recommended; the signals are optional on any interface class, and full coherency (snoop channels) moved to CHI.
